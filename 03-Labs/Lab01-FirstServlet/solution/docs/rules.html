Règles de Gestion

20 règles numérotées R1–R20 extraites du code source — validation des données, stockage, navigation, sécurité et observabilité.

Légende

Standard

Règle standard

Comportement fonctionnel normal de l'application — validation courante, navigation, affichage.

Critique

Règle critique

Sécurité ou intégrité des données — violation possible en cas de non-respect, avec impact direct sur la sécurité ou la cohérence.

Avertissement

Règle avertissement

Limitation connue ou comportement inhabituel à connaître (pas de persistance, données volatiles, etc.).

1. Validation des données
R1 Client-side
Champs obligatoires — alerte JavaScript
La fonction validateForm() dans add-client.html vérifie que les trois champs name, email et phone sont non vides après trim(). Si l'un est vide, une alert() est affichée et return false empêche la soumission du formulaire.
R2 Client-side
Longueur minimale du nom — 2 caractères
JavaScript vérifie que name.length < 2 après trim. Si la condition est vraie, une alerte "Name must be at least 2 characters long!" est affichée et la soumission est bloquée. L'attribut HTML minlength="2" fournit la même contrainte au niveau du navigateur.
R3 Client-side
Validation du format email par regex
JavaScript applique la regex /^[^\s@]+@[^\s@]+\.[^\s@]+$/ à la valeur du champ email. En cas d'échec, une alerte "Please enter a valid email address!" est affichée. L'attribut HTML type="email" fournit une validation complémentaire native.
R4 Client-side
Validation du format téléphone par regex
JavaScript applique la regex /^[\d\s\-\+\(\)]+$/ à la valeur du champ phone. En cas d'échec, une alerte "Please enter a valid phone number!" est affichée. L'attribut HTML type="tel" est utilisé sur le champ.
R5 Server-side
Validation serveur — champs non vides
Dans ClientListServlet.doPost(), les paramètres name, email et phone sont relus depuis la requête via request.getParameter(). Si l'un est null ou vide après trim(), le servlet appelle response.sendRedirect("add-client.html?error=missing") et sort immédiatement avec return.
R6 Critique Server-side
Échappement XSS — escapeHtml() obligatoire
Avant toute insertion d'une valeur client dans le HTML de réponse, la méthode escapeHtml() est appelée. Elle remplace & → &amp;, < → &lt;, > → &gt;, " → &quot;, ' → &#39;. Sans cet échappement, une injection XSS serait possible via les champs name, email, phone.
R7 Server-side
Trim des valeurs avant stockage
Dans doPost(), les trois champs sont stockés après trim() explicite : name.trim(), email.trim(), phone.trim(). Ainsi, les espaces en début et fin de chaîne ne sont pas conservés en base mémoire.
R8 Limitation
Longueurs maximales — contraintes HTML uniquement
Les attributs HTML maxlength="100" (name, email) et maxlength="20" (phone) limitent la longueur côté navigateur. Aucune vérification de longueur maximale n'est effectuée côté serveur dans doPost(). Un client HTTP sans navigateur pourrait soumettre des valeurs plus longues.
2. Stockage des données
R9 Avertissement
Stockage en mémoire uniquement — données volatiles
Tous les clients sont stockés dans une CopyOnWriteArrayList<Client> champ d'instance du servlet ClientListServlet. Toutes les données sont perdues à chaque redémarrage du serveur, rechargement du WAR ou arrêt du conteneur. Aucune base de données n'est utilisée dans ce Lab 01.
R10 Thread-Safety
Concurrence — CopyOnWriteArrayList
Le servlet étant un singleton partagé entre tous les threads de requête, la liste clients est déclarée final et de type CopyOnWriteArrayList. Les itérations dans doGet() et les ajouts dans doPost() sont ainsi thread-safe sans synchronisation explicite.
R11 Bootstrap
Données de démarrage — 5 clients pré-chargés
La méthode init() de ClientListServlet charge 5 clients hardcodés (IDs 1 à 5) à chaque démarrage du servlet : John Smith, Emma Johnson, Michael Brown, Sarah Davis, James Wilson. Ces données sont toujours présentes après un redémarrage.
R12 ID
Génération d'identifiant — max + 1
L'ID d'un nouveau client est calculé par clients.stream().mapToLong(Client::getId).max().orElse(0L) + 1. En l'absence de clients, l'ID commence à 1. Cette génération n'est pas atomique mais est suffisante dans un contexte mono-instance en mémoire.
3. Navigation et interface
R13 PRG
Pattern Post-Redirect-Get après création réussie
Après un POST /clients réussi, le servlet appelle response.sendRedirect("clients?message=success"). Le navigateur reçoit un HTTP 302, puis effectue un GET /clients?message=success. Ce pattern PRG empêche la double-soumission lors d'un rechargement de page.
R14 UX
Bannière de succès — paramètre URL message=success
Dans ClientListServlet.doGet(), si request.getParameter("message") retourne "success" (comparaison avec .equals()), une div <div class='message success'>Client added successfully!</div> est injectée en haut de la liste. La bannière disparaît lors de tout rechargement sans ce paramètre.
R15 UX
Message d'erreur côté client — paramètre URL error=missing
Dans add-client.html, le JavaScript window.onload lit URLSearchParams et, si le paramètre error=missing est présent, insère dynamiquement une div d'erreur rouge avant le formulaire : "⚠ All fields are required. Please fill in all information."
R16 Navigation
Welcome file — redirection vers index.html
Le fichier web.xml déclare index.html comme welcome-file. Toute requête GET / sans chemin explicite est redirigée vers index.html par Open Liberty.
4. Sécurité et session
R17 Critique
Cookie de session HttpOnly
La configuration web.xml impose <http-only>true</http-only> sur les cookies de session. Cela empêche l'accès au cookie JSESSIONID via JavaScript (document.cookie), réduisant le risque de vol de session par injection XSS.
R18 Session
Timeout de session — 30 minutes
Le fichier web.xml configure <session-timeout>30</session-timeout>. Les sessions HTTP inactives depuis plus de 30 minutes sont invalidées automatiquement par le conteneur Open Liberty.
R19 Critique
Encodage UTF-8 des réponses
Les deux servlets appellent response.setContentType("text/html;charset=UTF-8") avant d'écrire la réponse. Cela garantit l'encodage correct des caractères spéciaux dans toutes les réponses dynamiques.
5. Observabilité et opérations
R20 Log
Log des opérations significatives
ClientListServlet utilise la méthode log() héritée de GenericServlet pour deux événements : (1) à l'initialisation : "ClientListServlet initialized with 5 sample clients", (2) à chaque ajout : "New client added: Client{id=N, name='...', email='...', phone='...'}" via le toString() du POJO. Les logs apparaissent dans les traces Open Liberty (spec *=info).
