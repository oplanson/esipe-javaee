Règles de Sécurité

12 règles issues du code source de l'application, classées par criticité. Les règles critiques constituent des exigences non négociables de sécurité ; les règles d'avertissement signalent des configurations à renforcer en production.

● Critique ● Avertissement ● Recommandation

Règles critiques — Authentification et cryptographie

🔴 R1 CRITIQUE
Authentification JWT obligatoire sur tous les endpoints protégés
Tout endpoint protégé exige un token Bearer JWT valide dans l'en-tête Authorization: Bearer <token>. L'absence ou l'invalidité du token déclenche un retour 401 Unauthorized avant l'exécution du code métier.

Source : JwtAuthenticationMechanism.validateRequest()
🔴 R2 CRITIQUE
Hachage PBKDF2-SHA512 avec 310 000 itérations (standard OWASP 2023)
Les mots de passe ne sont jamais stockés en clair. L'algorithme PBKDF2WithHmacSHA512 est appliqué avec 310 000 itérations et un sel aléatoire de 64 octets unique par utilisateur. Ce paramétrage respecte la recommandation OWASP Password Storage Cheat Sheet 2023.

Source : PasswordService.hashPassword()
🔴 R3 CRITIQUE
Verrouillage du compte après 5 tentatives de connexion échouées
Le champ failed_login_attempts de l'entité User est incrémenté à chaque échec d'authentification. Lorsque le compteur atteint 5, le champ account_locked = true est positionné et tout accès ultérieur est bloqué jusqu'à un déblocage administratif.

Source : DatabaseIdentityStore + entité User
🔴 R4 CRITIQUE
Isolation CUSTOMER — accès aux seuls comptes personnels
Un utilisateur portant uniquement le rôle CUSTOMER ne peut consulter que les comptes dont account.ownerUsername == principal.getName(). Tout accès à un compte tiers est refusé avec 403 Forbidden et consigné dans la piste d'audit comme ACCESS_DENIED.

Source : AccountResource.getAccountById() + SecurityContext.isUserInRole("CUSTOMER")
🔴 R5 CRITIQUE
Secret JWT minimum 256 bits, expiration 24 h, double validation obligatoire
Le secret de signature HS256 doit comporter au minimum 256 bits (32 octets). Chaque token est validé sur deux critères simultanés :
  1. Signature HS256 — intégrité du token
  2. Expiration (exp) — token non expiré (24 h par défaut)
Un token dont l'une des deux validations échoue est rejeté immédiatement.

Source : JwtService.validateToken() / parseToken()

Règle d'avertissement — Configuration CORS

⚠️ R6 AVERTISSEMENT
CORS ouvert à toutes les origines — à restreindre en production
La configuration actuelle autorise Access-Control-Allow-Origin: *, ce qui permet à n'importe quel domaine d'effectuer des requêtes cross-origin vers l'API. En environnement de production, il convient de restreindre cette valeur aux domaines front-end connus (ex. https://bank.example.com).

Source : CorsFilter

Règles de bonnes pratiques

🔵 R7
Politique de mot de passe fort
Tout mot de passe soumis lors de l'inscription est évalué par PasswordService.isPasswordStrong(). Critères cumulatifs :
  • Longueur minimum : 8 caractères
  • Au moins une lettre majuscule
  • Au moins une lettre minuscule
  • Au moins un chiffre
  • Au moins un caractère spécial
Un mot de passe non conforme déclenche 400 Bad Request.
Source : PasswordService.isPasswordStrong()
🔵 R8
Hiérarchie stricte des rôles et cloisonnement des accès
Les droits d'accès sont déclarés via @RolesAllowed au niveau méthode :
  • ADMIN — toutes opérations, y compris suppression
  • MANAGER — toutes opérations sauf suppression ; virements inclus
  • TELLER — dépôts, retraits, création de compte ; pas de virement
  • CUSTOMER — consultation de ses propres comptes uniquement
Source : annotations @RolesAllowed sur AccountResource
🔵 R9
Piste d'audit exhaustive — tous les événements de sécurité sont enregistrés
L'ensemble des événements de sécurité (LOGIN, LOGOUT, ACCESS, ACCESS_DENIED, ACCOUNT_LOCKED, PASSWORD_CHANGE, REGISTRATION) est persisté en base avec les métadonnées : adresse IP, UserAgent, horodatage, résultat (SUCCESS / FAILURE / DENIED) et détails textuels.

Source : SecurityAuditService
🔵 R10
7 en-têtes de sécurité HTTP ajoutés systématiquement
Chaque réponse HTTP reçoit les en-têtes suivants, quels que soient le chemin et le résultat :
  • X-Frame-Options: DENY
  • X-Content-Type-Options: nosniff
  • X-XSS-Protection: 1; mode=block
  • Content-Security-Policy
  • Referrer-Policy: strict-origin-when-cross-origin
  • Permissions-Policy
  • Strict-Transport-Security (HSTS)
Source : SecurityHeadersFilter
🔵 R11
Comparaison de mots de passe en temps constant
La vérification du mot de passe utilise une comparaison en temps constant qui ne court-circuite pas selon la position du premier octet différent. Cette approche rend l'application résistante aux attaques par oracle temporel (timing attacks), qui exploitent les différences de latence de String.equals() pour deviner un hash caractère par caractère.

Source : PasswordService.verifyPassword()
🔵 R12
Rôle CUSTOMER attribué automatiquement à l'inscription
Lors de l'inscription via POST /api/auth/register, le rôle CUSTOMER est attribué automatiquement à tout nouvel utilisateur. L'élévation de privilèges (vers TELLER, MANAGER ou ADMIN) est une opération exclusivement réservée aux administrateurs et gestionnaires — elle ne peut pas être auto-assignée.

Source : AuthResource.register()
