Règles Métier

12 règles de validation, d'intégrité, d'audit et de gestion des erreurs. Les règles critiques déclenchent une erreur HTTP 400/404 si elles sont violées.

ℹ️
Les règles R1 à R5 sont critiques : leur violation bloque la transaction et retourne un ErrorResponse standardisé. Les règles R6 à R12 régissent le comportement, l'audit et la politique de notification.

Règles critiques — Validation

🔴 R1 CRITIQUE
Nom du client — 2 à 100 caractères, obligatoire
Le champ name du client est obligatoire (@NotNull) et doit contenir entre 2 et 100 caractères (@Size(min=2, max=100)). Une violation déclenche un ConstraintViolationException capturé par ConstraintViolationExceptionMapper → HTTP 400 avec la liste des violations dans details[].
Source : entité Client, BeanValidation, ConstraintViolationExceptionMapper.
🔴 R2 CRITIQUE
Email client — format valide et unique
Le champ email est obligatoire (@NotNull), doit respecter le format RFC 5322 (@Email) et doit être unique en base de données. Un doublon déclenche un ConstraintViolationException ou une exception de contrainte JPA → HTTP 400.
Source : @Email sur l'entité Client, contrainte UNIQUE PostgreSQL, ConstraintViolationExceptionMapper.
🔴 R3 CRITIQUE
Solde de compte — toujours ≥ 0
Le solde d'un compte ne peut jamais devenir négatif. La contrainte @DecimalMin("0.0") est appliquée à la fois au niveau de l'entité Account et de façon programmatique dans la méthode Account.withdraw(amount).
Source : @DecimalMin("0.0") sur Account.balance, méthode withdraw().
🔴 R4 CRITIQUE
Retrait — fonds suffisants obligatoires
Un retrait (WITHDRAWAL) ne peut être exécuté que si le solde du compte est supérieur ou égal au montant demandé. Si balance < amount, une IllegalArgumentException("Fonds insuffisants") est levée dans AccountService.withdraw(), interceptée par IllegalArgumentExceptionMapper → HTTP 400.
Source : AccountService.withdraw(), Account.withdraw(), IllegalArgumentExceptionMapper.
🔴 R5 CRITIQUE
Virement — les deux comptes doivent exister et les fonds être suffisants
Un virement (TRANSFER_OUT / TRANSFER_IN) requiert : (1) que le compte source et le compte destination existent en base ; (2) que le compte source ait un solde suffisant. L'absence d'un des comptes déclenche une NotFoundException → HTTP 404. Le manque de fonds déclenche IllegalArgumentException → HTTP 400.
Source : AccountService.transfer(fromId, toId, amount), NotFoundExceptionMapper, IllegalArgumentExceptionMapper.

Règles standard — Contraintes d'intégrité

🔵 R6
Numéro de compte — 5 à 34 caractères, unique
Le champ accountNumber doit contenir entre 5 et 34 caractères (@Size(min=5, max=34)) et être unique en base de données. Compatible avec les formats IBAN (max 34 caractères).
Source : @Size sur Account.accountNumber, contrainte UNIQUE PostgreSQL.
🔵 R7
Montant des opérations — strictement positif
Tout montant de dépôt, retrait ou virement doit être strictement supérieur à zéro (@DecimalMin("0.01")). Un montant à 0 ou négatif est rejeté avec HTTP 400 via la validation BeanValidation ou une vérification explicite dans le service.
Source : DTO de transaction, @DecimalMin("0.01"), ConstraintViolationExceptionMapper.

Règles standard — Audit et traçabilité

🟢 R8
Audit trail automatique — balanceBefore / balanceAfter
Chaque opération sur un compte (DEPOSIT, WITHDRAWAL, TRANSFER_OUT, TRANSFER_IN) crée automatiquement un enregistrement Transaction avec les champs balanceBefore et balanceAfter. Cet enregistrement est immuable et consultable via TransactionResource.
Source : AccountService, entité Transaction, @Entity persistée par em.persist().
🔵 R9
Notifications — politique Premium vs Standard
Les clients @Premium reçoivent une notification sur tous les canaux (email, SMS, push) pour chaque opération. Les clients @Standard ne reçoivent qu'un email, et uniquement si le montant de l'opération dépasse 1 000 €. Les qualifiers CDI (@Premium, @Standard) permettent à Liberty d'injecter la bonne implémentation de NotificationService.
Source : BankingEventObserver, qualifiers @Premium/@Standard, NotificationService.

Règles standard — Gestion des erreurs et intégrité référentielle

🔵 R10
Format d'erreur unifié — ErrorResponse
Toutes les erreurs de l'API retournent un objet JSON ErrorResponse structuré avec les champs status, error, message, timestamp et details[]. Aucun message d'erreur Java brut ne doit fuiter vers le client. Les 5 ExceptionMapper garantissent la couverture totale des exceptions.
Source : classe ErrorResponse, NotFoundExceptionMapper, ConstraintViolationExceptionMapper, GenericExceptionMapper…
🟡 R11
Suppression client — cascade sur tous les comptes associés
La suppression d'un client (DELETE /api/clients/{id}) entraîne la suppression en cascade de tous ses comptes bancaires via @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) sur l'entité Client. Les transactions associées aux comptes supprimés sont également affectées selon la stratégie de cascade JPA.
Source : @OneToMany(orphanRemoval=true) sur Client.accounts, EclipseLink.
🟢 R12
Transactions triées par date décroissante
Toutes les requêtes portant sur les transactions retournent les résultats triés par transactionDate DESC (les plus récentes en premier). Ce tri est défini dans les NamedQuery JPA de l'entité Transaction et ne dépend pas du code appelant.
Source : NamedQuery sur Transaction avec ORDER BY t.transactionDate DESC.
