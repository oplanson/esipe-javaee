Règles Métier

12 règles définissent le comportement de l'architecture Banking Microservices : 4 règles critiques de domaine, 5 règles de résilience MicroProfile Fault Tolerance, et 3 règles d'architecture.

🔴 Règles Métier Critiques

🔴 R1 — CRITIQUE  Inter-service
Un client doit exister avant la création d'un compte

Lors de la création d'un compte, le AccountService appelle ClientServiceClient pour vérifier que le client référencé (clientId) existe dans le Client Service. Cette validation inter-service garantit l'intégrité référentielle entre les deux domaines.

En cas d'indisponibilité du Client Service, le @Fallback retourne un ClientDTO fictif (name="Unknown") — le compte est tout de même créé (dégradation gracieuse acceptable). En revanche, un clientId connu comme inexistant ne peut pas être utilisé.

Source : AccountService.createAccount() + ClientServiceClient avec @CircuitBreaker + @Fallback

🔴 R2 — CRITIQUE  Domaine financier
Le solde d'un compte ne peut pas être négatif

Toutes les opérations financières (dépôt, retrait, transfert) vérifient que le solde résultant est supérieur ou égal à zéro.

  • Account.deposit(amount) — amount doit être positif
  • Account.withdraw(amount) — balance - amount >= 0 obligatoire
  • Account.transfer(amount, target) — vérification sur le compte source

Une IllegalArgumentException ou InsufficientFundsException est levée si la règle est violée.

Source : Modèle de domaine Account — méthodes deposit(), withdraw(), transfer()

🔴 R3 — CRITIQUE  Statut
Aucune opération financière sur un compte SUSPENDED ou CLOSED

Les méthodes financières du modèle de domaine Account vérifient en premier lieu le statut du compte.

  • Statut ACTIVE → toutes opérations autorisées
  • Statut SUSPENDED → dépôt, retrait, transfert bloqués
  • Statut CLOSED → toutes opérations définitivement bloquées

Un compte suspendu peut être réactivé via AccountResource POST /api/accounts/{id}/activate. Un compte fermé ne peut plus être rouvert.

Source : Guards dans Account.deposit(), Account.withdraw(), Account.transfer() — vérification this.status == ACTIVE

🔴 R4 — CRITIQUE  Clôture
Un compte ne peut être clôturé que si son solde est nul

La méthode Account.close() vérifie que balance == 0 avant d'autoriser la clôture. Si le solde est positif, une exception métier est levée.

Le client doit d'abord retirer ou transférer son solde vers un autre compte avant de pouvoir procéder à la clôture.

Endpoint : POST /api/accounts/{id}/close

Source : Account.close() — guard if (this.balance != 0) throw new AccountException("Solde doit être nul")

🛡️ Règles Fault Tolerance

⚡ R5  @CircuitBreaker
Circuit Breaker — s'ouvre après 50% d'échecs sur 4+ requêtes

Configuration appliquée sur toutes les méthodes des REST clients inter-services :

  • requestVolumeThreshold=4 — analyse sur les 4 dernières requêtes minimum
  • failureRatio=0.5 — s'ouvre si ≥ 50% d'échecs
  • delay=5000ms — circuit ouvert pendant 5 secondes
  • successThreshold=2 — referme après 2 succès consécutifs (état half-open)

Source : @CircuitBreaker sur AccountServiceClient, ClientServiceClient (Account Service et API Gateway)

🔄 R6  @Retry
Retry — 3 tentatives espacées de 1 seconde avant échec

En cas d'exception (timeout, erreur réseau, 5xx), les appels REST sont automatiquement retentés :

  • maxRetries=3 — jusqu'à 3 nouvelles tentatives (4 appels au total)
  • delay=1000ms — attente entre chaque tentative

Si toutes les tentatives échouent, le @Fallback est invoqué.

Source : @Retry(maxRetries=3, delay=1000) sur toutes les méthodes des REST clients inter-services

⏱ R7  @Timeout
Timeout — 2s (lectures Client Service), 3–5s (API Gateway)

Chaque appel REST distant dispose d'un timeout pour éviter les cascades de latence :

  • Account Service → Client Service : @Timeout(value=2000) (lectures rapides)
  • API Gateway → services : @Timeout(value=3000) à @Timeout(value=5000) selon l'opération

Un dépassement de timeout génère une TimeoutException qui déclenche la logique @Retry.

Source : @Timeout sur les méthodes de ClientServiceClient (Account Service) et AccountServiceClient / ClientServiceClient (API Gateway)

🛡️ R8  @Fallback
Fallback — toutes les méthodes REST ont une réponse de secours

Chaque méthode des REST clients dispose d'une méthode fallback dédiée qui retourne une valeur sûre :

  • getClient(id) → fallback : ClientDTO{id:id, firstName:"Unknown", lastName:"Unknown"}
  • getAccountsByClient(id) → fallback : new ArrayList<>() (liste vide)
  • Autres méthodes → valeurs nullables, objets vides ou defaults métier sûrs

Cette règle garantit que l'application ne retourne jamais d'erreur 500 non maîtrisée due à une panne inter-service.

Source : @Fallback(fallbackMethod="…") sur toutes les méthodes des REST clients

📦 R9  @Bulkhead
Bulkhead — maximum 10 appels concurrents vers BankingAggregationService

L'annotation @Bulkhead(value=10) limite le nombre de threads pouvant exécuter simultanément BankingAggregationService.getClientWithAccounts().

Au-delà de 10 appels concurrents, une BulkheadException est levée — le @Fallback est activé (retour données partielles). Cela protège le système contre les surcharges en cascade.

Source : @Bulkhead(10) sur BankingAggregationService.getClientWithAccounts()

🏛️ Règles d'Architecture

🗄️ R10  Database per Service
Chaque service possède sa propre base de données — aucun accès SQL croisé

Pattern Database per Service rigoureusement appliqué :

  • Client Service → bank_client_db (PostgreSQL port 5433)
  • Account Service → banking_account_db (PostgreSQL port 5434)
  • L'API Gateway n'a aucune base de données

Aucune requête SQL cross-service n'est autorisée. Les données partagées (ex: informations client dans Account Service) transitent exclusivement par appels REST inter-services.

Source : Décision d'architecture — configurations server.xml et persistence.xml par service

🔢 R11  Versioning API
Versionnement des APIs : /api/v1 (deprecated) et /api/v2

Les ressources REST exposent deux versions pour assurer la compatibilité ascendante :

  • /api/v1/clients, /api/v1/accounts — version dépréciée (maintenue pour compatibilité)
  • /api/v2/clients, /api/v2/accounts — version courante avec fonctionnalités complètes

Les nouveaux clients doivent utiliser les endpoints v2. Les endpoints v1 sont maintenus mais signalés comme dépréciés dans la documentation OpenAPI (@Deprecated).

Source : ClientResource et AccountResource — adaptateurs REST avec double mapping @Path

💓 R12  Health Checks
Readiness vérifie la base de données locale ET les services amont (API Gateway)

Stratégie de health check différenciée par service :

  • Client Service @Readiness : vérifie la connexion à bank_client_db (PostgreSQL :5433)
  • Account Service @Readiness : vérifie la connexion à banking_account_db (PostgreSQL :5434)
  • API Gateway ServicesHealthCheck @Readiness : appelle GET /health/ready des deux services — DOWN si l'un est indisponible

Les sondes @Liveness (ClientServiceLivenessCheck, AccountServiceLivenessCheck, GatewayLivenessCheck) vérifient uniquement l'état interne (mémoire, threads) sans dépendances externes.

Endpoints exposés : GET /health/ready et GET /health/live (MicroProfile Health 4.0)

Source : ServicesHealthCheck (API Gateway), ClientServiceHealthCheck, AccountServiceHealthCheck
