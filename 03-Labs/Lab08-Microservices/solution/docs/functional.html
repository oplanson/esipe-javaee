Architecture Fonctionnelle

Trois domaines métier indépendants, chacun encapsulé dans son propre service avec sa propre base de données. Aucun appel SQL cross-service — la communication se fait exclusivement via REST.

POST/api/accounts/{id}/suspendSuspendre un compte
POST/api/accounts/{id}/activateRéactiver un compte
POST/api/accounts/{id}/closeClôturer un compte (solde = 0)

Modèle de domaine — Account

Types de compte

  • CHECKING — Compte courant
  • SAVINGS — Compte épargne
  • BUSINESS — Compte professionnel

Cycle de vie (statut)

  • ACTIVE → SUSPENDED (suspend())
  • SUSPENDED → ACTIVE (activate())
  • ACTIVE → CLOSED si solde = 0 (close())
  • Opérations financières bloquées si SUSPENDED ou CLOSED

Validation — AccountDTO

  • @NotBlank accountName
  • @NotNull clientId, accountType
  • @DecimalMin("0.0") initialBalance
  • @Size(max=255) champs texte

Communication inter-service — ClientServiceClient

Lors de la création d'un compte, AccountService appelle ClientServiceClient pour vérifier que le client existe dans le Client Service.

@RegisterRestClient @Retry(maxRetries=3, delay=1000ms) @Timeout(value=2000ms) @CircuitBreaker(threshold=4, failure=50%, wait=5s, success=2) @Fallback → ClientDTO{name="Unknown"}

En cas d'indisponibilité du Client Service, le fallback retourne un ClientDTO avec le nom "Unknown" — le compte est tout de même créé (dégradation gracieuse).

🌐 Domaine 3 — API Gateway / BFF (port 9080)

Agrégation — BankingResource + BankingAggregationService

BankingResource.getClientWithAccounts(id) invoque BankingAggregationService qui appelle en parallèle :

  • ClientServiceClient.getClient(id) → récupère les infos client
  • AccountServiceClient.getAccountsByClient(id) → récupère la liste des comptes

Le résultat est assemblé dans un ClientWithAccountsDTO enrichi :

  • client — ClientDTO complet
  • accounts — List<AccountDTO>
  • totalBalance — somme des soldes calculée à la volée
  • accountCount — nombre de comptes
@Retry(maxRetries=2) @CircuitBreaker @Bulkhead(10) @Fallback → données partielles

Ressources Proxy

AccountProxyResource

@Path /api/accounts — redirige toutes les requêtes vers Account Service via AccountServiceClient.

Tous les endpoints CRUD + opérations financières sont proxifiés.

ClientProxyResource

@Path /api/clients — redirige toutes les requêtes vers Client Service via ClientServiceClient.

Tous les endpoints CRUD + recherche/premium sont proxifiés.

Health Checks — API Gateway

ServicesHealthCheck — @Readiness

Vérifie la disponibilité des deux services amont :

  • Appel HTTP vers http://localhost:9081/health
  • Appel HTTP vers http://localhost:9082/health
  • DOWN si l'un ou l'autre est inaccessible

GatewayLivenessCheck — @Liveness

Vérifie que la gateway est en vie (mémoire, état interne).

Indépendant de l'état des services amont.
