Règles métier

12 règles structurant le comportement de l'application bancaire EJB. Les règles critiques garantissent l'intégrité des données et la sécurité. Les règles d'avertissement signalent des contraintes importantes.

● Critique ● Avertissement ● Standard

Transactions & Intégrité

CRITIQUE R1
Transfert atomique — débit et crédit dans la même transaction CMT
Les opérations de débit (compte source) et de crédit (compte destinataire) doivent s'exécuter dans la même transaction CMT avec attribut REQUIRED. Toute exception (solde insuffisant, compte suspendu, erreur JPA) provoque un rollback automatique des deux opérations, garantissant qu'aucun fonds n'est perdu ni créé de toutes pièces.

Source : AccountServiceBean.transfer(fromId, toId, amount) — @TransactionAttribute(REQUIRED)

CRITIQUE R2
Verrouillage optimiste (@Version) — prévention des modifications concurrentes
L'entité Account possède un champ @Version int version géré automatiquement par EclipseLink. Toute modification concurrente du même compte déclenche une OptimisticLockException, qui provoque le rollback de la transaction perdante. Ce mécanisme protège contre les race conditions dans le pool de beans @Stateless.

Source : entité Account — champ @Version

R6
Lots @Stateful — chaque transfert dans sa propre transaction REQUIRES_NEW
Lors du traitement en lot via TransactionBatchBean.commitBatch(), chaque transfert est délégué à AccountServiceBean.transfer() avec l'attribut @TransactionAttribute(REQUIRES_NEW). Chaque transfert est ainsi indépendant : l'échec d'un transfert n'annule pas les précédents déjà commis.

Source : TransactionBatchBean.commitBatch()

Sécurité & Contrôle d'accès

CRITIQUE R3
Rôles d'accès — admin+teller pour les opérations, admin seul pour suppression et clôture
  • admin + teller : dépôt, retrait, transfert, création/modification client, liste clients
  • admin uniquement : suppression de client, clôture de compte (closeAccount), suspension de compte (suspendAccount), mise à jour des limites (ConfigServiceBean)
  • @PermitAll : lectures (getAccount, findClientByName) accessibles à tous les utilisateurs authentifiés
  • @DeclareRoles déclaré sur BankingServlet, BASIC auth sur /banking/*

Source : annotations @RolesAllowed sur AccountServiceBean et ClientServiceBean

Validation du solde & Plafonds

CRITIQUE R4
Solde suffisant obligatoire pour tout retrait ou transfert
Avant tout débit, la méthode Account.withdraw(amount) vérifie que balance >= amount. Si la condition n'est pas satisfaite, une InsufficientFundsException (RuntimeException) est levée, entraînant le rollback automatique de la transaction CMT englobante.

Source : Account.withdraw(BigDecimal amount)

AVERTISSEMENT R5
Plafonds par défaut configurables via ConfigServiceBean
Les plafonds suivants sont définis par défaut et chargés au démarrage par ConfigServiceBean @Startup. Ils peuvent être mis à jour dynamiquement par un administrateur sans redémarrage.
  • Retrait journalier : 5 000 € par compte
  • Montant par transfert : 10 000 €
  • Montant par transaction : 10 000 €

Source : ConfigServiceBean — méthode updateLimits(limits) protégée par @Lock(WRITE)

Configuration & Feature Flags

R7
ConfigServiceBean @Lock(READ) pour lectures concurrentes, @Lock(WRITE) pour mises à jour
Étant un @Singleton, ConfigServiceBean est accessible depuis plusieurs threads simultanément (pool de beans @Stateless). Les méthodes de lecture portent @Lock(LockType.READ) (accès concurrent autorisé), tandis que les méthodes de mise à jour portent @Lock(LockType.WRITE) (accès exclusif).

Source : ConfigServiceBean

R8
Feature flags dynamiques — transferts, lots, notifications activables/désactivables
Trois feature flags contrôlent l'activation dynamique des fonctionnalités sans redémarrage :
  • transfersEnabled — active/désactive tous les virements
  • batchEnabled — active/désactive le traitement en lot (Stateful)
  • notificationsEnabled — active/désactive l'envoi de messages JMS vers NotificationMDB
Un flag à false lève immédiatement une FeatureDisabledException.

Source : ConfigServiceBean — flags contrôlés via @Lock(WRITE)

Infrastructure — Timer & MDB

R9
Rapports planifiés non-persistants — ne survivent pas au redémarrage
Les timers déclarés avec @Schedule dans ReportGeneratorBean sont créés comme timers non-persistants (attribut persistent=false). Après un redémarrage du serveur Open Liberty, les timers ne sont pas restaurés et doivent attendre la prochaine exécution planifiée pour se déclencher. Ce comportement est intentionnel pour éviter des rapports parasites lors d'un démarrage en maintenance.

Source : ReportGeneratorBean — annotations @Schedule(persistent=false)

R10
NotificationMDB — types supportés et format pipe-delimited
Le NotificationMDB accepte les 4 types de notifications suivants via la queue jms/notificationQueue. Le format du message texte JMS est :
TYPE|DESTINATAIRE|SUJET|CORPS
  • EMAIL — envoi d'e-mail (confirmations, relevés)
  • SMS — message court (OTP, alertes urgentes)
  • PUSH — notification push mobile
  • ALERT — alerte interne sécurité, routée vers le groupe admin
Tout type inconnu est logué comme erreur et le message est acquitté (pas de requeue).

Source : NotificationMDB.onMessage(Message msg)

Cycle de vie des comptes

CRITIQUE R11
Clôture de compte — solde zéro et statut ACTIVE obligatoires
Un compte ne peut être clôturé que si les deux conditions suivantes sont simultanément vérifiées :
  • Solde exactement égal à zéro (balance.compareTo(BigDecimal.ZERO) == 0)
  • Statut du compte égal à AccountStatus.ACTIVE
Si l'une de ces conditions n'est pas remplie, une AccountCloseException est levée et la transaction est rollbackée. Un compte SUSPENDED doit d'abord être réactivé avant clôture.

Source : AccountServiceBean.closeAccount(accountId)

CRITIQUE R12
Compte SUSPENDED — aucune opération financière permise
Un compte avec le statut AccountStatus.SUSPENDED ne peut faire l'objet d'aucune opération financière : dépôt, retrait ou transfert (ni source ni destinataire). Toute tentative lève une AccountSuspendedException, provoquant le rollback de la transaction CMT. Seul un administrateur (@RolesAllowed("admin")) peut réactiver un compte suspendu.

Source : logique métier Account.checkActive() appelée avant toute opération
