Détail des Règles

⛔ R1 — Critique
Compte inactif — aucune opération financière permise
Tout compte dont le statut active = false refuse absolument toute opération financière (dépôt, retrait, clôture). La garde est vérifiée en tout premier dans Account.deposit(), Account.withdraw() et Account.close(). Une exception de domaine est levée immédiatement si le compte est inactif.
⛔ R2 — Critique
Solde insuffisant — retrait et transfert refusés
Un retrait ne peut aboutir si le solde résultant est inférieur au découvert autorisé selon le type de compte. CHECKING : solde minimum = −500€. SAVINGS : pas de découvert, solde minimum = 0€. Source : Account.withdraw(Money) combiné aux règles de AccountType.
⛔ R3 — Critique
Solde non nul — clôture de compte refusée
Un compte ne peut être clôturé que si son solde est strictement égal à zéro. La tentative de clôture d'un compte avec solde positif ou négatif lève une exception de domaine. Source : Account.close().
⛔ R4 — Critique
Devise incohérente — impossible d'opérer sur deux devises différentes
L'objet-valeur Money refuse toute opération arithmétique entre deux montants de devises différentes. La garde est vérifiée dans Money.add() et Money.subtract(). Le domaine n'effectue pas de conversion de change.
⚠ R5 — Avertissement
Frais de transfert — différenciés par statut client
Le service de domaine TransferService applique une politique de frais :
  • Client premium : frais = 0€ (transfert gratuit)
  • Client standard : frais = max(1€, min(50€, montant × 1%))
Les frais sont déduits du compte émetteur en plus du montant transféré. Le destinataire reçoit le montant exact sans frais.
ℹ R6 — Standard
Format AccountNumber — IBAN-like FR+27 chiffres
Tout numéro de compte doit respecter le format : préfixe FR suivi de 27 chiffres exactement (total 29 caractères). La méthode AccountNumber.generate() produit des numéros conformes. La méthode AccountNumber.getMasked() retourne une version masquée pour l'affichage. Source : AccountNumber value object.
ℹ R7 — Standard
Format Email — RFC 5322 simplifié, stocké en minuscules
Toute adresse email doit passer la validation RFC 5322 (simplifiée), être convertie en minuscules et ne pas dépasser 254 caractères. La méthode Email.of(String) valide et normalise l'email. getMasked() retourne la partie locale masquée. Source : Email value object.
ℹ R8 — Standard
Money immutable — toutes les opérations retournent une nouvelle instance
L'objet-valeur Money est immuable. Toute opération arithmétique (add(), subtract(), multiply()) retourne une nouvelle instance de Money. L'état du compte est mis à jour en réaffectant la référence au solde. Ce pattern garantit la thread-safety et prévient les effets de bord.
ℹ R9 — Standard
Règles différenciées par type de compte
L'enum AccountType définit deux comportements distincts :
  • CHECKING (Courant) : Pas d'intérêts. Découvert autorisé jusqu'à −500€.
  • SAVINGS (Épargne) : Intérêts quotidiens calculés sur le solde positif. Pas de découvert (solde ≥ 0€).
⚠ R10 — Avertissement
Versionnement API — V1 @Deprecated maintenu pour compatibilité
Les adaptateurs REST V1 (AccountRestAdapter, ClientRestAdapter) sont annotés @Deprecated mais restent déployés et fonctionnels pour assurer la rétrocompatibilité des clients existants. La V2 est la version courante et recommandée. Les deux versions ciblent les mêmes ports applicatifs — seul l'adaptateur change.
ℹ R11 — Standard
Événements de domaine — accumulation dans l'agrégat, publication après persistance
Les agrégats (Account, Client) accumulent leurs événements de domaine dans une liste interne durant le traitement métier. Les services applicatifs (AccountManagementService, MoneyOperationsService) publient ces événements après la persistance réussie via le port secondaire EventPublisher. Cela garantit la cohérence : on ne publie que si la transaction est commise.
ℹ R12 — Standard
Email unique — vérification d'unicité avant création et mise à jour
Avant la création d'un client (createClient) et lors d'une mise à jour d'email (updateClient), le service applicatif ClientManagementService vérifie l'unicité via ClientRepository.existsByEmail(email). Une exception métier est levée si l'email est déjà utilisé par un autre client.
