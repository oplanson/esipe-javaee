Règles de Gestion

14 règles extraites du code source, couvrant la validation des entrées, la sécurité, le routage, les patterns d'architecture et la qualité de service.

Validation des données client

R1  —  Nom obligatoire
Le nom d'un client ne peut pas être vide ou null
Lors de la création (POST action=create) ou de la mise à jour (POST action=update), si le paramètre name est null, vide ou blanc, l'opération est refusée et l'utilisateur est redirigé avec error=name_required.
Source : ClientController.createClient() / validateUpdateInput()
R2  —  Email obligatoire
L'email d'un client ne peut pas être vide ou null
Même mécanique que R1 pour le champ email. Redirection avec error=email_required. Le champ est validé par le type HTML input type="email" côté client (premier niveau), puis contrôlé côté serveur (second niveau obligatoire).
Source : ClientController.createClient() / validateUpdateInput()
R3  —  ID de client valide pour consultation / édition / suppression
Tout accès à un client individuel exige un ID numérique
Si le paramètre id est absent, vide ou non convertible en Long, la requête est rejetée avec 400 Bad Request. Si l'ID est valide mais qu'aucun client ne lui correspond, la réponse est 404 Not Found.
Source : ClientController.viewClient(), editClient(), deleteClient()
R4  —  Longueur maximale des champs
Les champs nom et email sont limités à 100 caractères
Contrainte HTML maxlength="100" appliquée dans client-form.jsp sur les deux champs. La validation est assurée côté client uniquement dans ce lab.
Source : client-form.jsp

Gestion des comptes bancaires

R5  —  Types de compte autorisés
Un compte est de type CHECKING (courant) ou SAVINGS (épargne)
La propriété type de Account est libre en Java mais la vue client-details.jsp n'affiche les labels localisés que pour CHECKING et SAVINGS. Tout autre type est affiché brut.
Source : Account.java, client-details.jsp
R6  —  Débit conditionnel
Un retrait n'est autorisé que si le solde est suffisant
La méthode Account.withdraw(amount) renvoie false sans modifier le solde si amount > balance. Elle rejette également les montants négatifs ou nuls.
Source : Account.withdraw()
R7  —  Dépôt positif uniquement
Un dépôt doit être strictement supérieur à zéro
La méthode Account.deposit(amount) ignore les montants ≤ 0 sans lever d'exception.
Source : Account.deposit()

Sécurité et contrôle d'accès

R8  —  Authentification obligatoire pour les ressources protégées
Les URLs /clients/* et /admin/* nécessitent une session authentifiée
AuthenticationFilter vérifie la présence de l'attribut user dans la session HTTP. Si absent, l'URL d'origine est sauvegardée en session (originalUrl) et l'utilisateur est redirigé vers /login.
Source : AuthenticationFilter.doFilter()
R9  —  CORS restreint aux origines autorisées
Seules les origines localhost:3000, localhost:4200, localhost:8080 sont autorisées pour les appels cross-origin
CorsFilter (pattern /api/*) compare l'en-tête Origin à une liste blanche statique. Les origines inconnues n'obtiennent pas les en-têtes CORS mais la requête n'est pas bloquée (pas de reject actif côté filtre). Les requêtes preflight OPTIONS reçoivent un 200 OK sans progression dans la chaîne.
Source : CorsFilter.doFilter()
R10  —  Suppression contrôlée par feature flag
La suppression d'un client est désactivable via configuration
Le paramètre de contexte web feature.client.deletion.enabled (défini dans web.xml) contrôle la disponibilité de l'action delete. Si false : le bouton de suppression est masqué dans la JSP et toute tentative de suppression HTTP retourne 403 Forbidden.
Source : ClientController.deleteClient(), client-list.jsp, client-details.jsp

Architecture et patterns

R11  —  Pattern PRG (Post-Redirect-Get)
Toutes les opérations d'écriture redirigent après leur exécution
Les actions create, update et delete redirigent systématiquement (302) vers une URL en GET après succès. Cela prévient la double soumission lors d'un rafraîchissement de page.
Source : ClientController.createClient(), updateClient(), deleteClient()
R12  —  Thread-safety du service
ClientService est partagé entre tous les threads de requêtes et doit être thread-safe
Une seule instance de ClientService est créée dans ClientController.init() (chargée au démarrage via loadOnStartup=1). Le stockage utilise ConcurrentHashMap et la génération d'ID utilise AtomicLong.
Source : ClientService.java

Qualité de service

R13  —  Alerte sur les requêtes lentes
Toute requête dont le traitement dépasse 1 seconde doit déclencher un avertissement
LoggingFilter mesure le temps de traitement de chaque requête. Si la durée dépasse 1000 ms, un message d'avertissement est ajouté au log de la réponse.
Source : LoggingFilter.logResponse()
R14  —  Compression automatique des réponses textuelles
Les réponses textuelles de plus de 1 Ko sont compressées en GZIP si le client le supporte
CompressionFilter capture les réponses via un HttpServletResponseWrapper. Si le client envoie Accept-Encoding: gzip et si la réponse est de type textuel (HTML, CSS, JS, JSON, XML…) et de taille supérieure à 1024 octets, le contenu est compressé GZIP avant envoi. L'en-tête Content-Encoding: gzip est positionné.
Source : CompressionFilter.doFilter()
