Règles Métier

10 règles documentées couvrant les validations métier, les contraintes transactionnelles, les stratégies de notification et les règles de cycle de vie CDI. Les règles critiques lèvent une exception en cas de violation ; les règles d'avertissement génèrent un log et une alerte sans bloquer l'opération.

Règles Métier Bancaires

R1 CRITIQUE
Dépôt uniquement pour un montant strictement positif
Tout appel à account.deposit(amount) avec un montant négatif ou nul lève une IllegalArgumentException. La transaction est annulée automatiquement (rollback CMT).

Source : Account.deposit(BigDecimal amount)  ·  Exception : IllegalArgumentException("Le montant du dépôt doit être positif")  ·  Rollback : automatique (@Transactional)
R2 CRITIQUE
Retrait uniquement si le solde est suffisant
Tout appel à account.withdraw(amount) dont le montant excède le solde disponible lève une InsufficientFundsException. Le solde ne peut pas devenir négatif.

Source : Account.withdraw(BigDecimal amount)  ·  Condition : balance < amount  ·  Exception : InsufficientFundsException  ·  Rollback : automatique (@Transactional)
R3
Virement atomique — débit et crédit dans la même transaction
AccountService.transfer(sourceId, destId, amount) exécute le retrait et le dépôt dans une transaction unique. Si l'une des deux opérations échoue, les deux sont annulées (atomicité).

Source : AccountService.transfer()  ·  Garantie : ACID via @Transactional CMT  ·  Événement : TransactionEvent.TRANSFER en cas de succès
R10
Type de compte limité à CHECKING ou SAVINGS
La propriété accountType de l'entité Account est contrainte à l'enum AccountType { CHECKING, SAVINGS }. Toute tentative de création avec un autre type est rejetée par la validation Jakarta Bean Validation.

Source : Account.accountType (@Enumerated(EnumType.STRING))  ·  Validation : @NotNull sur le champ

Règles de Notification

R4 AVERTISSEMENT
Alerte de conformité pour les transactions dépassant 10 000 €
Toute transaction d'un montant supérieur à 10 000 € déclenche une alerte de conformité via BankingEventObserver.onLargeTransaction(). Cette alerte est non-bloquante : l'opération est traitée normalement mais un WARNING est émis pour audit réglementaire.

Source : BankingEventObserver.onLargeTransaction()  ·  Seuil : amount.compareTo(BigDecimal.valueOf(10_000)) > 0  ·  Action : logger.warning("⚠ Large transaction: " + amount)
R5
Stratégie de notification différenciée par qualifier CDI
Le service de notification est résolu dynamiquement via les qualifieurs CDI selon le type du client :

Client @Premium → PremiumNotificationService : Email + SMS + Push + In-App (tous les canaux, sans seuil de montant minimum).
Client @Standard → StandardNotificationService : Email uniquement, et seulement si le montant de la transaction est supérieur à 1 000 €.

Source : PremiumNotificationService (@Premium) / StandardNotificationService (@Standard)  ·  Résolution : BankingEventObserver via qualifieurs CDI

Règles de Cycle de Vie CDI

R6
LoggingInterceptor trace toutes les méthodes annotées @Logged
L'intercepteur LoggingInterceptor est activé par l'annotation de liaison @Logged (posée sur la classe ou la méthode). Il enregistre systématiquement :
  • → Entrée : nom de méthode et arguments
  • ← Sortie : valeur retournée et durée d'exécution (ms)
  • ✗ Exception : type et message de l'exception relancée
Source : LoggingInterceptor (@AroundInvoke)  ·  Binding : @Logged (@InterceptorBinding)  ·  Activé sur : AccountService
R7
EntityManager @RequestScoped — un EM par requête HTTP
L'EntityManager est produit avec le scope @RequestScoped par EntityManagerProducer. Cela garantit qu'un EM distinct est créé pour chaque requête HTTP et détruit à sa fin, évitant tout problème de concurrence sur un EM partagé.

Source : EntityManagerProducer.createEntityManager() (@Produces @RequestScoped)  ·  Dispose : closeEntityManager(@Disposes)

Règles Transactionnelles

R8
CMT (@Transactional) — rollback automatique sur RuntimeException
Les services ClientService et AccountService sont annotés @Transactional (Container-Managed Transaction). Tout RuntimeException non attrapée déclenche un rollback automatique par le container, sans code boilerplate.

Source : Services @ApplicationScoped @Transactional  ·  Comportement : REQUIRED (par défaut — participe ou crée)  ·  Rollback sur : RuntimeException et sous-classes
R9
BMT (UserTransaction) — contrôle programmatique dans BatchTransferService
BatchTransferService utilise UserTransaction injecté pour un contrôle fin du cycle de vie transactionnel. Le timeout est configurable par lot pour éviter les verrous longue durée en base de données.

Source : BatchTransferService.processBatch()  ·  Séquence : utx.setTransactionTimeout(n) → utx.begin() → [traitement] → utx.commit() ou utx.rollback()
Avantage : Possibilité de commit/rollback partiels, timeouts différenciés par opération. Inconvénient : Code plus verbeux, gestion manuelle obligatoire des cas d'erreur.
