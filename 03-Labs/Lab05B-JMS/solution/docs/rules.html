Règles de Gestion

11 règles extraites du code source, couvrant la sécurité de désérialisation, la livraison garantie, les priorités de messages, le routage par sélecteur, l'acquittement et la concurrence des MDBs.

Sécurité des messages

R1  —  TextMessage JSON obligatoire — ObjectMessage rejeté
Seuls les TextMessage avec payload JSON sont acceptés ; les ObjectMessage sont rejetés
Tous les MDBs vérifient que le message reçu est un TextMessage. DeadLetterQueueMDB rejette explicitement les ObjectMessage dès réception pour contrer la vulnérabilité de désérialisation Java (CVE-2015-7501). Un message de type invalide est journalisé en erreur et abandonné sans persistance.
Source : Tous les MDBs + DeadLetterQueueMDB.onMessage()
R2  —  Propriété messageFormat='JSON' obligatoire
Chaque MDB vérifie la propriété messageFormat avant tout traitement
Avant de désérialiser le payload, chaque MDB appelle msg.getStringProperty("messageFormat") et vérifie que la valeur est "JSON". Si la propriété est absente ou différente, le message est rejeté sans traitement et une erreur est journalisée. Cela garantit un contrat de format explicite entre le producteur et les consommateurs.
Source : Méthodes onMessage() de tous les MDBs

Livraison et fiabilité

R3  —  Livraison PERSISTENT
Les messages sont envoyés en mode PERSISTENT — livraison garantie même après redémarrage
Le producteur configure DeliveryMode.PERSISTENT pour tous les envois. Le broker JMS (Liberty Messaging) persiste les messages sur disque avant d'accuser réception. En cas de redémarrage du serveur, les messages non encore consommés sont restaurés et redelivrés aux MDBs.
Source : TransactionEventProducer — configuration JMS deliveryMode
R4  —  Priorité différenciée par type de transaction
TRANSFER=7 (haute priorité) > WITHDRAWAL=6 > DEPOSIT=5 > default=4
TransactionEventProducer attribue une priorité JMS à chaque message selon le type de transaction. Les virements (TRANSFER) sont traités en premier par le broker car leur impact est le plus critique. Le broker respecte l'ordre de priorité lors de la distribution aux instances MDB disponibles.
Source : TransactionEventProducer.sendTransactionEvent()
R5  —  Message selector sur emailQueue
Seuls les messages portant notificationType='EMAIL' sont consommés par EmailNotificationMDB
L'annotation @ActivationConfigProperty(propertyName="messageSelector", propertyValue="notificationType='EMAIL'") configure le filtre au niveau du broker. Les messages sans cette propriété ne sont jamais livrés à ce MDB, ce qui évite des traitements inutiles et garantit l'isolation des canaux.
Source : EmailNotificationMDB — @ActivationConfigProperty
R6  —  Souscription durable sur auditTopic
Les messages du topic d'audit sont conservés si AuditLoggingMDB est temporairement indisponible
AuditLoggingMDB utilise un abonnement durable (clientId=AuditClient, subscriptionName=AuditSubscription). Contrairement à un abonnement non-durable, le broker retient les messages publiés pendant l'indisponibilité du MDB et les délivre à sa reconnexion. Aucun événement d'audit n'est perdu.
Source : AuditLoggingMDB — @ActivationConfigProperty(subscriptionDurability="Durable")
R7  —  Auto-acknowledge géré par le conteneur
L'acquittement est automatique après traitement sans exception
Le mode AUTO_ACKNOWLEDGE est configuré via @ActivationConfigProperty(propertyName="acknowledgeMode", propertyValue="Auto-acknowledge"). Le conteneur EJB acquitte automatiquement le message auprès du broker à la fin de onMessage() si aucune exception n'est levée. Si une exception est levée, le message est remis en attente pour relivraison (puis DLQ).
Source : activationConfig de chaque MDB

Résilience et erreurs

R8  —  Dead Letter Queue — capture des messages non traitables
Les messages échouant après épuisement des tentatives sont capturés et persistés
Après le nombre maximum de tentatives de relivraison configuré dans Liberty, le broker route le message vers deadLetterQueue. DeadLetterQueueMDB capture le message, crée une entité FailedMessage (payload, cause, horodatage, nombre de tentatives) et la persiste en base de données PostgreSQL pour analyse ultérieure.
Source : DeadLetterQueueMDB.onMessage()

Persistance

R9  —  Immutabilité de AuditLog.createdAt
Le champ createdAt est défini une seule fois à la création et ne peut plus être modifié
La méthode annotée @PrePersist de l'entité AuditLog initialise createdAt = LocalDateTime.now() avant le premier INSERT. L'absence de setter public sur ce champ garantit son immutabilité après persistance. Cette règle assure l'intégrité de la piste d'audit.
Source : AuditLog — méthode @PrePersist

Tests de charge

R10  —  Mode batch : 10 messages en séquence
L'endpoint /batch envoie 10 messages en séquence pour tester la charge et la concurrence des MDBs
MessagingTestServlet expose le chemin /test-messaging/batch qui déclenche une boucle d'envoi de 10 TransactionEvent vers transactionQueue. Ce mode permet de vérifier le comportement sous charge des 10 instances MDB concurrentes et d'observer l'ordonnancement par priorité.
Source : MessagingTestServlet — endpoint /batch
R11  —  Concurrence configurée par destination
Chaque destination JMS a un niveau de concurrence adapté à son volume attendu
La configuration server.xml définit maxConcurrency par MDB : transactionQueue=10 instances (volume élevé), emailQueue=5 (volume moyen), auditTopic=3 (écritures JPA), deadLetterQueue=2 (cas exceptionnels). Le pool de connexions JMS supporte jusqu'à 20 connexions simultanées (maxPoolSize=20).
Source : server.xml — maxConcurrency par MDB
