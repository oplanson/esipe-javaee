Règles de Gestion

20 règles numérotées R1–R20, extraites directement du code source. Chaque règle est tracée vers son fichier d'origine.

Standard

Règle métier ordinaire imposée par la logique domaine ou la configuration.

Critique

Règle d'intégrité des données ou de sécurité — violation entraîne exception ou refus d'opération.

Avertissement

Limitation connue, comportement déprécié ou contrainte à surveiller.

1. Validation des données

R1 Validation Client
Nom du client : obligatoire, 2 à 100 caractères
Le champ name est annoté @NotNull @Size(min=2, max=100) sur l'entité Client. Le formulaire HTML impose required maxlength="100". La méthode Client.create(name, email) normalise le nom avec name.trim() et rejette les chaînes vides avec IllegalArgumentException("Name cannot be null or empty"). La colonne DB est VARCHAR(100) NOT NULL.
R2 Validation Client
Email client : obligatoire, format valide, unique en base
Le Value Object Email valide le format avec la regex ^[A-Za-z0-9+_.-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$. L'email est normalisé en minuscules (value.trim().toLowerCase()). La colonne DB est VARCHAR(100) NOT NULL UNIQUE. Le formulaire HTML impose type="email" required maxlength="100". Un index idx_clients_email accélère les recherches.
R3 Critique
Numéro de compte : format IBAN obligatoire, unique
Le Value Object AccountNumber valide le format avec la regex ^[A-Z]{2}[0-9]{2}[A-Z0-9]{1,30}$ après normalisation toUpperCase().replaceAll("\\s", ""). La colonne DB est account_number VARCHAR(34) NOT NULL UNIQUE. La méthode AccountNumber.generate() produit automatiquement un IBAN FR76 + 23 chiffres (via UUID sans tirets). Le formulaire HTML impose maxlength="34".
R4 Validation Compte
Type de compte : CHECKING ou SAVINGS uniquement
L'enum AccountType ne contient que CHECKING et SAVINGS. La méthode AccountType.fromString() normalise en toUpperCase() avant valueOf(). La colonne DB a une contrainte CHECK (account_type IN ('CHECKING', 'SAVINGS')). Le formulaire HTML utilise un <select> avec exactement ces deux valeurs.
R5 Critique
Dépôt initial minimum de 10 EUR pour la création de compte
La factory method Account.create(client, accountType, initialDeposit) impose un dépôt minimum de Money.euros(10.0). Si initialDeposit.isLessThan(minimumDeposit) est vrai, une IllegalArgumentException("Initial deposit must be at least 10.00 EUR") est levée. Cette règle est appliquée exclusivement côté serveur dans le domaine.
R6 Critique
Solde CHECKING ≥ -500 EUR ; solde SAVINGS ≥ 0 EUR
L'enum AccountType.CHECKING définit overdraftLimit = -500.0 et SAVINGS définit overdraftLimit = 0.0. La méthode canWithdraw(balance, amount) calcule le solde résultant et le compare à getMinimumBalance(currency). En cas de violation lors d'un withdraw(), une IllegalStateException("Insufficient funds...") est levée. La migration V5 impose la même contrainte DB : CHECK ((account_type = 'CHECKING' AND balance_amount >= -500.0) OR (account_type = 'SAVINGS' AND balance_amount >= 0.0)).
R7 Critique
Montant de dépôt/retrait/virement strictement positif
Les méthodes Account.deposit(amount), Account.withdraw(amount) et Account.transferTo(toAccount, amount) appellent amount.isPositive() (compare avec BigDecimal.ZERO). Si négatif ou zéro, IllegalArgumentException est levée. L'API v1 vérifie amount <= 0 côté ressource JAX-RS. L'API v2 vérifie request.amount.compareTo(BigDecimal.ZERO) <= 0.
R8 Critique
Devise identique obligatoire pour toutes les opérations monétaires
Le Value Object Money vérifie la correspondance de devise dans add(), subtract(), isLessThan(), isGreaterThan(). Les méthodes deposit() et withdraw() de Account comparent amount.getCurrency().equals(balance.getCurrency()). En cas de mismatch, IllegalArgumentException("Currency mismatch: account uses EUR, deposit is USD"). Toutes les opérations de seed data sont en EUR.
R9 Validation Virement
Virement vers soi-même interdit
La méthode Account.transferTo(toAccount, amount) vérifie this.equals(toAccount). Si les deux comptes sont identiques (même id), IllegalArgumentException("Cannot transfer to the same account") est levée. Le TransferService.validateTransferParameters() effectue la même vérification avec fromAccount.equals(toAccount).
R10 Avertissement
Montant Money arrondi à 2 décimales (HALF_UP)
Le constructeur de Money appelle amount.setScale(2, RoundingMode.HALF_UP). Cela signifie que les montants avec plus de 2 décimales sont arrondis. Par exemple, 1.005 EUR devient 1.01 EUR. La colonne DB est DECIMAL(19,2). Ce comportement peut entraîner des écarts cumulés lors de nombreuses petites opérations.

2. Stockage des données

R11 Persistance
Persistance PostgreSQL via JPA/EclipseLink — aucun stockage en mémoire
Toutes les données sont persistées dans PostgreSQL via JPA (persistence.xml, PU bankingPU, JTA). L'EntityManager est @RequestScoped (via producer CDI). Les transactions sont déclaratives (@Transactional). La propriété JPA eclipselink.ddl-generation=none délègue le schéma entièrement à Flyway. Aucune liste statique ou cache applicatif n'est utilisé.
R12 Compatibilité
Colonne balance maintenue par trigger pour compatibilité ascendante
La migration V5 ajoute balance_amount et balance_currency (colonnes Money VO) tout en conservant l'ancienne colonne balance. Un trigger PostgreSQL trigger_sync_account_balance synchronise balance = balance_amount à chaque INSERT/UPDATE. La colonne balance est documentée comme DEPRECATED (à supprimer en V6). Cette migration est un exemple de OPTION 4 : Backward Compatible Migration.
R13 Intégrité
Suppression d'un client en cascade sur ses comptes
La relation @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) dans Client assure que la suppression d'un client supprime tous ses comptes. La FK DB est CONSTRAINT fk_accounts_client FOREIGN KEY (client_id) REFERENCES clients(id) ON DELETE CASCADE. Avant suppression, client.removeAccountFromCollection(account) est appelé pour éviter de mettre client_id = null avant le DELETE.
R14 Capacité
Nombre maximum de comptes par client : 5 (standard) ou 10 (premium)
La méthode Client.getMaxAccountsAllowed() retourne 10 si premium == true, sinon 5. La méthode Client.addAccount(account) vérifie accounts.size() >= getMaxAccountsAllowed() et lève IllegalStateException("Client has reached maximum number of accounts: N"). Client.canOpenNewAccount() expose cette règle de manière interrogative.
R15 Seed Data
Données initiales chargées par Flyway au premier démarrage
Les migrations V1 et V2 insèrent des données de démarrage : 5 clients (Jean Dupont, Marie Martin, Pierre Durand, Sophie Bernard, Luc Petit) et 6 comptes avec des soldes EUR réalistes. V4 passe les 2 premiers clients en premium. Flyway utilise baselineOnMigrate(true) pour gérer les bases existantes. Le DatabaseMigrationStartup ne lance pas d'exception si les migrations échouent (application continue).

3. Navigation et interface

R16 Critique
Pattern PRG (Post-Redirect-Get) sur toutes les actions d'écriture
Toutes les actions POST (createAccount, deleteAccount, deposit, withdraw, transfer, createClient, updateClient) se terminent par resp.sendRedirect(...) et jamais par un forward. Cela prévient la double soumission lors d'un rechargement F5. Les paramètres de confirmation sont transmis en query string (?message=account_created).
R17 Interface
Confirmation des suppressions par dialogue JavaScript
Les formulaires de suppression dans les vues JSP utilisent onsubmit="return confirm('Are you sure you want to delete this client?')" (dans client-list.jsp) et confirm('Are you sure you want to delete this account?')" (dans account-list.jsp). Cette confirmation est côté client uniquement — la vraie validation de droits est dans le serveur (deletionEnabled flag).
R18 Feature Flags
Suppression et virement conditionnés par feature flags MicroProfile Config
Les booléens feature.account.deletion.enabled (défaut true) et feature.account.transfer.enabled (défaut true) sont injectés via @Inject @ConfigProperty dans AccountController. Si deletionEnabled == false, le contrôleur retourne HTTP 403 Forbidden. De même pour transferEnabled. La propriété feature.client.deletion.enabled contrôle la suppression de clients.

4. Sécurité et session

R19 Avertissement
Cookie de session HttpOnly activé — Secure désactivé en développement
Le web.xml configure <http-only>true</http-only> (protection XSS) mais <secure>false</secure> (cookies transmissibles en HTTP). Le timeout de session est de 30 minutes. En production, secure doit être mis à true et l'accès doit se faire via HTTPS (port 9443). Aucun mécanisme d'authentification/autorisation n'est implémenté dans ce lab.
R20 Sécurité Données
Encodage HTML des sorties JSP via JSTL <c:out>
Les vues JSP qui utilisent JSTL (client-list.jsp, client-form.jsp) protègent les données utilisateurs contre le XSS via <c:out value='${client.name}'/> qui échappe les caractères HTML (<, >, &, "). Les vues en JSP scriptlet pur (account-list.jsp) affichent les données sans escaping — limitation identifiée.

5. Observabilité et opérations

R21 Logging
Intercepteur @Logged pour traçabilité automatique des méthodes de service
L'annotation @Logged applique LoggingInterceptor (priorité APPLICATION) sur toutes les méthodes annotées. L'intercepteur loggue : entrée (→ Entering: ClassName.method(params)), sortie avec durée (← Exiting: ClassName.method — Duration: Nms) et exceptions (✗ Exception in: ClassName.method). Les paramètres et résultats sont tronqués à 100 caractères. Le niveau de trace Liberty est com.bank.*=fine.
R22 Health
Health check de connectivité DB via MicroProfile Health Liveness
DatabaseHealthCheck implémente @Liveness HealthCheck. Il exécute SELECT 1 sur la DB via un EntityManagerFactory singleton local. Retourne UP {"status":"connected","type":"postgresql"} ou DOWN {"status":"disconnected"}. Accessible sur /health/live. La configuration Liberty désactive l'authentification sur /metrics (mpMetrics authentication="false") en mode dev.
R23 Événements
CDI Events pour chaque opération créatrice et transactionnelle
Trois types d'événements CDI sont émis : ClientCreatedEvent (dans ClientService.create()), AccountCreatedEvent (dans AccountService.create()), et TransactionEvent (dans AccountService.deposit(), withdraw(), transfer()). Le BankingEventObserver les observe et sélectionne le service de notification approprié (@Premium ou @Standard) selon le statut du client. Les transactions de plus de 10 000 EUR déclenchent une alerte logger.warning supplémentaire.
R24 Dépréciation
API v1 dépréciée avec sunset date 2026-06-01
Toutes les ressources JAX-RS de com.bank.api (v1) sont annotées @Deprecated(since="1.0", forRemoval=true). Chaque réponse v1 ajoute les headers HTTP : X-API-Version: 1.0, X-API-Deprecated: true, X-API-Deprecation-Info, X-API-Sunset-Date: 2026-06-01. L'API v2 (RestApplicationV2) enregistre explicitement uniquement AccountResourceV2 et ne retourne pas ces headers de dépréciation.
R25 Frais de virement
Frais de virement : 1% (min 1 EUR, max 50 EUR) pour les clients standard — gratuit premium
Le Domain Service TransferService.calculateTransferFee(amount, isPremiumClient) implémente cette règle : si isPremiumClient → Money.zero(currency) ; sinon amount.multiply(0.01), plafonné entre Money.of(1.0, currency) et Money.of(50.0, currency). La méthode transferWithFee() déduit les frais du compte source mais ne les dépose pas sur le compte destination (frais bancaires). Cette logique est dans le domaine, indépendante de l'infrastructure.
