Architecture Fonctionnelle

L'application expose deux surfaces d'interaction : une interface web JSP pour la gestion CRUD via navigateur, et une API REST duale (v1 dépréciée / v2 courante) pour l'intégration programmatique.

Carte des fonctionnalités

F1 Gestion des Clients

Créer, lire, modifier et supprimer des clients bancaires (Client aggregate root). Chaque client possède un nom, un email unique (Value Object Email), et un statut premium.

CRUD Premium/Standard CDI Events

F2 Gestion des Comptes

Créer des comptes bancaires (CHECKING / SAVINGS) associés à un client. Réaliser des dépôts, retraits et virements. Le solde est modélisé avec le Value Object Money (montant + devise EUR).

Dépôt / Retrait Virement Overdraft CHECKING

F3 API REST & Monitoring

API v1 (dépréciée) et v2 (courante) pour intégration. Health Check MicroProfile, métriques, OpenAPI/Swagger, et MicroProfile Rest Client pour les appels inter-services.

JAX-RS Health/Metrics OpenAPI

Analyse du modèle de données

Deux niveaux de représentation sont présentés : le Modèle Conceptuel de Données (MCD) — entités métier et associations indépendantes de toute technologie — et le Modèle Physique de Données (MPD) — tables PostgreSQL réelles telles qu'elles existent après les migrations Flyway V1 à V5.

MCD — Modèle Conceptuel de Données

Le domaine métier comporte deux entités principales, reliées par une association de possession (1,N). Les Value Objects DDD (Email, Money, AccountNumber, AccountType) sont des attributs composés sans identité propre.

MPD — Modèle Physique de Données (PostgreSQL après Flyway V5)

Le schéma physique reflète le refactoring DDD de la migration V5 : colonnes balance_amount/balance_currency (Money VO), account_number, account_type. La colonne balance est maintenue pour compatibilité ascendante via trigger. Les index optimisent les recherches courantes.

Comparaison MCD ↔ MPD : décisions de conception

Concept MCDRéalisation MPDDécision / Justification
Attribut email (VO Email) Colonne email VARCHAR(100) UNIQUE JPA @Embedded @AttributeOverride — le VO est aplati en une seule colonne. Unicité enforced en DB (index UNIQUE).
Attribut balance (VO Money) Deux colonnes : balance_amount DECIMAL(19,2) + balance_currency VARCHAR(3) Migration V5 : refactoring DDD — un VO Money se décompose en deux colonnes via @Embedded @AttributeOverrides. La précision DECIMAL(19,2) couvre toutes les devises ISO 4217.
Attribut accountNumber (VO AccountNumber) Colonne account_number VARCHAR(34) UNIQUE Renommé de number → account_number en V5 pour aligner sur le Ubiquitous Language DDD. Longueur 34 = max IBAN.
Attribut accountType (VO AccountType — enum) Colonne account_type VARCHAR(20) + CHECK constraint JPA @Enumerated(EnumType.STRING). Stocké en String pour lisibilité et extensibilité. Renommé de type → account_type en V5.
Association POSSÈDE (1,N) Clé étrangère client_id BIGINT NOT NULL + ON DELETE CASCADE JPA @ManyToOne(fetch=LAZY) + @OneToMany(cascade=ALL, orphanRemoval=true). La cascade DB garantit l'intégrité même en dehors de JPA.
— Colonne balance DEPRECATED Colonne héritée de V2, conservée pour compatibilité (trigger V5). Sera supprimée en migration V6. Illustre la migration incrémentale sans downtime.
— Colonne status VARCHAR(20) (V3) Ajoutée en V3 avec les valeurs ACTIVE/SUSPENDED/CLOSED. Non encore exposée dans le modèle Java — évolution future prévue.

Value Objects DDD

Money

Montant (BigDecimal, scale 2) + devise (String ISO 4217). Immuable. Opérations : add, subtract, multiply, comparaisons. Empêche les erreurs de devise différente.

AccountNumber

Numéro IBAN-like validé par regex ^[A-Z]{2}[0-9]{2}[A-Z0-9]{1,30}$. Méthode generate() produit un numéro FR76 + 23 chiffres via UUID.

Email

Adresse normalisée en minuscules, validée par regex. Méthodes utilitaires : getLocalPart(), getDomain(), getMasked().

AccountType

Enum CHECKING (découvert -500 EUR) / SAVINGS (min 0 EUR, intérêts calculés). Contient la logique métier : canWithdraw(), calculateInterest().

Acteurs

Navigateur (Client Web)

Accède à l'interface JSP via HTTP GET/POST. Les formulaires utilisent le patron PRG (Post-Redirect-Get) pour éviter les doubles soumissions. La confirmation de suppression est gérée côté client (confirm() inline dans le JSP).

Client API (Programmatique)

Consomme l'API REST v2 (/api/v2/) via JSON. Le BankingRestClient MicroProfile permet les appels inter-services typés. En-têtes de dépréciation inclus dans les réponses v1.

Serveur Open Liberty

Exécute les servlets (ClientController, AccountController), les ressources JAX-RS (ClientResource, AccountResourceV2), les services CDI et JPA EclipseLink avec PostgreSQL.

Limitation : Les règles de virement cross-devise ne sont pas implémentées — un virement entre comptes de devises différentes est rejeté (IllegalArgumentException). Toutes les données de seed sont en EUR.
