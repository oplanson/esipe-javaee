Règles Métier

Catalogue des 12 règles applicatives définissant les contraintes de validation, de transaction, de persistance et de gestion des comptes dans Banking JPA Application — Lab 03.

ℹ
Convention de priorité :   ● CRITIQUE — bloquant, lève une erreur immédiate  |  ● AVERTISSEMENT — comportement défensif  |  ● INFO — règle de conception
R1 CRITIQUE
Nom du client obligatoire
Le champ name ne peut pas être nul ni vide lors de la création ou de la mise à jour d'un client. La validation est effectuée côté serveur avant toute persistance. En cas d'échec, la requête retourne HTTP 400 Bad Request.

Source : ClientController.createClient()

R2 CRITIQUE
Email du client obligatoire
Le champ email ne peut pas être nul ni vide lors de la création ou de la mise à jour d'un client. La présence d'un email valide est une précondition à la persistance de l'entité. En cas d'échec, retourne HTTP 400 Bad Request.

Source : ClientController.validateUpdateInput()

R3 INFO
Identifiant numérique requis pour l'accès individuel
Pour tout accès à un client individuel (consultation, modification, suppression), le paramètre id doit être un entier valide. Un identifiant non numérique retourne HTTP 400. Un identifiant introuvable en base retourne HTTP 404 Not Found.

Source : ClientController — parsing du paramètre id

R4 INFO
Suppression en cascade Client → Comptes
La suppression d'un client entraîne automatiquement la suppression de tous ses comptes bancaires. Ce comportement est déclaré via orphanRemoval=true sur la relation @OneToMany côté JPA, et renforcé par la contrainte SQL ON DELETE CASCADE définie en V2 de Flyway.

Source : Client @OneToMany(cascade=CascadeType.ALL, orphanRemoval=true)

R5 AVERTISSEMENT
Montant de transaction limité à 10 000 € (configurable)
Tout montant de transaction soumis à /validate-transaction est comparé au seuil défini par l'entrée JNDI app/maxTransactionAmount (valeur par défaut : 10 000). Ce seuil est externalisé et modifiable sans recompilation.

Source : JndiConfigService, TransactionValidatorServlet

R6 CRITIQUE
Dépôt strictement positif
La méthode Account.deposit(amount) exige un montant strictement supérieur à zéro. Un montant nul ou négatif lève une IllegalArgumentException et n'est pas persisté.

Source : Account.deposit(double amount)

R7 AVERTISSEMENT
Retrait conditionné au solde suffisant
La méthode Account.withdraw(amount) vérifie que le solde courant est supérieur ou égal au montant demandé avant d'effectuer le débit. Si le solde est insuffisant, l'opération est refusée.

Source : Account.withdraw(double amount)

R8 INFO
Pattern PRG — Post/Redirect/Get
Toutes les opérations POST (création, modification, suppression) se terminent par une redirection HTTP 302 vers une ressource GET. Ce pattern évite la soumission multiple de formulaires lors du rechargement de la page par l'utilisateur.

Source : ClientController — response.sendRedirect("/clients")

R9 INFO
Gestion manuelle des transactions RESOURCE_LOCAL
L'unité de persistance bankingPU est configurée en mode RESOURCE_LOCAL. Toutes les opérations d'écriture doivent explicitement appeler em.getTransaction().begin(), commit() et, en cas d'erreur, rollback(). Il n'y a pas de transaction container-managed (CMT).

Source : ClientService — gestion begin/commit/rollback

R10 INFO
Migrations Flyway automatiques au démarrage
Le listener DatabaseMigrationStartup exécute automatiquement les migrations Flyway lors de l'initialisation du ServletContext. L'option baselineOnMigrate=true autorise la migration sur une base de données existante sans historique Flyway.

Source : DatabaseMigrationStartup (@WebListener ServletContextListener)

R11 INFO
Suppression SQL en cascade (ON DELETE CASCADE)
La contrainte SQL ON DELETE CASCADE est définie sur la clé étrangère accounts.client_id dans le script Flyway V2__create_accounts.sql. Garantit l'intégrité référentielle au niveau base de données, indépendamment du comportement JPA.

Source : migration V2__create_accounts.sql

R12 INFO
Négociation de contenu HTML / JSON
TransactionValidatorServlet inspecte l'en-tête Accept de la requête pour déterminer le format de la réponse. Si Accept: application/json, la réponse est sérialisée en JSON ({"valid": true/false, "amount": X, "max": Y}). Sinon, une page HTML est retournée.

Source : TransactionValidatorServlet — lecture de request.getHeader("Accept")
