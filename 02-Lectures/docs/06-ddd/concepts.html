Concepts clés

Comparatifs, tableaux de référence et glossaire pour Domain-Driven Design.

DDD Stratégique vs Tactique

AspectDDD StratégiqueDDD Tactique
ScopeVision globale du système, découpage en sous-domainesImplémentation interne d'un Bounded Context
PatternsBounded Context, Context Map, Ubiquitous Language, Sous-domainesEntité, Value Object, Aggregate, Repository, Domain Service, Domain Event
ObjectifIdentifier les frontières, éviter la corruption de modèle, aligner équipes et domainesConstruire un modèle de domaine riche, cohérent et expressif
OutilsEvent Storming, Domain Storytelling, Context Mapping, Core Domain ChartUML de domaine, code Java, tests unitaires de domaine
PublicArchitectes, Product Owners, Domain Experts, équipesDéveloppeurs, Tech Leads
Quand appliquerDès la phase de conception, avant de coderDurant l'implémentation de chaque contexte

Entité vs Value Object

CaractéristiqueEntitéValue Object
IdentitéIdentifiant unique et explicite (AccountId, UUID)Aucune identité — définie par ses valeurs
MutabilitéMutable — l'état évolue dans le tempsImmuable — final fields, pas de setters
ÉgalitéPar identifiant uniquementPar valeur de tous les attributs
Exemple métierAccount, Client, OrderMoney, Address, AccountNumber
Implémentation JavaClasse avec id, equals/hashCode sur id, méthodes métierClasse final ou record, equals/hashCode sur tous les champs
Durée de viePersiste dans le temps, suivi d'historiqueRemplacé, pas modifié — crée un nouveau VO
Cycle de vie DBTable dédiée, clé primaire, historisation possibleColonne(s) dans la table de l'entité (@Embedded)

Règles de Conception des Aggregates

RègleDescriptionExemple
Protéger les invariantsL'aggregate valide ses propres règles à chaque modificationAccount refuse un débit si solde insuffisant
Accès uniquement par la racineLes objets internes ne sont pas accessibles directement depuis l'extérieurPas de account.getTransactions().add(tx) — utiliser account.addTransaction(tx)
Référence par identifiantUn aggregate ne contient pas de référence directe à un autre aggregate rootClientId clientId dans Account, pas Client client
Taille réduiteUn aggregate doit rester petit — éviter les dépendances excessivesAccount contient des Transaction récentes seulement
Une transaction par aggregateUne transaction DB ne modifie qu'un seul aggregate à la foisTransfert entre comptes via Domain Events, pas en une seule transaction
Cohérence éventuelleLa cohérence entre aggregates est assurée de manière asynchrone via événementsTransferCompletedEvent déclenche la mise à jour du compte destinataire

Relations entre Bounded Contexts

PatternDescriptionCas d'usage
Anti-Corruption Layer (ACL)Couche de traduction protégeant le modèle local des concepts étrangersIntégration avec un système legacy, API tierce ou contexte aux conventions différentes
Shared KernelSous-ensemble de modèle partagé entre deux équipes avec coordination forteDeux équipes proches partageant quelques Value Objects communs (Money, Currency)
PartnershipDeux équipes évoluent en synchronisant leur planning mutuellementContexts fortement couplés, co-déployés, développés par des équipes très proches
Customer/SupplierUne équipe fournit une interface, l'autre la consommeRelation amont/aval avec un contrat établi et des tests d'acceptation
ConformistL'équipe aval adopte le modèle de l'équipe amont sans adapterIntégration avec un système dominant dont on ne peut pas influencer le modèle
Published LanguageLangage d'échange formalisé et documenté (OpenAPI, JSON Schema, Protobuf)Communication entre microservices via des contrats publics versionnés
Open Host ServiceService accessible via un protocole bien défini et documentéAPI publique REST consommée par de nombreux contextes différents

Modèle Anémique vs Modèle Riche

AspectModèle Anémique (anti-pattern)Modèle Riche (DDD)
StructureObjets = données uniquement (getters/setters)Objets = données + comportements métier
Logique métierÉparpillée dans des services transaction-scriptEncapsulée dans les entités et aggregates
InvariantsVérifiés dans le service — peuvent être oubliésGarantis par l'aggregate — impossible de créer un état invalide
TestabilitéTests d'intégration lourds — logique liée aux servicesTests unitaires légers — logique dans les entités POJO
Lisibilitéaccount.setBalance(account.getBalance().subtract(amount))account.debitAccount(amount)
Exemple d'accèsaccount.getTransactions().add(new Transaction(...))account.addTransaction(amount, description)
RisqueRègles métier violées facilement par inadvertanceRègles garanties par le code — encapsulation forte

Glossaire

TermeDéfinition
DDDDomain-Driven Design — approche de conception logicielle plaçant le domaine métier au centre, avec collaboration dev/expert et langage partagé (Eric Evans, 2003)
Bounded ContextFrontière explicite à l'intérieur de laquelle un modèle de domaine cohérent s'applique, avec son propre langage ubiquitaire
AggregateCluster d'objets de domaine traité comme une unité, avec une racine (Aggregate Root) qui garantit les invariants et contrôle l'accès
EntityObjet de domaine avec une identité unique persistant dans le temps, dont l'égalité est basée sur l'identifiant
Value ObjectObjet de domaine immuable sans identité propre, dont l'égalité est basée sur la valeur de tous ses attributs
RepositoryAbstraction simulant une collection d'aggregates, avec interface dans le domaine et implémentation dans l'infrastructure
Domain ServiceService stateless encapsulant une logique métier qui n'appartient naturellement à aucune Entité ou Value Object
Ubiquitous LanguageVocabulaire commun partagé par tous les membres de l'équipe (dev + experts métier), utilisé dans les conversations et dans le code
Domain EventFait métier immuable passé, nommé au passé (AccountDebited), utilisé pour découpler les aggregates et assurer la cohérence éventuelle
Anti-Corruption LayerCouche de traduction entre deux Bounded Contexts, protégeant le modèle local de la contamination par les concepts d'un système externe
