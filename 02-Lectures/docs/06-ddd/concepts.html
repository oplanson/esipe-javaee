Key Concepts

Comparisons, reference tables and glossary for Domain-Driven Design.

Strategic vs Tactical DDD

AspectStrategic DDDTactical DDD
ScopeOverall system vision, decomposition into sub-domainsInternal implementation of a Bounded Context
PatternsBounded Context, Context Map, Ubiquitous Language, Sub-domainsEntity, Value Object, Aggregate, Repository, Domain Service, Domain Event
ObjectiveIdentify boundaries, avoid model corruption, align teams and domainsBuild a rich, coherent and expressive domain model
ToolsEvent Storming, Domain Storytelling, Context Mapping, Core Domain ChartDomain UML, Java code, domain unit tests
AudienceArchitects, Product Owners, Domain Experts, teamsDevelopers, Tech Leads
When to applyFrom the design phase, before codingDuring the implementation of each context

Entity vs Value Object

CharacteristicEntityValue Object
IdentityUnique and explicit identifier (AccountId, UUID)No identity — defined by its values
MutabilityMutable — state evolves over timeImmutable — final fields, no setters
EqualityBy identifier onlyBy value of all attributes
Business exampleAccount, Client, OrderMoney, Address, AccountNumber
Java implementationClass with id, equals/hashCode on id, business methodsfinal class or record, equals/hashCode on all fields
LifecyclePersists over time, history trackingReplaced, not modified — creates a new VO
DB lifecycleDedicated table, primary key, possible historisationColumn(s) in the entity's table (@Embedded)

Aggregate Design Rules

RuleDescriptionExample
Protect invariantsThe aggregate validates its own rules at each modificationAccount refuses a debit if the balance is insufficient
Access only through the rootInternal objects are not directly accessible from outsideNo account.getTransactions().add(tx) — use account.addTransaction(tx)
Reference by identifierAn aggregate does not contain a direct reference to another aggregate rootClientId clientId in Account, not Client client
Small sizeAn aggregate must stay small — avoid excessive dependenciesAccount contains only recent Transaction objects
One transaction per aggregateA DB transaction modifies only one aggregate at a timeTransfer between accounts via Domain Events, not in a single transaction
Eventual consistencyConsistency between aggregates is ensured asynchronously via eventsTransferCompletedEvent triggers the update of the target account

Relations between Bounded Contexts

PatternDescriptionUse case
Anti-Corruption Layer (ACL)Translation layer protecting the local model from foreign conceptsIntegration with a legacy system, third-party API or context with different conventions
Shared KernelSubset of model shared between two teams with strong coordinationTwo close teams sharing some common Value Objects (Money, Currency)
PartnershipTwo teams evolve by synchronising their planning mutuallyTightly coupled contexts, co-deployed, developed by very close teams
Customer/SupplierOne team provides an interface, the other consumes itUpstream/downstream relationship with an established contract and acceptance tests
ConformistThe downstream team adopts the upstream team's model without adaptingIntegration with a dominant system whose model cannot be influenced
Published LanguageFormalised and documented exchange language (OpenAPI, JSON Schema, Protobuf)Communication between microservices via versioned public contracts
Open Host ServiceService accessible via a well-defined and documented protocolREST public API consumed by many different contexts

Anemic Model vs Rich Model

AspectAnemic Model (anti-pattern)Rich Model (DDD)
StructureObjects = data only (getters/setters)Objects = data + business behaviours
Business logicScattered across transaction-script servicesEncapsulated in entities and aggregates
InvariantsChecked in the service — can be forgottenGuaranteed by the aggregate — impossible to create an invalid state
TestabilityHeavy integration tests — logic tied to servicesLightweight unit tests — logic in POJO entities
Readabilityaccount.setBalance(account.getBalance().subtract(amount))account.debitAccount(amount)
Access exampleaccount.getTransactions().add(new Transaction(...))account.addTransaction(amount, description)
RiskBusiness rules easily violated inadvertentlyRules guaranteed by code — strong encapsulation

Glossary

TermDefinition
DDDDomain-Driven Design — software design approach placing the business domain at the centre, with dev/expert collaboration and shared language (Eric Evans, 2003)
Bounded ContextExplicit boundary inside which a coherent domain model applies, with its own ubiquitous language
AggregateCluster of domain objects treated as a unit, with a root (Aggregate Root) that guarantees invariants and controls access
EntityDomain object with a unique identity persisting over time, whose equality is based on the identifier
Value ObjectImmutable domain object without its own identity, whose equality is based on the value of all its attributes
RepositoryAbstraction simulating a collection of aggregates, with interface in the domain and implementation in the infrastructure
Domain ServiceStateless service encapsulating business logic that does not naturally belong to any Entity or Value Object
Ubiquitous LanguageCommon vocabulary shared by all team members (dev + domain experts), used in conversations and in code
Domain EventImmutable past business fact, named in the past tense (AccountDebited), used to decouple aggregates and ensure eventual consistency
Anti-Corruption LayerTranslation layer between two Bounded Contexts, protecting the local model from contamination by concepts of an external system
