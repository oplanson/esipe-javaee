🧭 Qu'est-ce que le DDD ?

Philosophie — le code doit refléter le métier

Le Domain-Driven Design (DDD), introduit par Eric Evans en 2003, place le domaine métier au cœur de la conception logicielle. Le code ne doit pas être une simple traduction technique de besoins — il doit parler le même langage que les experts métier.

  • Le modèle de domaine est la représentation vivante du métier dans le code
  • La complexité accidentelle (infrastructure, frameworks) est séparée de la complexité essentielle (règles métier)
  • Le code exprime clairement les invariants, contraintes et comportements du domaine
  • Tout changement de règle métier se traduit directement par un changement dans le modèle

Collaboration dev/expert métier

  • DDD exige une collaboration continue entre développeurs et experts du domaine
  • Les experts métier apportent la connaissance des règles, des cas limites et des priorités
  • Les développeurs structurent cette connaissance dans un modèle logiciel cohérent
  • Des sessions de Event Storming ou de Domain Storytelling facilitent cette collaboration

Langage ubiquitaire partagé

Le Ubiquitous Language (langage ubiquitaire) est un vocabulaire commun utilisé par tous les membres de l'équipe — développeurs ET experts métier — dans les conversations, la documentation ET le code.

  • Les noms de classes, méthodes et variables reflètent les termes métier (ex. Account, debitAccount())
  • Éliminer les termes ambigus et les doubles définitions
  • Évolue avec la compréhension du domaine

DDD stratégique vs tactique

  • DDD Stratégique — décomposer le problème en sous-domaines et Bounded Contexts, cartographier leurs relations (Context Map)
  • DDD Tactique — implémenter chaque Bounded Context avec les building blocks (Entités, Value Objects, Aggregats, Repositories, Domain Services, Domain Events)
🗺️ Pattern Stratégique — Bounded Context

Sous-domaine avec son propre modèle et langage

Un Bounded Context est une frontière explicite à l'intérieur de laquelle un modèle de domaine particulier s'applique. Au sein de cette frontière, chaque terme du langage ubiquitaire a une définition précise et unique.

  • Le même mot peut avoir des significations différentes dans deux Bounded Contexts (ex. Client dans le contexte Compte vs. Marketing)
  • Chaque Bounded Context a son propre modèle objet, sa propre base de données, ses propres équipes
  • Les frontières évitent la corruption du modèle par des concepts appartenant à d'autres contextes

Context Map — relations entre contexts

La Context Map est un diagramme qui documente les relations entre les différents Bounded Contexts d'un système.

  • Visualise les dépendances, les flux de données et les points d'intégration
  • Révèle les relations de pouvoir et de priorité entre équipes
  • Guide les décisions d'architecture sur la communication inter-contextes

Patterns d'intégration entre contextes

  • ACL (Anti-Corruption Layer) — couche de traduction qui protège le modèle local des concepts étrangers, évite la contamination du modèle cible
  • Shared Kernel — sous-ensemble de modèle partagé entre deux équipes, nécessite une coordination forte pour évoluer
  • Partnership — deux équipes évoluent ensemble en synchronisant leur planning, pour des contexts fortement couplés
  • Customer/Supplier — une équipe fournit un service, l'autre le consomme
  • Conformist — l'équipe aval adopte le modèle de l'équipe amont sans adapter
  • Published Language — langage d'échange formalisé (ex. JSON Schema, OpenAPI)
🧱 Patterns Tactiques — Entité et Value Object

Entity — identité unique, mutabilité

Une Entité est un objet de domaine qui possède une identité unique persistant dans le temps, même si ses attributs changent.

  • L'identité est représentée par un identifiant explicite (AccountId, ClientId)
  • Deux entités sont égales si et seulement si leurs identifiants sont égaux (equals/hashCode basé sur l'id)
  • Une entité peut être mutable — son état change au fil du temps (solde d'un compte, statut)
  • Elle encapsule ses invariants métier — les règles qui doivent toujours être respectées
  • Exemples : Account, Client, Order, Employee

Value Object — pas d'identité, immuabilité, égalité par valeur

Un Value Object est un objet de domaine qui représente un concept sans identité propre — sa valeur est son identité.

  • Pas d'identifiant — deux Value Objects avec les mêmes attributs sont équivalents
  • Immuabilité — un Value Object ne change jamais après sa création (utiliser final)
  • Égalité par valeur — equals/hashCode basés sur tous les attributs
  • Remplaçable — on ne modifie pas un VO, on en crée un nouveau
  • Exemples : Money, AccountNumber, Address, DateRange, Email

Comparaison Entité vs Value Object

  • Entité : Qui est-il ? — son identité compte
  • Value Object : Qu'est-ce que c'est ? — sa valeur compte
  • Règle : si vous pouvez remplacer un objet par un autre ayant les mêmes attributs sans impact métier → c'est un Value Object
🔒 Pattern Tactique — Aggregate

Racine d'agrégat et invariants métier

Un Aggregate est un cluster d'objets de domaine (Entités + Value Objects) traité comme une unité cohérente. L'Aggregate Root (racine) est l'unique point d'entrée pour toute modification.

  • Les invariants métier sont garantis à l'intérieur des frontières de l'aggregate
  • Toute modification passe obligatoirement par la racine — jamais directement sur les objets internes
  • L'aggregate est chargé et sauvegardé comme une seule unité transactionnelle

Référence par ID à d'autres agrégats

  • Un aggregate ne doit jamais contenir de référence directe à un autre aggregate root
  • On référence un autre aggregate par son identifiant uniquement (ClientId clientId, pas Client client)
  • Cela maintient des frontières transactionnelles claires et évite les couplages implicites

Règles de conception des Aggregates

  • ✅ Protéger les invariants métier — l'aggregate valide ses propres règles
  • ✅ Taille réduite — un aggregate doit rester petit (éviter les god objects)
  • ✅ Cohérence transactionnelle — une transaction = un aggregate modifié
  • ✅ Modifier un seul aggregate par transaction — coordonner plusieurs aggregates via Domain Events

Aggregate bancaire Account/Transaction

Dans l'application bancaire, Account est l'aggregate root qui contient une liste de Transaction. Toute opération de crédit ou débit passe par Account, qui vérifie les invariants (solde positif, limite de transaction, statut actif).

🗄️ Repository Pattern

Abstraction d'accès aux données

Le Repository est une abstraction qui simule une collection d'objets en mémoire pour les aggregates. Il sépare la logique métier des détails d'accès aux données.

  • Le domaine ne connaît que l'interface du repository — jamais l'implémentation concrète
  • Le repository masque la complexité de la persistance (JPA, NoSQL, API externe)
  • Facilite les tests unitaires — on peut substituer une implémentation en mémoire

Interface dans le domaine

  • L'interface est définie dans la couche domaine (domain.port ou domain.repository)
  • Elle parle le langage du domaine : findById(AccountId), findByClient(ClientId), save(Account)
  • Un repository existe par aggregate root — pas un repository générique pour toutes les entités

Implémentation dans l'infrastructure

  • L'implémentation concrète (JpaAccountRepository) vit dans la couche infrastructure
  • Elle utilise JPA, JDBC, MongoDB ou tout autre mécanisme de persistance
  • Injectée via CDI — le domaine ne voit jamais l'implémentation concrète

Patron de collection d'objets

  • Le repository se comporte comme un Set ou une Collection d'aggregates
  • Méthodes typiques : findById, findAll, save (add/update), delete
  • Pas de méthodes de requête complexe dans l'interface — utiliser des Specifications ou des Query Objects si nécessaire
⚡ Domain Services et Domain Events

Service de domaine pour opérations sans entité naturelle

Un Domain Service encapsule une logique métier qui n'appartient naturellement à aucune Entité ou Value Object — par exemple une opération impliquant plusieurs aggregates.

  • Un service de domaine est stateless — il ne conserve pas d'état entre les appels
  • Exemple : un transfert d'argent implique deux comptes — ni AccountA ni AccountB n'est responsable de l'opération complète
  • Nommé selon le verbe métier : MoneyTransferService, FraudDetectionService
  • À distinguer des Services Applicatifs (orchestration) et des Services Techniques (infrastructure)

Domain Event — fait métier passé

Un Domain Event représente quelque chose d'important qui s'est produit dans le domaine — c'est un fait passé, immuable, nommé au passé : TransferCompleted, AccountOpened, PaymentFailed.

  • Les Domain Events découplent les aggregates — un aggregate publie un événement, d'autres réagissent
  • Permettent la cohérence éventuelle entre aggregates sans transaction distribuée
  • Immuables — contiennent toutes les informations nécessaires à la réaction

Publication et observation avec CDI (@ApplicationScoped)

  • Jakarta CDI Events (Event<T>) sont le mécanisme naturel en Jakarta EE
  • Le publisher injecte Event<TransferCompletedEvent> et appelle fire()
  • Les observateurs utilisent @Observes pour réagir de manière déclarée
  • Pattern adapté pour les événements synchrones intra-JVM
🏗️ Architecture en Couches DDD

Les 4 couches de l'architecture DDD

  • Domain — le cœur : Entités, Value Objects, Aggregates, Domain Services, Interfaces de Repository, Domain Events. Aucune dépendance vers l'extérieur.
  • Application — orchestre les cas d'usage : Application Services, Command Handlers, DTOs. Coordonne les aggregates et appelle les Domain Services.
  • Infrastructure — implémentations concrètes : JPA Repositories, Message Brokers, clients HTTP, adaptateurs techniques.
  • Presentation — points d'entrée : JAX-RS resources, JSF controllers, CLI. Traduit les requêtes en commandes applicatives.

Structure de packages recommandée

  • com.esipe.bank.domain — entités, VOs, aggregates, interfaces
  • com.esipe.bank.domain.event — domain events
  • com.esipe.bank.application — application services, use cases
  • com.esipe.bank.infrastructure.jpa — repositories JPA
  • com.esipe.bank.presentation.rest — JAX-RS resources

Dépendances vers l'intérieur (Dependency Rule)

  • Le domaine ne dépend de rien — ni de Jakarta EE, ni de JPA, ni d'aucun framework
  • L'application dépend du domaine
  • L'infrastructure dépend du domaine et de l'application (implémente les interfaces)
  • La présentation dépend de l'application
  • L'inversion de dépendances (DIP) permet à l'infrastructure d'implémenter les interfaces du domaine
🔄 Refactorisation vers DDD — Application Bancaire

Modèle anémique vs modèle riche

Le Modèle Anémique (anti-pattern) est un objet qui ne contient que des getters/setters sans logique métier — la logique est éparpillée dans des services. Le Modèle Riche encapsule la logique dans les entités elles-mêmes.

  • Anémique : account.setBalance(newBalance) — aucune règle vérifiée
  • Riche : account.debitAccount(amount) — vérifie solde, statut, invariants

Avant refactoring — code procédural

  • Classe Account avec uniquement des champs et des getters/setters
  • Service BankingService contenant toute la logique de débit, crédit, validation
  • Duplication de règles métier à travers plusieurs services
  • Règles métier invisibles — pas de méthode exprimant l'intention

Après refactoring — modèle riche DDD

  • AccountId — Value Object pour l'identité
  • Money — Value Object immuable avec opérations arithmétiques
  • AccountNumber — Value Object avec validation et génération
  • Account — Entity/Aggregate Root avec méthodes métier (debitAccount, creditAccount)
  • Règles métier centralisées dans l'aggregate — impossibilité de créer un état invalide

Value Objects Money et AccountNumber refactorisés

  • Money remplace BigDecimal nu — ajoute la devise, les opérations typées et les validations
  • AccountNumber remplace String nu — format validé, génération centralisée
  • Impossible de confondre un montant avec un numéro de compte dans le code — type safety maximale
