💉 Qu'est-ce que l'Injection de Dépendances ?

Le problème sans DI — l'opérateur new

Sans injection de dépendances, les classes créent elles-mêmes leurs dépendances avec new, engendrant un couplage fort difficile à tester et à maintenir.

  • Couplage fort — la classe connaît l'implémentation concrète de chaque dépendance
  • Testabilité nulle — impossible de substituer une fausse implémentation (mock)
  • Violation du SRP — la classe gère à la fois sa logique et la création de ses dépendances
  • Rigidité — changer d'implémentation exige de modifier chaque classe consommatrice

La solution CDI

CDI (Contexts and Dependency Injection) délègue la création et la gestion des objets au conteneur Jakarta EE. Les dépendances sont injectées automatiquement.

  • Le conteneur instancie, configure et injecte chaque bean
  • Le cycle de vie est géré selon le scope déclaré
  • L'injection se fait par type — type-safe et vérifié à la compilation

Bénéfices

  • ✅ Testabilité — injection de mocks dans les tests unitaires
  • ✅ Couplage faible — les classes dépendent d'interfaces, pas d'implémentations
  • ✅ Maintenabilité — changement d'implémentation sans modifier les consommateurs
  • ✅ Réutilisabilité — beans partagés et réutilisés à travers l'application
🔄 Scopes CDI

Le scope détermine la durée de vie et la portée d'un bean CDI. Choisir le bon scope est essentiel pour la cohérence et les performances.

@ApplicationScoped

  • Une seule instance partagée par toute l'application (équivalent singleton)
  • Créée au premier accès, détruite à l'arrêt de l'application
  • Idéal pour : services stateless, caches, configurations globales

@RequestScoped

  • Une nouvelle instance par requête HTTP
  • Créée au début de la requête, détruite à la fin
  • Idéal pour : traitement de données de formulaire, opérations unitaires

@SessionScoped

  • Une instance par session utilisateur (doit implémenter Serializable)
  • Partagée pendant toute la durée de la session HTTP
  • Idéal pour : panier d'achat, préférences utilisateur, état de connexion

@Dependent

  • Instance liée au cycle de vie du bean injecteur (pseudo-scope)
  • Scope par défaut si aucun scope n'est déclaré
  • Idéal pour : value objects, helpers, beans légers

Callbacks de cycle de vie

  • @PostConstruct — appelé après l'injection, avant la première utilisation
  • @PreDestroy — appelé avant la destruction du bean, pour libérer les ressources
💡 Injection avec @Inject

Field Injection

L'annotation @Inject est placée directement sur le champ. Simple mais déconseillé pour la testabilité.

Constructor Injection (préféré)

Les dépendances sont déclarées comme paramètres du constructeur. Méthode recommandée car :

  • Rend les dépendances explicites et obligatoires
  • Facilite les tests unitaires sans conteneur
  • Permet les champs final (immutabilité)
  • Détecte les cycles de dépendances à la compilation

Method Injection

L'injection se fait via une méthode setter annotée @Inject. Utile pour les dépendances optionnelles.

🏷️ Qualificateurs CDI

Lorsque plusieurs implémentations d'une interface coexistent, CDI ne sait pas laquelle injecter. Les qualificateurs résolvent cette ambiguïté.

Annotation @Qualifier personnalisée

  • Créer une annotation méta-annotée @Qualifier, @Retention(RUNTIME), @Target({METHOD, FIELD, PARAMETER, TYPE})
  • Appliquer sur l'implémentation et sur le point d'injection

Résolution d'ambiguïté

  • CDI résout l'injection par type + qualificateurs
  • Sans qualificateur, @Default est implicitement appliqué
  • Plusieurs qualificateurs peuvent être combinés sur un même point d'injection

@Alternative pour les implémentations switchables

  • @Alternative marque une implémentation inactive par défaut
  • Activée dans beans.xml ou via @Priority globalement
  • Idéal pour les implémentations de test, de stub ou par environnement
🏭 Producer Methods

Les Producer Methods permettent de créer des beans CDI dont la création nécessite une logique particulière — par exemple un EntityManager ou un objet configuré depuis un fichier externe.

@Produces

  • Méthode annotée @Produces — le type de retour devient un bean CDI injectable
  • Peut porter un scope (@ApplicationScoped, @RequestScoped…)
  • Peut accepter des paramètres injectés par CDI

Producers avec configuration

  • Permet d'initialiser des ressources tierces (DataSource, Logger, configuration externe)
  • La logique de construction est centralisée dans une seule méthode

Producers avec qualificateurs

  • Un producer peut porter un qualificateur pour distinguer plusieurs instances du même type

@Disposer pour le cleanup

  • Méthode annotée @Disposes appelée automatiquement lors de la destruction du bean produit
  • Permet de fermer proprement les connexions, flux ou ressources
🔍 Intercepteurs

Les intercepteurs CDI permettent d'ajouter un comportement transversal (cross-cutting concerns) sans modifier le code métier.

@InterceptorBinding

  • Annotation personnalisée méta-annotée @InterceptorBinding, @Retention(RUNTIME), @Target({METHOD, TYPE})
  • Appliquée sur la méthode ou la classe à intercepter

Implémentation @Interceptor

  • Classe annotée @Interceptor + l'annotation de binding
  • Activé dans beans.xml ou via @Priority

@AroundInvoke

  • Méthode d'interception appelée autour de l'invocation
  • Reçoit un InvocationContext — peut lire/modifier les paramètres, le résultat
  • Doit appeler context.proceed() pour continuer l'invocation

Exemples d'utilisation

  • ✅ Logging — journaliser l'entrée/sortie de chaque méthode
  • ✅ Performance — mesurer le temps d'exécution
  • ✅ Sécurité — vérifier les autorisations avant l'exécution
  • ✅ Cache — court-circuiter l'appel si le résultat est en cache
💳 Transactions @Transactional

@Transactional (CDI / Jakarta Transactions) permet une gestion déclarative des transactions sans code de gestion explicite.

Types de propagation

  • REQUIRED (défaut) — utilise la transaction existante ou en crée une nouvelle
  • REQUIRES_NEW — suspend la transaction courante et crée une nouvelle transaction indépendante
  • MANDATORY — exige qu'une transaction active existe (exception sinon)
  • SUPPORTS — utilise la transaction courante si elle existe, sinon s'exécute sans
  • NOT_SUPPORTED — suspend toute transaction active, s'exécute toujours sans transaction
  • NEVER — lève une exception si une transaction est active

Stratégies de rollback

  • Rollback automatique sur RuntimeException et Error
  • rollbackOn — spécifier des exceptions supplémentaires déclenchant le rollback
  • dontRollbackOn — exceptions à ne pas considérer pour le rollback
  • Rollback programmatique : context.setRollbackOnly()
📡 CDI Events

Le système d'événements CDI implémente le pattern Observer de façon type-safe et sans couplage direct entre producteur et consommateur.

@Observes

  • Méthode observatrice annotée @Observes sur le paramètre de l'événement
  • Appelée automatiquement par CDI lors du déclenchement de l'événement
  • Peut avoir une priorité avec @Priority

@Inject Event<T>

  • Injecter Event<MonEvent> pour déclencher un événement
  • event.fire(payload) — déclenchement synchrone
  • event.fireAsync(payload) — déclenchement asynchrone (retourne un CompletionStage)

Événements synchrones et asynchrones

  • Synchrone — tous les observateurs s'exécutent dans le même thread, avant le retour de fire()
  • Asynchrone — les observateurs s'exécutent dans un thread séparé, non bloquant

Qualificateurs d'événements

  • Les qualificateurs filtrent les observateurs — un observateur ne reçoit que les événements correspondant à ses qualificateurs
  • event.select(new AnnotationLiteral<MonQualificateur>(){}).fire(payload)
