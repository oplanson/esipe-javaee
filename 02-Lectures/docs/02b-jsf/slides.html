🏗️ JSF Architecture and Lifecycle

JSF (JavaServer Faces) is a component-oriented MVC framework for building web user interfaces in Java EE/Jakarta EE.

The 6 phases of the JSF lifecycle:

  1. Restore View — rebuilds or creates the component tree (UIViewRoot) for the current request
  2. Apply Request Values — each component extracts and stores its value from the request parameters
  3. Process Validations — validators and converters run on submitted values; errors are recorded
  4. Update Model Values — validated values are pushed to Managed Bean properties via ValueExpressions
  5. Invoke Application — action listeners and action methods (e.g. commandButton) are invoked
  6. Render Response — the view is rendered (HTML generated) and sent to the browser

Short-circuit: if validation errors occur in phase 3, the cycle jumps directly to phase 6 (Render Response) to display error messages.

🫘 Managed Beans with CDI

In modern JSF (Jakarta EE 9+), Managed Beans are CDI beans annotated with @Named to make them accessible from Expression Language.

CDI bean scopes:

  • @RequestScoped — bean created for each HTTP request, destroyed at request end. Ideal for one-off actions.
  • @ViewScoped (jakarta.faces.view.ViewScoped) — bean alive as long as the user stays on the same JSF view. Perfect for forms with AJAX.
  • @SessionScoped — bean tied to the user's HTTP session. For data persisting across pages (e.g. cart, logged-in user).
  • @ApplicationScoped — single instance shared across the whole application. For caches and global data.
  • @Dependent (CDI default) — the bean has the same scope as the bean that injects it.

@Named annotation:

@Named("clientBean") exposes the bean under the name clientBean in EL. Without a value, the name is derived from the class (e.g. ClientBean → clientBean).

java 
@Named
@RequestScoped
public class ClientBean {
    @Inject
    private ClientService clientService;
    // accessible via #{clientBean.name}
}
📄 Facelets and Templates

Facelets is the official JSF templating engine since JSF 2.0, definitively replacing JSP. Facelets files have the .xhtml extension.

Advantages of Facelets over JSP:

  • Strict XML syntax — pages are valid HTML5 viewable directly in a browser
  • Template inheritance via ui:composition, ui:define, ui:insert
  • Better integration with Expression Language (EL)
  • No separate compilation needed

Main templating tags:

  • ui:composition template="..." — declares that a page uses a template and delimits the content to include
  • ui:define name="..." — in a client page, defines the content for a template zone
  • ui:insert name="..." — in the template, marks the location where a page's content will be inserted
  • ui:include src="..." — includes a reusable Facelets fragment
  • ui:repeat — iterates over a collection (alternative to h:dataTable)
🧩 JSF Core Components

JSF provides a rich library of UI components split across two main namespaces: h: (HTML) and f: (Core).

Input and output components:

  • h:inputText — text input field, bound to a property via value="#{bean.prop}"
  • h:inputSecret — password field
  • h:inputTextarea — multi-line text area
  • h:outputLabel — label linked to a component via for="componentId"
  • h:outputText — displays a value with automatic HTML encoding
  • h:message — displays error messages for a component identified by for
  • h:messages — displays all JSF messages on the page

Action and navigation components:

  • h:commandButton — form submit button, triggers an action or action listener
  • h:commandLink — hyperlink triggering an action
  • h:form — HTML form, required for any interactive JSF component

List components:

  • h:dataTable — HTML table generated dynamically from a collection
  • h:selectOneMenu — single-selection dropdown list
  • h:selectManyCheckbox — multiple-selection checkboxes
✅ Validation and Converters

JSF includes a validation and conversion mechanism that runs in phase 3 of the lifecycle. On error, the cycle short-circuits to phase 6.

Built-in validators:

  • f:validateRequired — checks that the field is not empty
  • f:validateLength — controls the minimum and/or maximum length of a string
  • f:validateLongRange — validates that an integer is within a given range
  • f:validateDoubleRange — validates a decimal number within a range
  • f:validateRegex — validates a string against a regular expression

Custom validators:

Create a class annotated @FacesValidator("id") implementing jakarta.faces.validator.Validator and its validate() method. Throw a ValidatorException with a FacesMessage on error.

Converters:

  • f:convertNumber — number conversion with format, locale and type (number, currency, percent)
  • f:convertDateTime — date and time conversion with pattern and timezone
  • Custom converters via @FacesConverter implementing Converter<T>
xhtml 
<h:inputText id="email" value="#{clientBean.email}">
    <f:validateRequired/>
    <f:validateRegex pattern="^[A-Za-z0-9+_.-]+@(.+)$"/>
</h:inputText>
<h:message for="email" styleClass="error-msg"/>
⚡ AJAX with JSF

JSF natively supports AJAX via the f:ajax component, without requiring an external JavaScript library. Partial requests update only a portion of the page.

Key attributes of f:ajax:

  • execute — list of component IDs whose values are submitted during the AJAX request. @form submits the whole form, @this only the current component.
  • render — list of component IDs to re-render in the AJAX response. @all re-renders the whole page.
  • event — triggering DOM event (e.g. click, change, keyup, blur). Default: action for buttons, valueChange for inputs.
  • listener — bean method to invoke in addition to the normal action (signature: void method(AjaxBehaviorEvent))
  • onevent — JavaScript callback executed at each step of the AJAX request
xhtml 
<h:commandButton value="Search" action="#{clientBean.search}">
    <f:ajax execute="@form" render="resultPanel" event="click"/>
</h:commandButton>

<h:panelGroup id="resultPanel">
    <!-- content updated by AJAX -->
</h:panelGroup>
🧭 Navigation Rules

JSF manages navigation between views by resolving the value returned by an action method (outcome).

Implicit navigation (JSF 2.0+):

By default, if a method returns the string "clients", JSF looks for the view /clients.xhtml. This is the recommended approach — simple and without XML configuration.

  • Return null or void — stays on the current view
  • Return "clients?faces-redirect=true" — redirects (PRG pattern)
  • Return "clients" — internal forward to /clients.xhtml

Explicit navigation (faces-config.xml):

Defined in /WEB-INF/faces-config.xml — useful for complex or conditional rules that are not easily expressed with implicit navigation.

Redirect vs Forward:

  • Forward (default) — the server passes the request internally, the browser URL does not change
  • Redirect — a 302 response is sent, the browser makes a new GET request — the URL changes
💡 JSF Best Practices

Architecture and design:

  • Avoid business logic in beans — Managed Beans are MVC controllers; delegate logic to injected CDI services
  • Use CDI scopes correctly — prefer @RequestScoped or @ViewScoped by default; avoid @SessionScoped for data not tied to the user session
  • Prefer implicit navigation — avoid faces-config.xml rules unless strictly necessary
  • Avoid deep session scope — store in session only what is strictly necessary; prefer view parameters (@ViewScoped)

Performance and maintainability:

  • Use f:ajax for partial updates rather than reloading the whole page
  • Organise views with Facelets templates (header, footer, common layout)
  • Use h:outputText rather than direct #{...} for automatic HTML encoding (XSS prevention)
  • Enable JSF development mode (ProjectStage.Development) during development for detailed error messages
  • Disable client-side ViewState in production if not needed, or use server-side ViewState
