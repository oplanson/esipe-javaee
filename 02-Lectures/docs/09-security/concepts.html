Méthodes d'Authentification — Comparaison

MéthodeProtocoleSécuritéÉtatUse CaseRisques
Basic Auth HTTP RFC 7617 ⚠️ Faible sans TLS Stateless APIs dev, outils internes Credentials en clair (Base64) sans HTTPS, rejeu possible
Form-Based HTTP POST + Session ✅ Bonne Stateful Applications web traditionnelles CSRF, session fixation, session hijacking
Token (JWT) RFC 7519 / Bearer ✅ Bonne Stateless APIs REST, microservices, SPAs XSS si stocké en localStorage, token theft, pas de révocation immédiate
Certificate (mTLS) TLS/X.509 RFC 5246 ✅✅ Excellente Stateless Service-to-service, systèmes critiques Complexité de gestion des certificats, PKI nécessaire
OAuth2 / OIDC RFC 6749 / OIDC ✅✅ Excellente Stateless Délégation, login social, fédération d'identité Complexité du protocole, misconfiguration du redirect_uri

RBAC vs ABAC

FeatureRBACABAC
FlexibilitéFaible — basé sur des rôles prédéfinisÉlevée — combinaison de multiples attributs
ComplexitéSimple à comprendre et administrerComplexe — politique XACML, règles conditionnelles
ScalabilitéBonne pour peu de rôlesExcellente pour de nombreux cas d'accès
Use CaseApplications avec rôles métier clairs (ADMIN, USER, VIEWER)Systèmes multi-tenant, contrôle fin (heure, IP, classification)
Jakarta EE Support✅ Natif — @RolesAllowed, SecurityContext.isCallerInRole()⚠️ Partiel — nécessite implémentation personnalisée
AuditFacile — qui a accès à quoi par rôleDifficile — décisions contextuelles dynamiques
ExempleL'utilisateur "alice" a le rôle ADMINL'utilisateur "alice" peut accéder si département=RH et heure entre 8h-18h

Vulnérabilités OWASP Top 10 (2021)

RangVulnérabilitéDescriptionMitigation Jakarta EE
A01 Broken Access Control Accès non autorisé à des ressources ou fonctionnalités @RolesAllowed, SecurityContext, test des autorisations côté serveur
A02 Cryptographic Failures Données sensibles transmises ou stockées en clair TLS obligatoire, bcrypt/Argon2 pour les mots de passe, chiffrement JCE
A03 Injection Injection SQL, LDAP, OS via des données non validées JPQL paramétré, Jakarta Validation (@NotNull, @Size), critères JPA
A04 Insecure Design Absence de modèle de menace, contrôles de sécurité insuffisants dès la conception Threat modeling, defense-in-depth, principe du moindre privilège
A05 Security Misconfiguration Configurations par défaut non sécurisées, erreurs détaillées exposées Désactiver les endpoints de debug, configurer les error pages, renforcer server.xml
A07 Identification & Auth Failures Authentification faible, sessions non invalidées, mots de passe faibles Jakarta Security API, HTTPS, expiration des tokens, @RememberMe sécurisé
A03 XSS (Cross-Site Scripting) Injection de scripts malveillants dans les pages web Encodage HTML des outputs, CSP header, validation côté serveur
A08 Software & Data Integrity Failures Mise à jour de dépendances non signées, désérialisation non sécurisée Vérifier les checksums Maven, éviter la désérialisation Java native

Structure d'un Token JWT

PartieDescriptionExemple de contenu
Header Métadonnées du token : algorithme de signature (alg) et type (typ) {"alg": "RS256", "typ": "JWT", "kid": "rsa-key-2026"}
Payload Claims : identité, rôles, dates d'émission et d'expiration, émetteur, audience {"iss": "https://auth.bank.com", "sub": "alice", "aud": "banking-api", "exp": 1735689600, "iat": 1735686000, "groups": ["USER", "MANAGER"], "upn": "alice@bank.com"}
Signature Hash cryptographique de (Base64URL(header) + "." + Base64URL(payload)) signé avec la clé privée RSA-SHA256 ou HMAC-SHA256 — vérifiable avec la clé publique
Format final Les trois parties encodées en Base64URL, séparées par des points eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.SflKxwRJSMeKKF2QT4fwpMeJf36

Bonnes Pratiques de Sécurité

CatégoriePratiqueImplémentation Jakarta EE
TransportToujours HTTPS en production, redirection HTTP → HTTPSLiberty <ssl>, HSTS header, désactiver HTTP port
AuthentificationUtiliser des algorithmes de hachage adaptés (bcrypt, Argon2)IdentityStore avec BCrypt, ne jamais stocker les mots de passe en clair
AutorisationPrincipe du moindre privilège — accorder le minimum nécessaire@DenyAll par défaut, @RolesAllowed explicite
TokensDurée de vie courte pour les access tokens (15-60 min)Claim exp dans JWT, refresh tokens longue durée séparés
EntréesValider et sanitiser toutes les entrées utilisateurJakarta Validation, @Pattern, @Size, @Valid
ErreursNe pas exposer les détails techniques dans les messages d'erreurExceptionMapper JAX-RS retournant des messages génériques
SecretsNe jamais coder en dur les credentials et clés dans le codeMicroProfile Config depuis env vars, Kubernetes Secrets
HeadersAjouter les security headers HTTP dans toutes les réponsesFilter JAX-RS ou Servlet ajoutant CSP, HSTS, X-Frame-Options
LogsJournaliser les accès et les échecs d'authentificationEviter de logger les données sensibles (passwords, tokens)

Codes HTTP liés à la Sécurité

CodeSignificationQuand l'utiliser
200 OKSuccèsRequête authentifiée et autorisée traitée avec succès
400 Bad RequestRequête malforméeToken JWT malformé, paramètres invalides, validation échouée
401 UnauthorizedNon authentifiéAucun token fourni, token expiré ou invalide — relancer l'authentification
403 ForbiddenNon autoriséAuthentifié mais ne possède pas le rôle requis (RBAC refus)
404 Not FoundRessource introuvableÀ utiliser à la place de 403 pour masquer l'existence d'une ressource privée
405 Method Not AllowedMéthode HTTP non autoriséeTentative d'accès par une méthode non permise sur la ressource
429 Too Many RequestsRate limit dépasséTrop de requêtes depuis une même IP/token — renvoyer Retry-After
498 Invalid TokenToken invalide (non-standard)Certaines APIs utilisent ce code pour les tokens expirés ou révoqués
500 Internal Server ErrorErreur serveurErreur de traitement — ne pas exposer les détails dans le body

Glossaire

TermeDéfinition
CIA TriadLes trois piliers de la sécurité : Confidentiality (confidentialité), Integrity (intégrité), Availability (disponibilité)
JWTJSON Web Token — standard RFC 7519 pour les tokens auto-porteurs signés, composés d'un header, payload et signature en Base64URL
OAuth2Protocole de délégation d'autorisation (RFC 6749) permettant à une application d'accéder aux ressources d'un utilisateur sans connaître ses credentials
OIDCOpenID Connect — couche d'identité au-dessus d'OAuth2 ajoutant un ID Token (JWT) pour l'authentification des utilisateurs
RBACRole-Based Access Control — contrôle d'accès basé sur des rôles prédéfinis assignés aux utilisateurs
ABACAttribute-Based Access Control — contrôle d'accès basé sur des attributs dynamiques (utilisateur, ressource, environnement)
mTLSMutual TLS — authentification TLS bidirectionnelle où le client et le serveur présentent chacun un certificat X.509
OWASPOpen Web Application Security Project — organisation produisant le Top 10 des vulnérabilités web les plus critiques
CSPContent Security Policy — en-tête HTTP définissant les sources de contenu autorisées pour prévenir le XSS
CORSCross-Origin Resource Sharing — mécanisme navigateur contrôlant les requêtes HTTP vers un domaine différent de l'origine
CSRFCross-Site Request Forgery — attaque forçant un utilisateur authentifié à exécuter une action non désirée sur un site tiers
HSTSHTTP Strict Transport Security — en-tête forçant le navigateur à utiliser HTTPS exclusivement pour un domaine donné
