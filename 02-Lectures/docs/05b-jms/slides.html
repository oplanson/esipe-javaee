📨 Messagerie Enterprise — Pourquoi ?

Les limites des appels directs

Les appels synchrones (REST, EJB Remote) créent un couplage fort entre les services : l'appelant doit attendre la réponse, et une panne du service cible bloque l'ensemble de la chaîne.

  • Couplage fort — l'émetteur connaît l'adresse et le contrat du récepteur
  • Disponibilité requise — les deux services doivent être actifs simultanément
  • Scalabilité limitée — la montée en charge d'un service impacte directement l'autre
  • Risque de cascade — une panne se propage instantanément

La messagerie enterprise : bénéfices

  • ✅ Couplage faible — les services communiquent via un broker, sans se connaître directement
  • ✅ Communication asynchrone — l'émetteur n'attend pas la réponse du récepteur
  • ✅ Résilience — les messages sont persistés ; si le consommateur est indisponible, les messages l'attendent
  • ✅ Découplage temporel — émetteur et récepteur n'ont pas besoin d'être actifs en même temps
  • ✅ Lissage de la charge — le broker absorbe les pics de trafic
  • ✅ Traçabilité — les messages peuvent être rejoués, archivés, audités

JMS vs Appels Directs

CritèreAppel Direct (REST/EJB)Messagerie JMS
ModeSynchrone — bloquantAsynchrone — non bloquant
CouplageFort — adresse connueFaible — via broker
DisponibilitéRequise des deux côtésIndépendante
RésiliencePropagation des pannesIsolation et rétention
🏗️ Architecture JMS

JMS (Jakarta Messaging Service) définit une API standard pour la communication asynchrone par messages via un broker de messages.

Composants principaux

  • ConnectionFactory — fabrique de connexions, configurée dans le serveur d'application (JNDI). Point d'entrée pour créer des connexions ou un JMSContext
  • Destination — cible des messages : Queue (Point-à-Point) ou Topic (Pub/Sub)
  • Connection — connexion physique au broker (gère l'authentification, le pool)
  • Session — contexte transactionnel pour l'envoi et la réception de messages
  • MessageProducer — crée et envoie des messages vers une Destination
  • MessageConsumer — reçoit des messages depuis une Destination (synchrone ou async)
  • Message — unité de données échangée — corps + en-têtes + propriétés

JMS 2.0 — API simplifiée

JMS 2.0 (Jakarta EE 7+) introduit JMSContext, qui combine Connection + Session en un seul objet injectable via @Inject.

  • @Inject JMSContext jmsContext — injection directe dans un bean CDI
  • jmsContext.createProducer().send(destination, body) — envoi en une ligne
  • Gestion automatique de la connexion par le conteneur
📥 Point-à-Point (Queue)

Le modèle Point-à-Point utilise une Queue : chaque message est consommé par un seul consommateur.

Caractéristiques

  • Un message → un consommateur — même si plusieurs consommateurs écoutent la même Queue, chaque message n'est délivré qu'à un seul
  • Garantie de livraison — les messages sont persistés et attendent jusqu'à être consommés
  • Persistance — les messages survivent au redémarrage du broker (messages persistants)
  • Accusé de réception (ACK) — le broker attend un ACK du consommateur avant de supprimer le message
  • Load balancing naturel — plusieurs instances du même consommateur se partagent la charge
  • Ordre FIFO — les messages sont généralement consommés dans l'ordre d'arrivée

Cas d'usage typiques

  • Traitement de commandes e-commerce
  • File de tâches (job queue) — envoi d'emails, génération de rapports
  • Intégration entre microservices (commande → stock → facturation)
📡 Pub/Sub (Topic)

Le modèle Publish/Subscribe utilise un Topic : chaque message est diffusé à tous les abonnés actifs.

Caractéristiques

  • Un message → plusieurs abonnés — chaque abonné reçoit une copie du message
  • Broadcast — idéal pour notifier plusieurs systèmes d'un même événement
  • Abonnements non-durables — l'abonné doit être actif au moment de la publication pour recevoir le message
  • Abonnements durables — le broker conserve les messages pour les abonnés temporairement déconnectés

Durable vs Non-Durable

TypeAbonné hors ligneCas d'usage
Non-durableMessages perdusNotifications temps réel, logs
DurableMessages conservés jusqu'à reconnexionNotifications critiques, audit

Cas d'usage typiques

  • Notifications d'événements métier (création d'un compte, passage d'une commande)
  • Synchronisation de cache entre instances
  • Publication de cours boursiers, de métriques temps réel
📄 Types de Messages JMS

JMS définit 5 types de messages, chacun adapté à un type de contenu particulier.

Les 5 types

  • TextMessage — corps de type String ; idéal pour JSON, XML, texte brut. Le plus utilisé en pratique
  • ObjectMessage — corps de type Serializable ; transporte un objet Java sérialisé. À éviter en inter-applicatif (couplage fort)
  • MapMessage — paires clé/valeur (String → primitif) ; accès nommé aux champs, portable
  • BytesMessage — corps de type tableau d'octets (byte[]) ; pour les données binaires (images, fichiers, protocoles custom)
  • StreamMessage — flux de types primitifs Java écrits et lus séquentiellement

En-têtes JMS (headers)

  • JMSMessageID — identifiant unique généré par le broker
  • JMSDestination — Queue ou Topic cible
  • JMSDeliveryMode — PERSISTENT ou NON_PERSISTENT
  • JMSPriority — priorité de livraison (0–9, défaut 4)
  • JMSExpiration — date d'expiration du message
  • JMSCorrelationID — pour relier une réponse à sa requête (request-reply)

Propriétés et sélecteurs

Les propriétés sont des métadonnées applicatives arbitraires (String, int, boolean…) attachées au message via message.setStringProperty("key", "value").

Les sélecteurs de messages (Message Selectors) permettent aux consommateurs de filtrer les messages en fonction de leurs propriétés, via une syntaxe proche de SQL WHERE : "transferType = 'INTERNATIONAL' AND amount > 1000".

⚙️ Producteurs et Consommateurs

JMS 2.0 simplifie drastiquement l'API avec JMSContext — une seule interface remplace Connection + Session.

Producteur avec JMSContext (JMS 2.0)

  • @Inject JMSContext jmsContext — injection directe dans un CDI bean
  • @Inject @JMSConnectionFactory("jms/cf") ConnectionFactory — factory JNDI
  • jmsContext.createProducer().send(queue, textMessage) — envoi simplifié
  • Options du producteur : priorité, TTL, mode de livraison, délai

Consommateur synchrone

  • jmsContext.createConsumer(destination).receiveBody(String.class) — bloquant
  • receiveBody(String.class, timeout) — avec délai d'attente en ms
  • À éviter dans les servlets / EJB (threads gérés par le conteneur)

Consommateur asynchrone — MessageListener

  • Implémente MessageListener avec onMessage(Message msg)
  • Appelé automatiquement par le conteneur à chaque nouveau message
  • Non bloquant — le thread est libéré entre les messages

Pattern Request-Reply

  • L'émetteur définit JMSReplyTo (Queue temporaire) et JMSCorrelationID
  • Le récepteur envoie sa réponse sur la Queue JMSReplyTo
  • L'émetteur consomme la réponse en filtrant sur JMSCorrelationID
🤖 Message-Driven Beans

Les Message-Driven Beans (MDB) sont des EJB déclenchés automatiquement par l'arrivée d'un message JMS. Ils constituent le moyen standard de consommer des messages dans Jakarta EE.

Annotation @MessageDriven

  • @MessageDriven(activationConfig = {...}) — configure l'abonnement JMS du MDB
  • @ActivationConfigProperty(propertyName="destinationType", propertyValue="jakarta.jms.Queue")
  • @ActivationConfigProperty(propertyName="destination", propertyValue="jms/transferQueue")
  • @ActivationConfigProperty(propertyName="messageSelector", propertyValue="...") — filtre de messages

Cycle de vie du MDB

  • Does Not Exist → Pooled — le conteneur crée un pool d'instances MDB au démarrage
  • Pooled → onMessage() — une instance est sélectionnée et la méthode est invoquée
  • Après onMessage(), l'instance retourne dans le pool
  • @PostConstruct et @PreDestroy sont supportés

Injection CDI dans un MDB

  • @Inject fonctionne dans un MDB comme dans un EJB Session
  • Les services applicatifs (BankingService, NotificationService…) sont injectables
  • Pas de scope conversationnel — le MDB est stateless

MDB Topic (Pub/Sub)

  • destinationType = jakarta.jms.Topic
  • subscriptionDurability = "Durable" — pour les abonnements durables
  • durableSubscriptionName = "myDurableSub" — nom unique de l'abonnement
  • clientId = "myClientId" — identifiant client pour la durabilité
🔐 Transactions JMS

La gestion des transactions est critique en messagerie enterprise pour garantir qu'un message est traité exactement une fois.

CMT par défaut dans les MDB

  • Le conteneur démarre une transaction avant onMessage() et la committe après son retour normal
  • La transaction couvre à la fois l'ACK du message JMS et les opérations JPA/BD
  • Atomicité garantie : si la BD échoue, le message est remis en file

Rollback et rélivraison

  • En cas d'exception, la transaction est rollbackée et le message est rélivré par le broker
  • Le nombre de tentatives est configurable (propriété maxRedeliveryCount)
  • Après N tentatives échouées, le message est envoyé en Dead Letter Queue (DLQ)

Poison Message Detection

  • Un poison message est un message qui déclenche systématiquement une exception, entraînant une boucle infinie de rélivraison
  • La DLQ interrompt cette boucle en isolant le message défaillant
  • Stratégie : inspecter le header JMSXDeliveryCount dans onMessage()

Dead Letter Queue

  • File dédiée recevant les messages non traitables après épuisement des tentatives
  • Un MDB dédié (DLQ Handler) consomme cette file pour alerter, journaliser, corriger ou archiver
  • Évite la perte silencieuse de messages
🏆 Meilleures Pratiques JMS

Conception des messages

  • ✅ Préférer TextMessage avec JSON — interopérable, lisible, versionnable
  • ✅ Garder les messages petits — inclure uniquement l'identifiant et les données essentielles
  • ✅ Inclure un timestamp et un correlationId dans le corps JSON
  • ⛔ Éviter ObjectMessage entre applications différentes — couplage Java-to-Java

Sélecteurs pour le filtrage

  • Utiliser les sélecteurs JMS pour router les messages vers les MDB spécialisés
  • Les sélecteurs sont évalués côté broker — réduisent le trafic réseau
  • Exemple : "transferType = 'INTERNATIONAL'" sur une Queue partagée

Gestion de la DLQ

  • Toujours configurer une DLQ par Queue applicative importante
  • Déployer un MDB DLQ Handler qui alerte et journalise en temps réel
  • Prévoir un outil de replay pour réinjecter les messages corrigés

Monitoring et performance

  • Superviser la profondeur des Queues (métrique queueDepth)
  • Configurer le pool de MDB (maxEndpoints) selon la charge
  • Éviter les opérations longues dans onMessage() — déléguer à un thread asynchrone si nécessaire

Configuration Open Liberty

  • Activer les features messagingClient-3.0, mdb-3.2, wasJmsClient-2.0 dans server.xml
  • Déclarer jmsActivationSpec, jmsConnectionFactory, jmsQueue, jmsTopic
  • Utiliser JNDI names cohérents : jms/transferCF, jms/transferQueue, jms/dlq
