Concepts clés

Comparatifs, tableaux de référence et glossaire pour l'Architecture Hexagonale — Ports & Adapters.

Architecture Hexagonale vs Autres Architectures

AspectMonolithe ClassiqueDDDHexagonale
Direction des dépendances UI → Service → DAO — vers le bas, couplage fort Vers le domaine, mais peut dériver selon l'implémentation Toujours vers le centre — domaine sans dépendance externe
Testabilité ⚠️ Difficile — tests d'intégration nécessaires, serveur requis ✅ Bonne si le domaine est pur, mais les repos peuvent coupler ✅✅ Excellente — domaine et use cases testables en POJO pur
Couplage infrastructure/domaine ❌ Fort — entités JPA dans le domaine, SQL dans les services ⚠️ Moyen — risque d'annotations JPA dans les entités domaine ✅ Nul — entités domaine pures, mapping dans l'adapter
Isolation du domaine ❌ Faible — la logique fuite dans les couches techniques ✅ Bonne si les patterns tactiques sont respectés ✅✅ Maximale — le domaine ignore tout de l'infrastructure
Remplacement d'un composant technique ❌ Risqué — propagation dans tout le code ⚠️ Partiel — dépend de l'abstraction des repositories ✅ Simple — remplacer un adapter sans toucher au domaine
Complexité de mise en place ✅ Faible — structure simple, apprentissage rapide ⚠️ Élevée — nombreux patterns à maîtriser ⚠️ Moyenne — plus de classes, mais structure claire

Ports Primaires vs Secondaires

TypeDirectionQui appelle quiExemplesAnnotation Jakarta EE
Port Primaire
(Driving)		 Entrant — vers le domaine Adapter primaire → appelle → Port primaire MoneyTransferUseCase, AccountQueryUseCase, CreateAccountUseCase Aucune — interface Java pure dans le domaine
Adapter Primaire
(Driving)		 Entrant — reçoit du monde externe Monde externe → appelle → Adapter → Port REST Resource (@Path), Servlet, CLI, Test Driver @Path, @ApplicationScoped, @WebServlet
Port Secondaire
(Driven)		 Sortant — le domaine sort vers l'extérieur Use case → appelle → Port secondaire AccountPort, NotificationPort, AuditPort Aucune — interface Java pure dans le domaine
Adapter Secondaire
(Driven)		 Sortant — reçoit des appels du domaine Port → délégué → Adapter → Infrastructure JPA Adapter, JMS Adapter, REST Client Adapter @ApplicationScoped, @PersistenceContext, @Inject

Règles de Dépendance

CouchePeut dépendre deNe peut PAS dépendre de
Domaine
com.bank.domain		 Lui-même uniquement — Java standard (JDK) seulement Application, Infrastructure, Jakarta EE (jakarta.*), JPA, JAX-RS, JMS
Application
com.bank.application		 Domaine — peut aussi utiliser des annotations CDI (@ApplicationScoped, @Inject) Infrastructure — ne connaît pas les adapters concrets
Infrastructure
com.bank.infrastructure		 Domaine, Application, et toutes les APIs Jakarta EE (JPA, JAX-RS, JMS, CDI) Pas de contrainte supplémentaire — c'est la couche technique

Bénéfices Architecture Hexagonale

BénéficeDescriptionImpact
Testabilité maximale Le domaine et les use cases sont testables en Java pur, sans serveur ni base de données Tests unitaires 100× plus rapides qu'avec Arquillian
Isolation du domaine La logique métier ne connaît aucune technologie — elle exprime purement les règles métier Code lisible par les experts métier, bugs métier facilement localisables
Remplacement d'infrastructure Remplacer JPA par MongoDB, ou REST par GraphQL, ne touche que les adapters Migration technologique sans risque de régression sur les règles métier
Multi-entrée La même logique métier accessible depuis REST, JMS, CLI, tests — via des adapters différents Pas de duplication de la logique pour chaque point d'entrée
Maintenabilité Structure explicite — chaque développeur sait exactement où placer un nouveau code Onboarding plus rapide, revues de code facilitées
Évolutivité vers microservices Un bounded context hexagonal est naturellement extractible en microservice Migration monolithe → microservices moins risquée

Quand Utiliser l'Architecture Hexagonale

CritèreFavorable ✅Défavorable ⚠️
Complexité du domaine Domaine métier riche avec de nombreuses règles — secteur financier, e-commerce, santé Application CRUD simple — formulaire → base de données → affichage
Durée de vie du projet Application maintenue sur plusieurs années, avec évolutions fréquentes des règles métier Prototype ou POC court terme — overhead de structure non justifié
Tests automatisés Équipe avec une culture de tests unitaires — bénéfice immédiat de la testabilité Pas de culture test — la structure hexagonale sans tests n'apporte pas grand chose
Évolution de l'infrastructure Plusieurs sources de données, migration prévue, multiples clients (REST + JMS + CLI) Infrastructure fixe, une seule source de données, un seul type d'API
Taille de l'équipe Équipe de développeurs ayant besoin d'une structure commune et de frontières claires Développeur solo sur un petit projet — overhead de communication pas nécessaire

Glossaire

TermeDéfinition
Port Primaire Interface Java déclarée dans le domaine, exposant un use case de l'application au monde extérieur. Exemple : MoneyTransferUseCase.
Port Secondaire Interface Java déclarée dans le domaine, que le domaine utilise pour accéder à des ressources externes (BDD, messagerie). Exemple : AccountPort.
Adapter Primaire Composant d'infrastructure qui reçoit les entrées du monde externe et les traduit en appels vers un port primaire. Exemple : TransferRestAdapter (ressource JAX-RS).
Adapter Secondaire Composant d'infrastructure qui implémente un port secondaire. Traduit les appels du domaine en appels techniques. Exemple : JpaAccountAdapter implements AccountPort.
Use Case Cas d'utilisation de l'application — une action que l'utilisateur ou un système peut déclencher. Implémenté par un service applicatif qui implémente un port primaire.
Domaine Cœur de l'application contenant toute la logique métier pure. Entités, Value Objects, Services de domaine, interfaces des ports. Aucune dépendance technique.
DIP Dependency Inversion Principle — les modules de haut niveau (domaine) ne dépendent pas des modules de bas niveau (infrastructure). Les deux dépendent d'abstractions (interfaces/ports).
Clean Architecture Architecture proposée par Robert C. Martin (Uncle Bob) partageant les mêmes principes que l'hexagonale : règle de dépendance vers l'intérieur, isolation du domaine, testabilité.
