Key Concepts

Comparisons, reference tables and glossary for Hexagonal Architecture — Ports & Adapters.

Hexagonal Architecture vs Other Architectures

AspectClassic MonolithDDDHexagonal
Dependency direction UI → Service → DAO — downward, strong coupling Towards the domain, but can drift depending on implementation Always towards the centre — domain with no external dependency
Testability ⚠️ Difficult — integration tests needed, server required ✅ Good if the domain is pure, but repos can couple ✅✅ Excellent — domain and use cases testable as plain POJOs
Infrastructure/domain coupling ❌ Strong — JPA entities in the domain, SQL in services ⚠️ Medium — risk of JPA annotations in domain entities ✅ Zero — pure domain entities, mapping in the adapter
Domain isolation ❌ Weak — logic leaks into technical layers ✅ Good if tactical patterns are respected ✅✅ Maximum — the domain is unaware of infrastructure
Replacing a technical component ❌ Risky — propagation throughout the whole codebase ⚠️ Partial — depends on repository abstraction ✅ Simple — replace an adapter without touching the domain
Setup complexity ✅ Low — simple structure, fast learning curve ⚠️ High — many patterns to master ⚠️ Medium — more classes, but a clear structure

Primary vs Secondary Ports

TypeDirectionWho calls whomExamplesJakarta EE Annotation
Primary Port
(Driving)		 Inbound — towards the domain Primary adapter → calls → Primary port MoneyTransferUseCase, AccountQueryUseCase, CreateAccountUseCase None — pure Java interface in the domain
Primary Adapter
(Driving)		 Inbound — receives from the external world External world → calls → Adapter → Port REST Resource (@Path), Servlet, CLI, Test Driver @Path, @ApplicationScoped, @WebServlet
Secondary Port
(Driven)		 Outbound — the domain reaches out Use case → calls → Secondary port AccountPort, NotificationPort, AuditPort None — pure Java interface in the domain
Secondary Adapter
(Driven)		 Outbound — receives calls from the domain Port → delegates → Adapter → Infrastructure JPA Adapter, JMS Adapter, REST Client Adapter @ApplicationScoped, @PersistenceContext, @Inject

Hexagonal Architecture Benefits

BenefitDescriptionImpact
Maximum testability Domain and use cases are testable in pure Java, without server or database Unit tests 100× faster than with Arquillian
Domain isolation Business logic knows no technology — it purely expresses business rules Code readable by domain experts, business bugs easily located
Infrastructure replacement Replacing JPA with MongoDB, or REST with GraphQL, only touches the adapters Technology migration with no risk of regression on business rules
Multiple entry points Same business logic accessible from REST, JMS, CLI, tests — via different adapters No duplication of logic for each entry point
Maintainability Explicit structure — every developer knows exactly where to place new code Faster onboarding, easier code reviews
Scalability towards microservices A hexagonal bounded context is naturally extractable as a microservice Less risky monolith → microservices migration

When to Use Hexagonal Architecture

CriterionFavourable ✅Unfavourable ⚠️
Domain complexity Rich business domain with many rules — finance, e-commerce, healthcare Simple CRUD application — form → database → display
Project lifespan Application maintained over several years, with frequent business rule changes Short-term prototype or POC — structural overhead not justified
Automated testing Team with a unit testing culture — immediate testability benefit No test culture — hexagonal structure without tests adds little value
Infrastructure evolution Multiple data sources, planned migration, multiple clients (REST + JMS + CLI) Fixed infrastructure, single data source, single API type
Team size Team of developers needing a common structure and clear boundaries Solo developer on a small project — communication overhead not needed

Glossary

TermDefinition
Primary Port Java interface declared in the domain, exposing an application use case to the outside world. Example: MoneyTransferUseCase.
Secondary Port Java interface declared in the domain, used by the domain to access external resources (DB, messaging). Example: AccountPort.
Primary Adapter Infrastructure component that receives external-world input and translates it into calls on a primary port. Example: TransferRestAdapter (JAX-RS resource).
Secondary Adapter Infrastructure component that implements a secondary port. Translates domain calls into technical calls. Example: JpaAccountAdapter implements AccountPort.
Use Case Application use case — an action a user or system can trigger. Implemented by an application service that implements a primary port.
Domain Core of the application containing all pure business logic. Entities, Value Objects, Domain Services, port interfaces. No technical dependencies.
DIP Dependency Inversion Principle — high-level modules (domain) do not depend on low-level modules (infrastructure). Both depend on abstractions (interfaces/ports).
Clean Architecture Architecture proposed by Robert C. Martin (Uncle Bob) sharing the same principles as hexagonal: inward dependency rule, domain isolation, testability.
