Architecture Hexagonale — Diagramme

Représentation visuelle du pattern Ports & Adapters — le domaine au centre, les adapters à la périphérie.

Adapters Primaires (Driving)

Les adapters primaires initient l'exécution d'un use case. Ils traduisent un événement externe (requête HTTP, message, commande CLI) en appel sur un port primaire du domaine. L'adapter ne contient aucune logique métier — il délègue immédiatement au port.

  • REST Controllers / Resources — ressources JAX-RS annotées @Path, reçoivent les requêtes HTTP et appellent le use case
  • Servlets — @WebServlet pour des cas d'usage non-REST (formulaires, téléchargements)
  • Message Consumers (initiant des requêtes) — Message-Driven Beans qui traitent un message entrant et déclenchent un use case
  • CLI Commands — outils de ligne de commande pour les opérations de maintenance ou de batch
  • Test Drivers — les classes de test JUnit qui appellent directement les use cases — c'est la valeur principale de l'architecture !

Adapters Secondaires (Driven)

Les adapters secondaires reçoivent les appels du domaine via les ports secondaires. Ils traduisent les requêtes du domaine (en termes métier) en appels techniques (SQL, JMS, HTTP). L'adapter effectue le mapping entre les objets du domaine et les entités techniques.

  • JPA Repositories — implémentent les ports secondaires avec JPA (EntityManager, entités JPA séparées des entités domaine)
  • JMS Producers / Consumers (driven) — publient des événements métier vers un broker de messagerie
  • External HTTP Clients (Rest Client) — MicroProfile Rest Client appelant des APIs tierces (système de paiement, service de fraude)
  • File System Adapters — lecture/écriture de fichiers (import CSV, export de rapports)
  • In-Memory Adapters (for tests) — implémentations HashMap-based pour les tests unitaires des use cases sans base de données

Flux de Dépendance

La règle fondamentale de l'architecture hexagonale est que toutes les flèches de dépendance pointent vers le domaine, jamais vers l'extérieur :

  • Les adapters primaires dépendent des interfaces de ports primaires (définis dans le domaine)
  • Les adapters secondaires implémentent les interfaces de ports secondaires (définis dans le domaine)
  • Le domaine n'a zéro connaissance des adapters — il ne les importe pas, ne les référence pas
  • Si le domaine voulait parler à l'extérieur, il pose une interface (port secondaire) — l'extérieur l'implémente
  • Le résultat : remplacer un adapter (ex. migrer de JPA vers MongoDB) ne nécessite aucune modification dans le domaine ou les use cases
