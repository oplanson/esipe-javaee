⬡ Architecture Hexagonale — Introduction

Historique — Alistair Cockburn 2005

L'architecture hexagonale, aussi connue sous le nom de Ports and Adapters, a été introduite par Alistair Cockburn en 2005. Elle propose de placer le domaine métier au centre de l'application et d'isoler toute communication avec l'extérieur derrière des interfaces appelées ports.

  • Alias : Ports and Adapters Architecture
  • Objectif fondamental : permettre à une application d'être également pilotée par des utilisateurs, des programmes, des tests automatisés ou des scripts batch
  • La forme hexagonale symbolise la possibilité d'avoir plusieurs points d'entrée et de sortie — aucun côté n'est privilégié

Problèmes résolus

  • Couplage infrastructure/domaine — le domaine ne doit jamais importer de classes JPA, JAX-RS ou JMS
  • Testabilité difficile — avec l'hexagonale, les use cases sont testables en POJO pur, sans serveur
  • Changements d'infrastructure coûteux — remplacer JPA par MongoDB ne touche que les adapters secondaires
  • Logique métier éparpillée — centralisée dans le domaine, aucune fuite vers les couches techniques

Évolution des architectures

  • Monolithe classique — couches horizontales (UI → Service → DAO), dépendances vers le bas, domaine couplé à la base de données
  • DDD — modèle de domaine riche, bounded contexts, mais toujours risque de couplage infrastructure si mal appliqué
  • Architecture Hexagonale — domaine au centre, infrastructure à la périphérie, ports comme contrats, adapters comme implémentations
🔄 Principe d'Inversion de Dépendances

DIP — Dépendre des abstractions, pas des concrétions

Le Dependency Inversion Principle (DIP) est le fondement technique de l'architecture hexagonale. Il stipule que les modules de haut niveau (domaine, use cases) ne doivent jamais dépendre des modules de bas niveau (JPA, REST). Les deux doivent dépendre d'abstractions (interfaces).

  • Règle 1 — Les modules de haut niveau ne doivent pas dépendre des modules de bas niveau
  • Règle 2 — Les abstractions ne doivent pas dépendre des détails — ce sont les détails qui dépendent des abstractions
  • En pratique : le domaine définit des interfaces, l'infrastructure les implémente

Le domaine ne connaît pas l'infrastructure

  • Aucune annotation JPA (@Entity, @Column) dans le domaine
  • Aucun import jakarta.persistence.* dans les entités ou services de domaine
  • Aucune annotation JAX-RS (@Path, @GET) dans le domaine
  • Le domaine est un module Java ordinaire — compilable sans dépendances Jakarta EE

Interfaces dans le domaine, implémentations dans l'infra

  • L'interface AccountPort vit dans com.bank.domain — c'est un port secondaire
  • La classe JpaAccountAdapter implements AccountPort vit dans com.bank.infrastructure
  • CDI injecte l'implémentation concrète sans que le domaine ne la connaisse

Avant / Après le DIP

  • Avant : MoneyTransferService importe et instancie JpaAccountRepository directement → couplage fort
  • Après : MoneyTransferService déclare une dépendance sur AccountPort (interface) → l'implémentation est injectée par CDI
🏗️ Structure Hexagonale — Couches

Couche Domaine — le cœur immuable

La couche Domaine contient toute la logique métier. Elle est totalement indépendante de tout framework ou technologie.

  • Entités — objets avec identité métier (Account, Client)
  • Value Objects — objets immuables sans identité (Money, AccountId)
  • Services de domaine — logique métier impliquant plusieurs entités
  • Interfaces des ports — contrats que l'infrastructure devra implémenter
  • Aucune annotation Jakarta EE, aucun framework — Java pur

Couche Application — orchestration des use cases

  • Contient les use cases (cas d'utilisation) de l'application
  • Orchestre les entités du domaine et les appels aux ports secondaires
  • Implémente les ports primaires (interfaces des use cases)
  • Exemples : MoneyTransferService, AccountQueryService

Couche Infrastructure — adapters techniques

  • Adapters REST — ressources JAX-RS qui reçoivent les requêtes HTTP et appellent les ports primaires
  • Adapters JPA — implémentations JPA des ports secondaires (repositories)
  • Adapters JMS — Message-Driven Beans ou producteurs JMS
  • Adapters API externe — clients HTTP (MicroProfile Rest Client) implémentant des ports secondaires
🔌 Ports Primaires vs Secondaires

Ports Primaires (Driving) — entrées du domaine

Les ports primaires sont les interfaces que le domaine expose vers l'extérieur. Ils représentent les cas d'usage que l'application offre. Les adapters primaires les appellent pour déclencher une action dans le domaine.

  • Exemples : MoneyTransferUseCase, AccountQueryUseCase, CreateAccountUseCase
  • Les REST Controllers, Servlets et CLI sont des adapters primaires qui utilisent ces ports
  • Direction du flux : Adapter → Port → Domaine

Ports Secondaires (Driven) — sorties du domaine

Les ports secondaires sont les interfaces que le domaine définit pour accéder à des ressources externes (base de données, messagerie, API tierces). Le domaine les définit, l'infrastructure les implémente.

  • Exemples : AccountPort, TransactionPort, NotificationPort
  • Les adapters JPA, JMS et HTTP Client sont des adapters secondaires qui implémentent ces ports
  • Direction du flux : Domaine → Port → Adapter

Résumé mnémotechnique

  • Primaire = le monde extérieur pilote (drive) l'application
  • Secondaire = l'application pilote (drive) le monde extérieur
📦 Package Structure et Dependency Flow

Organisation des packages recommandée

  • com.bank.domain.account — entités (Account, Transaction), value objects (Money, AccountId), interfaces des ports (AccountPort)
  • com.bank.domain.transfer — logique de transfert, port primaire (MoneyTransferUseCase)
  • com.bank.application — use cases / services applicatifs (MoneyTransferService)
  • com.bank.infrastructure.persistence — adapters JPA (JpaAccountAdapter, entités JPA)
  • com.bank.infrastructure.web — adapters REST (TransferRestAdapter)
  • com.bank.infrastructure.messaging — adapters JMS

Règles de dépendance — la règle d'or

  • ✅ application peut importer des classes de domain
  • ✅ infrastructure peut importer des classes de domain et application
  • ❌ domain ne doit jamais importer des classes de infrastructure
  • ❌ domain ne doit jamais importer des classes de application
  • ❌ Jamais d'import jakarta.persistence, jakarta.ws.rs, jakarta.jms dans le package domain

Enforcer la règle avec ArchUnit

  • La bibliothèque ArchUnit permet de tester les règles d'architecture en JUnit
  • Un test noClasses().that().resideInPackage("..domain..")​.should().dependOnClassesThat().resideInPackage("..infrastructure..") échoue immédiatement si la règle est violée
⚙️ Implémentation des Ports et Adapters

Port = interface Java dans le domaine

Un port est simplement une interface Java déclarée dans le package domaine. Elle utilise exclusivement des types du domaine — pas de types JPA, JAX-RS ou JDBC.

  • Port primaire — interface du use case : MoneyTransferUseCase avec transferMoney(TransferCommand)
  • Port secondaire — interface repository : AccountPort avec findById(AccountId), save(Account)

Adapter = implémentation dans l'infrastructure

  • Adapter primaire REST — ressource JAX-RS TransferRestAdapter annotée @Path, @ApplicationScoped ; injecte le port primaire et délègue
  • Adapter secondaire JPA — classe JpaAccountAdapter implements AccountPort annotée @ApplicationScoped ; contient @PersistenceContext EntityManager ; effectue le mapping entre entités JPA et entités domaine

Mapping entre entités JPA et entités domaine

  • L'adapter JPA utilise des entités JPA séparées (AccountJpaEntity) dans le package infrastructure
  • Aucune annotation JPA sur les entités domaine — séparation stricte
  • Le mapping (entité JPA ↔ entité domaine) se fait dans l'adapter — méthodes toDomain() / toJpa()
🧪 Stratégies de Test

Test du domaine — POJO pur, sans framework

La couche domaine est testable avec de simples tests JUnit 5 — aucun serveur d'application, aucune base de données, aucune configuration Jakarta EE requise.

  • Tests unitaires ultra-rapides (millisecondes) — exécutables à chaque compilation
  • Les règles métier sont testées directement sur les entités et value objects
  • Exemple : account.debitAccount(Money.of(100, "EUR")) → vérification des invariants

Test des use cases — mock adapters

  • Les ports secondaires sont remplacés par des mock adapters (implémentations in-memory)
  • On peut utiliser Mockito ou implémenter manuellement un AccountPortMock avec une Map<AccountId, Account>
  • Les tests des services applicatifs s'exécutent sans Spring, sans CDI, sans JPA
  • Le comportement complet d'un use case est testé en isolant strictement les dépendances

Test des adapters — tests d'intégration ciblés

  • Adapters JPA — testés avec une base H2 ou Testcontainers (PostgreSQL réel)
  • Adapters REST — testés avec Arquillian ou REST-assured + Open Liberty embedded
  • Les tests d'intégration sont moins nombreux mais couvrent les contrats d'interface

Bénéfices pour la maintenabilité

  • Rapidité — les tests unitaires du domaine s'exécutent en < 1 seconde
  • Isolation — chaque couche est testée indépendamment
  • Fiabilité — les tests ne cassent pas quand on change un adapter (ex. migration JPA → MongoDB)
  • Documentation vivante — les tests du domaine documentent les règles métier
🔄 Refactorisation DDD → Hexagonale

Pourquoi refactoriser depuis DDD ?

Une application DDD bien conçue est déjà à mi-chemin vers l'hexagonale. La refactorisation consiste principalement à extraire des interfaces et à déplacer les implémentations dans l'infrastructure.

Étapes de la refactorisation

  • Étape 1 — Identifier le domaine : repérer les entités, value objects et services qui contiennent la logique métier pure
  • Étape 2 — Extraire les interfaces (ports) : créer AccountPort depuis JpaAccountRepository, créer MoneyTransferUseCase depuis MoneyTransferService
  • Étape 3 — Déplacer les implémentations : JpaAccountRepository devient JpaAccountAdapter implements AccountPort dans le package infrastructure
  • Étape 4 — Inverser les dépendances : supprimer tous les imports infrastructure dans le domaine, vérifier avec ArchUnit
  • Étape 5 — Tester : écrire les tests unitaires du domaine et les tests des use cases avec mock adapters

Avantages vs DDD seul

  • DDD — fournit le modèle de domaine riche, le langage ubiquitaire, les bounded contexts
  • Hexagonale — ajoute l'isolation stricte du domaine, la testabilité maximale, la flexibilité d'infrastructure
  • Les deux se complètent : DDD modélise quoi faire, l'hexagonale organise comment les couches communiquent
  • Résultat : un domaine testé en POJO pur + des adapters remplaçables sans toucher au domaine
