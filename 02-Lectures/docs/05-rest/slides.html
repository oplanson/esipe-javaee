🌐 Principes REST et Richardson Maturity Model

Qu'est-ce que REST ?

REST (Representational State Transfer) est un style architectural défini par Roy Fielding en 2000. Il repose sur les ressources, les représentations et le protocole HTTP comme moteur d'état applicatif.

Level 0 — Plain Old XML / POX

  • HTTP utilisé comme simple protocole de transport
  • Un seul endpoint pour toutes les opérations — ex. POST /api
  • L'opération est décrite dans le corps de la requête
  • Pas de distinction de ressources — comparable à du RPC sur HTTP

Level 1 — Ressources

  • Les ressources sont identifiées par des URIs distinctes
  • Ex. POST /clients, POST /clients/42
  • HTTP toujours utilisé comme simple tunnel — verbes non respectés
  • Amélioration : chaque ressource possède son propre endpoint

Level 2 — Verbes HTTP

  • Utilisation sémantique correcte des verbes HTTP : GET, POST, PUT, DELETE, PATCH
  • Codes de statut HTTP significatifs : 200, 201, 204, 400, 404, 409…
  • Ex. GET /clients, POST /clients, PUT /clients/42, DELETE /clients/42
  • La grande majorité des APIs REST modernes se situent à ce niveau

Level 3 — HATEOAS

  • HATEOAS (Hypermedia As The Engine Of Application State)
  • Les réponses contiennent des liens vers les actions possibles suivantes
  • Le client découvre l'API dynamiquement à travers les hyperliens
  • Ex. : une réponse GET /clients/42 inclut des liens self, update, delete, orders
  • Niveau rarement atteint en pratique — surtout pertinent pour les APIs publiques évolutives
📌 Annotations JAX-RS

@Path — Identification des ressources

  • @Path("/clients") sur la classe — chemin racine de la ressource
  • @Path("/{id}") sur la méthode — sous-chemin avec paramètre de chemin
  • Les paths se composent : /clients/{id}

Verbes HTTP — @GET @POST @PUT @DELETE @PATCH

  • @GET — lecture d'une ressource ou liste (idempotent, sans corps)
  • @POST — création d'une nouvelle ressource (non idempotent)
  • @PUT — remplacement complet d'une ressource existante (idempotent)
  • @DELETE — suppression d'une ressource (idempotent)
  • @PATCH — mise à jour partielle d'une ressource

Paramètres de la requête

  • @PathParam("id") — extrait un segment de l'URI : /clients/{id}
  • @QueryParam("page") — paramètre de requête URL : ?page=2&size=10
  • @HeaderParam("Authorization") — valeur d'un en-tête HTTP
  • @BeanParam — regroupe plusieurs paramètres dans un objet

Négociation de contenu

  • @Produces(MediaType.APPLICATION_JSON) — type MIME de la réponse
  • @Consumes(MediaType.APPLICATION_JSON) — type MIME attendu du corps de requête
  • Valeurs courantes : APPLICATION_JSON, APPLICATION_XML, TEXT_PLAIN

@ApplicationPath — Point d'entrée de l'application

  • Classe étendant jakarta.ws.rs.core.Application annotée @ApplicationPath("/api")
  • Définit le préfixe global de toutes les ressources JAX-RS
  • Peut être vide pour déléguer la configuration au serveur
📦 JSON-B — Sérialisation JSON

JSON-B (Jakarta JSON Binding) est la spécification standard Jakarta EE pour la conversion bidirectionnelle entre objets Java et JSON.

@JsonbProperty — Renommage des champs

  • @JsonbProperty("full_name") sur un champ — le JSON utilisera full_name au lieu du nom Java
  • Utile pour respecter les conventions snake_case des APIs REST

@JsonbTransient — Exclusion de champs

  • @JsonbTransient sur un champ — exclu de la sérialisation et désérialisation JSON
  • Idéal pour les mots de passe, tokens, champs sensibles

@JsonbDateFormat — Format des dates

  • @JsonbDateFormat("yyyy-MM-dd") — contrôle le format de sérialisation des dates
  • Applicable aux champs LocalDate, LocalDateTime, ZonedDateTime

Naming Strategies

  • PropertyNamingStrategy.LOWER_CASE_WITH_UNDERSCORES — conversion automatique camelCase → snake_case
  • PropertyNamingStrategy.UPPER_CAMEL_CASE — PascalCase pour tous les champs
  • Configurable via JsonbConfig ou @JsonbNillable, @JsonbPropertyOrder

Custom Adapters

  • Implémenter JsonbAdapter<Original, Adapted> pour une conversion sur mesure
  • Méthodes adaptToJson() et adaptFromJson()
  • Enregistrement via @JsonbTypeAdapter sur le champ ou via JsonbConfig

Références circulaires

  • Problème courant avec les entités JPA bidirectionnelles (ex. Client ↔ Order)
  • Solution 1 : @JsonbTransient sur le côté propriétaire inverse
  • Solution 2 : utiliser des DTOs sans cycles au lieu des entités directement
  • Solution 3 : adapter personnalisé qui interrompt la récursion
⚠️ Gestion des Exceptions

JAX-RS fournit un mécanisme élégant pour intercepter les exceptions et les convertir en réponses HTTP structurées.

ExceptionMapper<T>

  • Interface JAX-RS à implémenter : ExceptionMapper<MonException>
  • Méthode unique : Response toResponse(MonException exception)
  • Permet de retourner un corps JSON avec le message d'erreur, le code, le champ concerné

@Provider

  • Annotation JAX-RS indiquant au runtime que cette classe est un composant de l'infrastructure
  • Enregistrement automatique des ExceptionMapper, MessageBodyWriter, ContainerFilter…

WebApplicationException

  • Exception JAX-RS de base — encapsule un Response directement
  • Sous-classes prêtes à l'emploi : NotFoundException (404), BadRequestException (400), NotAuthorizedException (401), ForbiddenException (403)
  • Peut être lancée directement depuis une méthode de ressource

Exceptions personnalisées

  • Créer une exception métier ClientNotFoundException extends RuntimeException
  • Créer le mapper correspondant @Provider ClientNotFoundExceptionMapper
  • Découplage total entre logique métier et protocole HTTP

Validation avec Bean Validation

  • @NotNull — le champ ne peut pas être null
  • @Size(min=2, max=100) — contrainte de longueur sur une chaîne ou collection
  • @Email — format d'adresse email valide
  • @Valid sur le paramètre de la méthode JAX-RS pour déclencher la validation
  • Les violations sont reportées via ConstraintViolationException interceptable par un mapper
🔌 MicroProfile Rest Client

MicroProfile Rest Client permet de consommer des APIs REST distantes à travers une interface Java typée — sans code HTTP boilerplate.

@RegisterRestClient

  • Annotation placée sur l'interface — enregistre le client auprès du runtime MicroProfile
  • configKey — clé de configuration pour l'URL de base dans microprofile-config.properties
  • Ex. : @RegisterRestClient(configKey="currency-api")

Interface @Path annotée

  • L'interface utilise les mêmes annotations JAX-RS que les ressources serveur : @Path, @GET, @POST, @PathParam, @QueryParam, @Produces, @Consumes
  • Aucune implémentation à écrire — le runtime génère le proxy automatiquement

@Inject @RestClient

  • Injection CDI du client avec le qualificateur @RestClient
  • Le runtime injecte le proxy généré — utilisation identique à une dépendance locale

Configuration dans microprofile-config.properties

  • currency-api/mp-rest/url=https://api.exchangerate.host
  • currency-api/mp-rest/connectTimeout=3000
  • currency-api/mp-rest/readTimeout=5000
  • currency-api/mp-rest/scope=jakarta.enterprise.context.ApplicationScoped

ResponseExceptionMapper — Gestion des erreurs distantes

  • Implémenter ResponseExceptionMapper<RuntimeException> pour transformer les réponses erreur en exceptions Java
  • Méthode toThrowable(Response response) — inspekte le statut et retourne l'exception appropriée
  • Enregistrement avec @RegisterProvider(MonExceptionMapper.class) sur l'interface cliente
🔗 Intégration REST + CDI

JAX-RS et CDI s'intègrent nativement dans Jakarta EE — les ressources JAX-RS sont des beans CDI à part entière.

Service CDI @ApplicationScoped dans une ressource REST

  • Injection directe par @Inject dans la classe ressource JAX-RS
  • La ressource peut elle-même porter un scope CDI (@RequestScoped, @ApplicationScoped)
  • Meilleure pratique : scope @RequestScoped pour les ressources JAX-RS

Intercepteur CDI sur les ressources REST

  • Les intercepteurs CDI (@Logged, @Audited…) s'appliquent aussi sur les méthodes JAX-RS
  • Permet d'ajouter du logging, de la sécurité ou du métriques sans modifier le code de ressource

CDI Events déclenchés par des opérations REST

  • Injecter Event<ClientCreatedEvent> dans la ressource JAX-RS
  • Déclencher l'événement après une opération réussie (création, mise à jour, suppression)
  • Les observateurs CDI réagissent de façon découplée : notifications, audit, cache invalidation

CDI Qualifiers avec Rest Clients

  • Plusieurs implémentations de la même interface cliente peuvent être distinguées par des qualificateurs CDI
  • Ex. : @Production et @Staging clients configurés sur des URLs différentes
  • Combinaison de @RegisterRestClient + qualificateur CDI sur l'interface
📖 OpenAPI et Documentation

MicroProfile OpenAPI génère automatiquement une documentation /openapi (format YAML/JSON) à partir des annotations Java.

@OpenAPIDefinition — Métadonnées globales

  • Placée sur la classe Application ou une classe de configuration
  • Définit info (titre, version, description), servers, tags, security

@Operation — Documentation d'un endpoint

  • summary — résumé court de l'opération
  • description — description longue détaillée
  • operationId — identifiant unique utilisé par les générateurs de clients
  • tags — regroupement logique dans l'UI Swagger

@APIResponse — Documentation des réponses

  • responseCode — code HTTP de la réponse documentée
  • description — explication du cas de réponse
  • content — schéma du corps de réponse avec @Content et @Schema

@Schema — Structure des DTOs

  • Placé sur les classes DTO et leurs champs
  • description, example, required, minimum, maximum
  • Enrichit la documentation générée avec des exemples concrets

@Parameter — Documentation des paramètres

  • Documente les @PathParam, @QueryParam, @HeaderParam
  • in (path/query/header), required, description, schema

Endpoint /openapi

  • Disponible automatiquement sur GET /openapi (YAML) ou GET /openapi?format=JSON
  • Interface Swagger UI souvent accessible sur /swagger-ui selon le runtime
🔢 Codes HTTP et bonnes pratiques

Le choix du code de statut HTTP est fondamental pour une API REST sémantiquement correcte et prévisible.

Codes de succès

  • 200 OK — succès générique pour GET, PUT, PATCH avec corps de réponse
  • 201 Created — ressource créée avec succès (POST) — inclure l'en-tête Location avec l'URI de la ressource créée
  • 204 No Content — succès sans corps de réponse (DELETE, PUT sans retour)

Codes d'erreur client (4xx)

  • 400 Bad Request — requête malformée, validation échouée, données invalides
  • 401 Unauthorized — authentification requise ou token invalide/expiré
  • 403 Forbidden — authentifié mais sans les droits nécessaires
  • 404 Not Found — ressource demandée inexistante
  • 409 Conflict — conflit d'état : doublon, version obsolète (optimistic lock), état incompatible

Codes d'erreur serveur (5xx)

  • 500 Internal Server Error — erreur interne non gérée — ne jamais exposer les stack traces

Bonnes pratiques REST

  • ✅ Utiliser des noms de ressources au pluriel : /clients et non /client
  • ✅ Toujours retourner l'en-tête Location après un POST 201
  • ✅ Inclure un corps d'erreur JSON structuré pour les 4xx et 5xx
  • ✅ Versionner les APIs : /api/v1/clients ou via Accept Header
  • ✅ Ne jamais retourner 200 avec un corps d'erreur — antipattern courant
