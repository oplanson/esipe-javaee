🏗️ EJB Architecture and Container Services

What is an EJB?

Enterprise Java Beans are server-side components managed by the EJB container of a Jakarta EE application server. They encapsulate business logic and delegate cross-cutting concerns (transactions, security, lifecycle) to the container.

EJB bean types

  • Stateless Session — no state between calls, automatic pooling, high performance
  • Stateful Session — preserves conversational state per client, passivation possible
  • Singleton Session — a single shared instance throughout the application
  • Message-Driven Bean (MDB) — asynchronous processing of JMS messages

Services provided by the container

  • ✅ Pooling — automatic management of an instance pool for Stateless beans
  • ✅ Security — declarative access control via annotations (@RolesAllowed, @DenyAll)
  • ✅ Transactions — automatic CMT management or programmatic BMT
  • ✅ Timers — task scheduling with the Timer Service
  • ✅ Interception — interceptors around method invocations
  • ✅ Injection — dependency injection via @EJB and @Inject
  • ✅ Remote access — @Remote interfaces for cross-JVM calls
🔵 Stateless Session Beans

Characteristics

A Stateless Session Bean annotated @Stateless preserves no conversational state between two client calls. Each method is an autonomous, independent operation.

  • The container maintains an instance pool — reused between requests
  • Very high performance and scalability — the most used bean type in practice
  • Thread-safe by nature — the container guarantees a single thread uses one instance at a time
  • Dependency injection via @EJB for other EJBs or @Inject for CDI beans

Typical use cases

  • Stateless business services: payment, validation, calculation
  • Facades to the persistence layer (DAO Pattern)
  • Notification or email sending services
  • REST backend services (injection into JAX-RS resources)

Lifecycle

  • @PostConstruct — called after injection, when entering the pool
  • @PreDestroy — called when removed from the pool and the instance is destroyed
🔶 Stateful Session Beans

Characteristics

A Stateful Session Bean annotated @Stateful maintains a conversational state specific to each client. The instance is dedicated to a single client for the entire duration of the conversation.

  • State (instance fields) is preserved between successive calls from the same client
  • No pool — one instance per active client conversation
  • Must implement java.io.Serializable to allow passivation

Extended lifecycle management

  • @Remove — marks a method that releases the instance after its call (end of conversation)
  • @PrePassivate — called before passivation (disk save) by the container
  • @PostActivate — called after reactivation (reload from disk)
  • Passivation allows the container to free RAM by serialising inactive beans

Typical use cases

  • E-commerce shopping cart — accumulating items across multiple requests
  • Multi-step wizards — multi-page forms with intermediate state
  • Collaborative work sessions — document editing state
⬛ Singleton Session Beans

Characteristics

A Singleton Session Bean annotated @Singleton guarantees that only one instance of this bean exists in the entire application. Shared by all clients, it requires explicit concurrency management.

  • A single instance created and shared by the entire container
  • Initialised at application startup if annotated @Startup
  • State persists for the entire lifetime of the application

Concurrency management

  • @ConcurrencyManagement(CONTAINER) — the container manages locks automatically (default)
  • @ConcurrencyManagement(BEAN) — the developer manages synchronisation manually
  • @Lock(READ) — concurrent read access allowed for multiple simultaneous threads
  • @Lock(WRITE) — exclusive access, one thread at a time (default on methods)
  • @AccessTimeout — maximum wait time for acquiring a lock

Startup initialisation

  • @Startup — forces Singleton initialisation at server startup
  • — declares an ordered initialisation dependency" data-fr="@DependsOn(\"AutreBean\") — déclare une dépendance d'initialisation ordonnée">@DependsOn("OtherBean") — declares an ordered initialisation dependency
  • Useful for pre-loading caches, reading configurations, initialising connections
📨 Message-Driven Beans

Characteristics

A Message-Driven Bean (MDB) annotated @MessageDriven enables asynchronous processing of JMS messages (Jakarta Messaging). It is triggered by the arrival of a message in a queue or topic.

  • Implements the jakarta.jms.MessageListener interface with the onMessage(Message) method
  • Fully asynchronous — the sending client does not wait for a response
  • Automatic instance pooling managed by the container
  • CMT transactions applicable on the onMessage() method

Configuration via @ActivationConfigProperty

  • destinationType — jakarta.jms.Queue or jakarta.jms.Topic
  • destinationLookup — JNDI name of the JMS destination
  • messageSelector — SQL-like filter on message properties
  • acknowledgeMode — acknowledgement mode (Auto-acknowledge, Dups-ok-acknowledge)

Typical use cases

  • Asynchronous banking request processing (wire transfers, payments)
  • Sending notifications (email, SMS) in the background
  • Integration of heterogeneous systems via message broker
  • Batch processing decoupled from the user interface
💳 CMT and BMT Transactions

CMT — Container-Managed Transactions (default)

With CMT, the container automatically manages the transaction lifecycle. The developer declares behaviour via @TransactionAttribute.

  • REQUIRED — participates in existing transaction or creates a new one (default)
  • REQUIRES_NEW — suspends the current transaction, creates an independent one
  • MANDATORY — requires an active transaction, throws an exception otherwise
  • NOT_SUPPORTED — suspends any active transaction, executes without a transaction
  • SUPPORTS — uses the current transaction if one exists, otherwise without a transaction
  • NEVER — throws an exception if a transaction is active

Rollback in CMT

  • Automatic on any uncaught RuntimeException
  • Programmatic via EJBContext.setRollbackOnly()
  • Fine-grained control via @ApplicationException(rollback=true) for checked exceptions

BMT — Bean-Managed Transactions

With BMT (@TransactionManagement(BEAN)), the developer manually manages transactions via the UserTransaction API.

  • Inject @Resource UserTransaction utx or obtain via EJBContext
  • Explicitly call utx.begin(), utx.commit(), utx.rollback()
  • Total control — suited for saga patterns, long transactions, conditional logic
🔐 EJB Security

Declarative security

The EJB container enforces role-based access controls before invoking the bean's methods.

  • — allows only the listed roles" data-fr="@RolesAllowed({\"ADMIN\", \"EMPLOYEE\"}) — autorise uniquement les rôles listés">@RolesAllowed({"ADMIN", "EMPLOYEE"}) — allows only the listed roles
  • @PermitAll — allows all authenticated or anonymous callers
  • @DenyAll — denies all calls (method inaccessible in production)
  • — executes the bean under a different role (privilege escalation)" data-fr="@RunAs(\"SYSTEM\") — exécute le bean sous un rôle différent (élévation de privilèges)">@RunAs("SYSTEM") — executes the bean under a different role (privilege escalation)

Applying annotations

  • On the class — applies to all methods of the class
  • On the method — overrides the class declaration for that specific method

  • — dynamically checks if the caller has a role" data-fr="EJBContext.isCallerInRole(\"ADMIN\") — vérifie dynamiquement si l'appelant possède un rôle">EJBContext.isCallerInRole("ADMIN") — dynamically checks if the caller has a role
  • EJBContext.getCallerPrincipal() — gets the Principal representing the current user
  • Useful for fine-grained conditional logic based on caller identity
⏰ Timer Service and Asynchronous Methods

Timer Service — scheduled tasks

The EJB Timer Service allows methods to be triggered at regular intervals or at specific times, managed entirely by the container.

  • — automatic triggering via a cron expression" data-fr="@Schedule(hour=\"0\", minute=\"0\", second=\"0\", persistent=true) — déclenchement automatique selon une expression cron">@Schedule(hour="0", minute="0", second="0", persistent=true) — automatic triggering via a cron expression
  • @Schedules({@Schedule(...), @Schedule(...)}) — multiple schedules on the same method
  • @Timeout — callback method invoked when a programmatic timer expires
  • Attributes of @Schedule: second, minute, hour, dayOfWeek, dayOfMonth, month, year
  • persistent=true — the timer survives server restarts (stored in the database)

Programmatic timers

  • Inject @Resource TimerService timerService
  • timerService.createTimer(delay, interval, info) — repeating interval timer
  • timerService.createSingleActionTimer(delay, config) — single-fire timer
  • The @Timeout method receives a Timer object with metadata

@Asynchronous — non-blocking methods

  • @Asynchronous on an EJB method — the call returns immediately to the client
  • Return type void or Future<T> / CompletableFuture<T>
  • The container executes the method in a separate thread from the pool
  • Ideal for long decoupled tasks: email sending, report generation, data import
🔄 EJB vs CDI — Migration to Modern Jakarta EE

Context: EJB deprecation in Jakarta EE 11+

In modern Jakarta EE 11+, EJBs are deprecated in favour of CDI Beans + MicroProfile. EJBs remain supported for backward compatibility, but new projects should use CDI @ApplicationScoped + @Transactional (Jakarta Transactions).

EJB to CDI migration table

EJB (legacy) CDI Modern equivalent Notes
@Stateless @ApplicationScoped No per-request state; CDI bean is the standard choice for stateless services
@Stateful @SessionScoped Conversational state stored in CDI session scope; requires Serializable
@EJB @Inject Standard CDI injection; works for any bean type
Container-managed transactions (CMT) @Transactional Jakarta Transactions interceptor; same semantics as CMT @TransactionAttribute
@MessageDriven MicroProfile Reactive Messaging @Incoming / @Outgoing on CDI beans; works with Kafka, AMQP, JMS
Timer Service (@Schedule) MicroProfile Metrics + Quartz / custom CDI producer No direct CDI equivalent; use Quartz, Spring Scheduling, or a JEE Timer via CDI wrapper

When to still use EJBs

  • Maintaining legacy applications that already use EJBs extensively
  • Requirements for distributed transactions across multiple resources (XA)
  • Remote EJB calls across JVMs in a tightly coupled cluster
  • EJB Timer Service with persistence requirement and no external scheduler available
