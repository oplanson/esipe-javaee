🏗️ Architecture EJB et Services du Conteneur

Qu'est-ce qu'un EJB ?

Les Enterprise Java Beans sont des composants serveur gérés par le conteneur EJB du serveur d'applications Jakarta EE. Ils encapsulent la logique métier et délèguent les préoccupations transversales (transactions, sécurité, cycle de vie) au conteneur.

Types de beans EJB

  • Session Stateless — pas d'état entre les appels, pooling automatique, haute performance
  • Session Stateful — conserve l'état conversationnel par client, passivation possible
  • Session Singleton — une seule instance partagée dans toute l'application
  • Message-Driven Bean (MDB) — traitement asynchrone de messages JMS

Services fournis par le conteneur

  • ✅ Pooling — gestion automatique d'un pool d'instances pour les beans Stateless
  • ✅ Sécurité — contrôle d'accès déclaratif via annotations (@RolesAllowed, @DenyAll)
  • ✅ Transactions — gestion automatique CMT ou programmatique BMT
  • ✅ Timers — planification de tâches avec le Timer Service
  • ✅ Interception — intercepteurs autour des invocations de méthodes
  • ✅ Injection — injection de dépendances via @EJB et @Inject
  • ✅ Accès distant — interfaces @Remote pour appels inter-JVM
🔵 Stateless Session Beans

Caractéristiques

Un Stateless Session Bean annoté @Stateless ne conserve aucun état conversationnel entre deux appels clients. Chaque méthode est une opération autonome et indépendante.

  • Le conteneur maintient un pool d'instances — réutilisées entre les requêtes
  • Très haute performance et scalabilité — bean le plus utilisé en pratique
  • Thread-safe par nature — le conteneur garantit qu'une instance n'est utilisée que par un seul thread à la fois
  • Injection de dépendances via @EJB pour d'autres EJBs ou @Inject pour les beans CDI

Cas d'usage typiques

  • Services métier sans état : paiement, validation, calcul
  • Façades vers la couche de persistance (DAO Pattern)
  • Services d'envoi de notifications, d'emails
  • Services REST backends (injection dans les ressources JAX-RS)

Cycle de vie

  • @PostConstruct — appelé après l'injection, lors de l'entrée dans le pool
  • @PreDestroy — appelé lors du retrait du pool et de la destruction de l'instance
🔶 Stateful Session Beans

Caractéristiques

Un Stateful Session Bean annoté @Stateful maintient un état conversationnel propre à chaque client. L'instance est dédiée à un seul client pendant toute la durée de la conversation.

  • L'état (champs de l'instance) est conservé entre les appels successifs du même client
  • Pas de pool — une instance par conversation client active
  • Doit implémenter java.io.Serializable pour permettre la passivation

Gestion du cycle de vie étendu

  • @Remove — marque une méthode qui libère l'instance après son appel (fin de conversation)
  • @PrePassivate — appelé avant la passivation (sauvegarde sur disque) par le conteneur
  • @PostActivate — appelé après la réactivation (rechargement depuis disque)
  • La passivation permet au conteneur de libérer de la mémoire RAM en sérialisant les beans inactifs

Cas d'usage typiques

  • Panier d'achat e-commerce — accumulation d'articles sur plusieurs requêtes
  • Wizards multi-étapes — formulaires en plusieurs étapes avec état intermédiaire
  • Sessions de travail collaboratif — état d'édition d'un document
⬛ Singleton Session Beans

Caractéristiques

Un Singleton Session Bean annoté @Singleton garantit qu'il n'existe qu'une seule instance de ce bean dans toute l'application. Partagée par tous les clients, elle nécessite une gestion explicite de la concurrence.

  • Une seule instance créée et partagée par tout le conteneur
  • Initialisée au démarrage de l'application si annotée @Startup
  • Persistance de l'état pendant toute la durée de vie de l'application

Gestion de la concurrence

  • @ConcurrencyManagement(CONTAINER) — le conteneur gère les verrous automatiquement (défaut)
  • @ConcurrencyManagement(BEAN) — le développeur gère la synchronisation manuellement
  • @Lock(READ) — accès concurrent en lecture autorisé pour plusieurs threads simultanés
  • @Lock(WRITE) — accès exclusif, un seul thread à la fois (défaut sur les méthodes)
  • @AccessTimeout — durée maximale d'attente pour l'obtention d'un verrou

Initialisation au démarrage

  • @Startup — force l'initialisation du Singleton au démarrage du serveur
  • @DependsOn("AutreBean") — déclare une dépendance d'initialisation ordonnée
  • Utile pour pré-charger des caches, lire des configurations, initialiser des connexions
📨 Message-Driven Beans

Caractéristiques

Un Message-Driven Bean (MDB) annoté @MessageDriven permet le traitement asynchrone de messages JMS (Jakarta Messaging). Il est déclenché par l'arrivée d'un message dans une queue ou un topic.

  • Implémente l'interface jakarta.jms.MessageListener avec la méthode onMessage(Message)
  • Entièrement asynchrone — le client émetteur n'attend pas la réponse
  • Pooling automatique d'instances géré par le conteneur
  • Transactions CMT applicables sur la méthode onMessage()

Configuration via @ActivationConfigProperty

  • destinationType — jakarta.jms.Queue ou jakarta.jms.Topic
  • destinationLookup — nom JNDI de la destination JMS
  • messageSelector — filtre SQL-like sur les propriétés du message
  • acknowledgeMode — mode d'acquittement (Auto-acknowledge, Dups-ok-acknowledge)

Cas d'usage typiques

  • Traitement de demandes bancaires asynchrones (virements, paiements)
  • Envoi de notifications (email, SMS) en arrière-plan
  • Intégration de systèmes hétérogènes via message broker
  • Traitement batch découplé de l'interface utilisateur
💳 Transactions CMT et BMT

CMT — Container-Managed Transactions (défaut)

Avec CMT, le conteneur gère automatiquement le cycle de vie des transactions. Le développeur déclare le comportement via @TransactionAttribute.

  • REQUIRED — participe à la transaction existante ou en crée une nouvelle (défaut)
  • REQUIRES_NEW — suspend la transaction courante, crée une transaction indépendante
  • MANDATORY — exige une transaction active, lance une exception sinon
  • NOT_SUPPORTED — suspend toute transaction active, s'exécute sans transaction
  • SUPPORTS — utilise la transaction courante si elle existe, sinon sans transaction
  • NEVER — lève une exception si une transaction est active

Rollback en CMT

  • Automatique sur toute RuntimeException non catchée
  • Programmatique via EJBContext.setRollbackOnly()
  • Contrôle fin via @ApplicationException(rollback=true) pour les checked exceptions

BMT — Bean-Managed Transactions

Avec BMT (@TransactionManagement(BEAN)), le développeur gère manuellement les transactions via l'API UserTransaction.

  • Injecter @Resource UserTransaction utx ou obtenir via EJBContext
  • Appeler explicitement utx.begin(), utx.commit(), utx.rollback()
  • Contrôle total — adapté aux patterns saga, transactions longues, logique conditionnelle
🔐 Sécurité EJB

Sécurité déclarative

Le conteneur EJB applique des contrôles d'accès basés sur les rôles avant d'invoquer les méthodes du bean.

  • @RolesAllowed({"ADMIN", "EMPLOYEE"}) — autorise uniquement les rôles listés
  • @PermitAll — autorise tous les appelants authentifiés ou anonymes
  • @DenyAll — refuse tous les appels (méthode inaccessible en production)
  • @RunAs("SYSTEM") — exécute le bean sous un rôle différent (élévation de privilèges)

Application des annotations

  • Sur la classe — s'applique à toutes les méthodes de la classe
  • Sur la méthode — surcharge la déclaration de classe pour cette méthode précise
  • Combinaison possible : classe avec @RolesAllowed("EMPLOYEE"), méthode avec @RolesAllowed("ADMIN")

Sécurité programmatique

  • EJBContext.isCallerInRole("ADMIN") — vérifie dynamiquement si l'appelant possède un rôle
  • EJBContext.getCallerPrincipal() — obtient le Principal représentant l'utilisateur courant
  • Utile pour des logiques conditionnelles fines selon l'identité de l'appelant
⏰ Timer Service et Méthodes Asynchrones

Timer Service — tâches planifiées

Le Timer Service EJB permet de déclencher des méthodes à intervalles réguliers ou à des moments précis, géré entièrement par le conteneur.

  • @Schedule(hour="0", minute="0", second="0", persistent=true) — déclenchement automatique selon une expression cron
  • @Schedules({@Schedule(...), @Schedule(...)}) — plusieurs planifications sur une même méthode
  • @Timeout — méthode callback appelée lors de l'expiration d'un timer programmatique
  • Attributs de @Schedule : second, minute, hour, dayOfWeek, dayOfMonth, month, year
  • persistent=true — le timer survit aux redémarrages du serveur (stocké en base)

Timers programmatiques

  • Injecter @Resource TimerService timerService
  • timerService.createTimer(delay, interval, info) — timer à intervalles répétitifs
  • timerService.createSingleActionTimer(delay, config) — timer à déclenchement unique
  • La méthode @Timeout reçoit un objet Timer avec les métadonnées

@Asynchronous — méthodes non bloquantes

  • @Asynchronous sur une méthode EJB — l'appel retourne immédiatement au client
  • Type de retour void ou Future<T> / CompletableFuture<T>
  • Le conteneur exécute la méthode dans un thread séparé du pool
  • Idéal pour les traitements longs découplés : envoi email, génération de rapports, import de données
