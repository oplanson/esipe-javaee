Patterns Microservices

Patterns architecturaux essentiels pour systèmes distribués.

API Gateway

L'API Gateway est le point d'entrée unique (single entry point) pour tous les clients externes. Elle masque la complexité interne de l'architecture microservices : les clients ne connaissent ni l'adresse, ni l'existence des services individuels.

Cas d'usage : Toute architecture microservices exposée à des clients externes (web, mobile, tiers). La Gateway est systématiquement présente en production.

Responsabilités : routing, authentification & autorisation JWT/OAuth2, rate limiting, SSL termination, logging centralisé, agrégation de réponses (BFF).

Bénéfices : les clients n'ont qu'une seule URL à connaître ; les services internes peuvent évoluer librement sans impact sur les clients.

Risques : single point of failure si non répliqué ; bottleneck potentiel sous forte charge si l'agrégation est lourde.

java 
// Routing dans la Gateway — annotation JAX-RS standard
@Path("/api")
@ApplicationScoped
public class GatewayResource {

    @Inject @RestClient AccountServiceClient accountClient;

    @GET @Path("/accounts/{id}")
    public Response routeToAccountService(@PathParam("id") Long id) {
        return Response.ok(accountClient.getAccount(id)).build();
    }
}

Circuit Breaker

Le Circuit Breaker est un pattern de résilience inspiré des disjoncteurs électriques. Lorsqu'un service distant tombe en panne ou répond trop lentement, le Circuit Breaker détecte la défaillance et interrompt les appels pour éviter l'effet de cascade (cascading failure) qui pourrait paralyser tout le système.

Cas d'usage : Tout appel synchrone inter-services en production, particulièrement sur les chemins critiques.

@CircuitBreaker(
    requestVolumeThreshold = 4,     // évalue après 4 requêtes min
    failureRatio           = 0.75,  // ouvre si 75% d'échecs
    delay                  = 2000,  // reste OPEN 2 secondes
    successThreshold       = 2      // 2 succès en HALF-OPEN pour refermer
)
@Fallback(fallbackMethod = "getAccountFallback")
public Account getAccount(Long id) {
    return accountClient.getAccount(id);
}

Database par Service

Le pattern Database per Service stipule que chaque microservice est seul propriétaire de sa base de données. Aucun autre service ne peut accéder directement aux données d'un autre — uniquement via son API exposée. Ce pattern est un prérequis de l'indépendance réelle des services.

Cas d'usage : Systématiquement dans une architecture microservices correctement conçue. Sans ce pattern, une base partagée recrée du couplage structurel entre les services.

AvantagesInconvénients
✅ Indépendance totale — chaque service choisit sa technologie de stockage⚠️ Pas de JOIN SQL natif entre services — requêtes croisées via API
✅ Schéma de données évolutif sans coordination avec les autres équipes⚠️ Eventual consistency — données potentiellement divergentes entre services
✅ Scalabilité indépendante de la couche données⚠️ Duplication partielle des données dans les read models (CQRS)
✅ Isolation des pannes — panne d'une DB n'impacte qu'un service⚠️ Saga nécessaire pour les transactions distribuées multi-services

L'eventual consistency est le corollaire inévitable de ce pattern : entre deux services, la cohérence n'est pas immédiate mais garantie à terme via la propagation d'événements.

Pattern Saga

Le Pattern Saga résout le problème des transactions distribuées dans une architecture microservices. Puisqu'il n'y a pas de transaction ACID globale possible à travers plusieurs bases de données, la Saga découpe l'opération en une séquence de transactions locales. Si une étape échoue, des transactions compensatoires annulent les étapes déjà validées.

Variantes : Choreography — pas de coordinateur, les services réagissent aux événements des autres ; Orchestration — un coordinateur central pilote les étapes et les compensations.

Cas d'usage : Toute opération métier touchant plusieurs services (ex. virement bancaire : débit + crédit + notification).

Transactions compensatoires : chaque étape validée doit disposer d'une opération inverse. Exemple : si le crédit du compte destinataire échoue après que le débit ait été réalisé, le service émet un DebitCompensatedEvent qui déclenche le remboursement du montant débité.

java 
// Déclenchement du Saga — Transfer Service
public void initiateTransfer(String id, String from, String to, double amount) {
    transferRepository.save(new Transfer(id, from, to, amount, "INITIATED"));
    // Choreography : on publie un événement et on laisse les services réagir
    debitEvent.fire(new AccountDebitedEvent(id, from, amount));
}

// Transaction compensatoire — Account Service
public void onDebitFailed(@Observes DebitFailedEvent event) {
    // Annule le débit si le crédit a échoué
    accountRepository.credit(event.fromAccount(), event.amount()); // remboursement
    compensatedEvent.fire(new DebitCompensatedEvent(event.transferId()));
}

CQRS et Event Sourcing

CQRS (Command Query Responsibility Segregation) sépare le modèle d'écriture (Commands) du modèle de lecture (Queries). Le modèle de commandes garantit la cohérence transactionnelle ; le modèle de requêtes est optimisé pour les lectures complexes et les performances. Les deux modèles sont synchronisés de façon asynchrone via des événements.

Event Sourcing pousse ce principe plus loin : l'état d'une entité n'est jamais stocké directement. Au lieu de cela, chaque changement d'état est persisé comme un événement immuable dans un Event Store. L'état courant est recalculé en rejouant tous les événements depuis le début.

Cas d'usage : Domaines avec besoin d'audit trail complet (finance, santé), scalabilité en lecture, besoins de vues multiples sur les mêmes données.

Avantages combinés CQRS + Event Sourcing :

  • ✅ Audit trail complet — chaque changement d'état est enregistré avec son contexte et sa date
  • ✅ Replay des événements — possibilité de reconstruire l'état à n'importe quel instant passé
  • ✅ Vues multiples — plusieurs projections (read models) peuvent être créées depuis le même flux d'événements
  • ✅ Scalabilité en lecture — les read models peuvent être répliqués et mis en cache indépendamment
  • ⚠️ Complexité accrue — eventual consistency entre write et read model, schema evolution des événements
java 
// Command — intention métier (écriture)
public record DebitAccountCommand(String accountId, double amount, String transferId) {}

// Event — fait passé immuable
public record MoneyDebitedEvent(String accountId, double amount,
                                String transferId, Instant occurredAt) {}

// Aggregate — reconstruit l'état depuis les événements
@ApplicationScoped
public class AccountAggregate {

    // Applique un événement au write model
    public Account applyDebit(Account current, MoneyDebitedEvent event) {
        return new Account(
            current.id(),
            current.iban(),
            current.balance() - event.amount(), // déduction
            current.ownerId()
        );
    }

    // Rejoue tous les événements pour reconstruire l'état courant
    public Account rebuildFromHistory(List<Object> events) {
        Account account = new Account(null, null, 0.0, null);
        for (Object event : events) {
            account = switch (event) {
                case AccountOpenedEvent e -> applyOpen(account, e);
                case MoneyDepositedEvent e -> applyDeposit(account, e);
                case MoneyDebitedEvent e   -> applyDebit(account, e);
                default -> account;
            };
        }
        return account;
    }
}

// Projection — read model optimisé pour les requêtes
@ApplicationScoped
public class AccountSummaryProjection {

    @Inject
    private AccountSummaryRepository readRepository;

    // Mise à jour asynchrone du read model quand un événement arrive
    public void on(@Observes MoneyDebitedEvent event) {
        AccountSummary summary = readRepository.findById(event.accountId());
        summary.setBalance(summary.getBalance() - event.amount());
        summary.setLastTransactionAt(event.occurredAt());
        readRepository.save(summary);
    }
}
