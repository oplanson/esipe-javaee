Microservices Patterns

Essential architectural patterns for distributed systems.

API Gateway

The API Gateway is the single entry point for all external clients. It hides the internal complexity of the microservices architecture: clients know neither the address nor the existence of individual services.

Use case: Any microservices architecture exposed to external clients (web, mobile, third-party). The Gateway is always present in production.

Responsibilities: routing, JWT/OAuth2 authentication & authorization, rate limiting, SSL termination, centralized logging, response aggregation (BFF).

Benefits: clients only need to know one URL; internal services can evolve freely without impact on clients.

Risks: single point of failure if not replicated; potential bottleneck under heavy load if aggregation is heavy.

java 
// Routing dans la Gateway — annotation JAX-RS standard
@Path("/api")
@ApplicationScoped
public class GatewayResource {

    @Inject @RestClient AccountServiceClient accountClient;

    @GET @Path("/accounts/{id}")
    public Response routeToAccountService(@PathParam("id") Long id) {
        return Response.ok(accountClient.getAccount(id)).build();
    }
}

Circuit Breaker

The Circuit Breaker is a resilience pattern inspired by electrical circuit breakers. When a remote service goes down or responds too slowly, the Circuit Breaker detects the failure and interrupts calls to prevent the cascading failure that could paralyse the whole system.

Use case: Any synchronous inter-service call in production, particularly on critical paths.

java 
@CircuitBreaker(
    requestVolumeThreshold = 4,     // évalue après 4 requêtes min
    failureRatio           = 0.75,  // ouvre si 75% d'échecs
    delay                  = 2000,  // reste OPEN 2 secondes
    successThreshold       = 2      // 2 succès en HALF-OPEN pour refermer
)
@Fallback(fallbackMethod = "getAccountFallback")
public Account getAccount(Long id) {
    return accountClient.getAccount(id);
}

Database per Service

The pattern Database per Service stipulates that each microservice is the sole owner of its database. No other service can directly access another's data — only via its exposed API. This pattern is a prerequisite for real service independence.

Use case: Systematically in a correctly designed microservices architecture. Without this pattern, a shared database recreates structural coupling between services.

AdvantagesDrawbacks
✅ Full independence — each service chooses its storage technology⚠️ No native SQL JOIN between services — cross-service queries via API
✅ Evolving data schema without coordination with other teams⚠️ Eventual consistency — potentially divergent data between services
✅ Independent scalability of the data layer⚠️ Partial data duplication in read models (CQRS)
✅ Failure isolation — a DB failure only impacts one service⚠️ Saga required for distributed multi-service transactions

The eventual consistency is the inevitable corollary of this pattern: between two services, consistency is not immediate but guaranteed in time via event propagation.

Saga Pattern

The Saga Pattern solves the problem of distributed transactions in a microservices architecture. Since there is no possible global ACID transaction across multiple databases, the Saga breaks the operation into a sequence of local transactions. If a step fails, compensatory transactions cancel the already validated steps.

Variants: Choreography — no coordinator, services react to each other's events; Orchestration — a central coordinator drives the steps and compensations.

Use case: Any business operation touching multiple services (e.g. bank transfer: debit + credit + notification).

Compensatory transactions: each validated step must have an inverse operation. Example: if the credit of the target account fails after the debit was performed, the service emits a DebitCompensatedEvent that triggers the refund of the debited amount.

java 
// Déclenchement du Saga — Transfer Service
public void initiateTransfer(String id, String from, String to, double amount) {
    transferRepository.save(new Transfer(id, from, to, amount, "INITIATED"));
    // Choreography : on publie un événement et on laisse les services réagir
    debitEvent.fire(new AccountDebitedEvent(id, from, amount));
}

// Transaction compensatoire — Account Service
public void onDebitFailed(@Observes DebitFailedEvent event) {
    // Annule le débit si le crédit a échoué
    accountRepository.credit(event.fromAccount(), event.amount()); // remboursement
    compensatedEvent.fire(new DebitCompensatedEvent(event.transferId()));
}

CQRS and Event Sourcing

CQRS (Command Query Responsibility Segregation) separates the write model (Commands) from the read model (Queries). The command model guarantees transactional consistency; the query model is optimised for complex reads and performance. Both models are synchronised asynchronously via events.

Event Sourcing pushes this principle further: the state of an entity is never stored directly. Instead, each state change is persisted as an immutable event in an Event Store. The current state is recalculated by replaying all events from the beginning.

Use case: Domains requiring a complete audit trail (finance, health), read scalability, needs for multiple views of the same data.

Combined CQRS + Event Sourcing advantages:

  • ✅ Complete audit trail — every state change is recorded with its context and date
  • ✅ Event replay — ability to reconstruct state at any past point in time
  • ✅ Multiple views — several projections (read models) can be created from the same event stream
  • ✅ Read scalability — read models can be replicated and cached independently
  • ⚠️ Increased complexity — eventual consistency between write and read model, event schema evolution
java 
// Command — intention métier (écriture)
public record DebitAccountCommand(String accountId, double amount, String transferId) {}

// Event — fait passé immuable
public record MoneyDebitedEvent(String accountId, double amount,
                                String transferId, Instant occurredAt) {}

// Aggregate — reconstruit l'état depuis les événements
@ApplicationScoped
public class AccountAggregate {

    // Applique un événement au write model
    public Account applyDebit(Account current, MoneyDebitedEvent event) {
        return new Account(
            current.id(),
            current.iban(),
            current.balance() - event.amount(), // déduction
            current.ownerId()
        );
    }

    // Rejoue tous les événements pour reconstruire l'état courant
    public Account rebuildFromHistory(List<Object> events) {
        Account account = new Account(null, null, 0.0, null);
        for (Object event : events) {
            account = switch (event) {
                case AccountOpenedEvent e -> applyOpen(account, e);
                case MoneyDepositedEvent e -> applyDeposit(account, e);
                case MoneyDebitedEvent e   -> applyDebit(account, e);
                default -> account;
            };
        }
        return account;
    }
}

// Projection — read model optimisé pour les requêtes
@ApplicationScoped
public class AccountSummaryProjection {

    @Inject
    private AccountSummaryRepository readRepository;

    // Mise à jour asynchrone du read model quand un événement arrive
    public void on(@Observes MoneyDebitedEvent event) {
        AccountSummary summary = readRepository.findById(event.accountId());
        summary.setBalance(summary.getBalance() - event.amount());
        summary.setLastTransactionAt(event.occurredAt());
        readRepository.save(summary);
    }
}
