🏗️ What are Microservices?

Definition

Microservices are an architectural style in which an application is split into small, independent services, each with a single, clearly delimited responsibility. Each service is independently deployable, communicates via lightweight interfaces (HTTP/REST or asynchronous messaging) and can be developed, updated and scaled autonomously.

Fundamental Characteristics

  • Single Responsibility — each service focuses on a precise business domain (Single Responsibility Principle extended to architecture)
  • Independent Deployment — a service can be put into production without touching the others
  • Database per Service — each service is the sole owner of its data (Database per Service pattern)
  • Communication via defined interfaces — services do not share internal code, only API contracts
  • Heterogeneous technology possible — each service can use the language and framework best suited to its needs

Monolith vs Microservices

  • Monolith — all business logic, data layer and presentation are compiled and deployed in a single artifact (WAR/EAR)
  • Microservices — the application is divided into N autonomous services, each with its own lifecycle
  • The monolith is simpler to develop initially, but becomes difficult to maintain and scale at large scale
  • Microservices introduce operational complexity (network, observability) but offer greater agility in the long run

Conway's Law

"Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations." — Melvin Conway, 1967. In practice, teams working on microservices must be organized around autonomous business domains (team topology), not by technical layer.

⚖️ Benefits and Challenges

Benefits of microservices

  • Independent scalability — only the service under load is replicated, saving resources compared to horizontal scaling of an entire monolith
  • Independent deployment — faster continuous delivery, reduced risk per deployment
  • Technological diversity — each service chooses the stack best suited to its needs (JVM, Node, Go, Python…)
  • Resilience — the failure of one service does not stop the entire application if resilience patterns are applied
  • Autonomous teams — each team owns its service end-to-end (code, deployment, monitoring)
  • Better testability — each service is smaller, integration tests have a reduced scope

Challenges and complexities

  • Network complexity — inter-service calls introduce latency, timeouts, network failures and require resilience patterns
  • Data consistency — no distributed ACID transaction — you must accept eventual consistency and implement patterns like Saga
  • Distributed testing — integration and end-to-end tests are significantly more complex
  • Observability — a request traverses N services — distributed tracing infrastructure, centralized logging and metrics are required
  • Operational overhead — N services to deploy, monitor, update, version
  • Possible code duplication — shared utilities must be extracted into libraries or common services
✂️ Decomposition — Strategies

Decomposition by Business Capability

Each service corresponds to a stable business capability in the organization. Business capabilities are identified through an Event Storming or DDD modelling workshop.

  • Banking example: Customer Management, Account Management, Transfers, Notifications, Reporting
  • Advantage: services remain stable even if technologies or processes change
  • DDD bounded contexts delimit the responsibility of each service

Decomposition by Subdomain

  • Core domain — main domain, source of differentiating value — maximum investment
  • Supporting subdomain — necessary but not differentiating — can be developed internally or outsourced
  • Generic subdomain — generic functionality (authentication, billing) — use an existing product or SaaS

Database per Service Pattern

  • Each service owns its own database — not directly accessible by other services
  • Services can only access other services' data via their exposed APIs
  • Allows choosing the most suitable storage technology: PostgreSQL, MongoDB, Redis, Cassandra…
  • Requires managing eventual consistency for cross-service reads

Banking application — Microservices decomposition

  • client-service — customer profile management (CRUD, KYC)
  • account-service — bank account and balance management
  • transfer-service — inter-account transfer orchestration
  • notification-service — notification sending (email, SMS, push)
🔗 Inter-Service Communication

Synchronous communication — REST with MicroProfile Rest Client

Synchronous communication is suitable for requests that require an immediate response. It uses HTTP/REST with the MicroProfile Rest Client for a type-safe client.

  • @RegisterRestClient(configKey="account-service") — registers the interface as a REST client
  • URL configured via MicroProfile Config: account-service/mp-rest/url=http://account-service:8080
  • @Inject @RestClient AccountServiceClient accountClient — CDI injection of the client

Asynchronous communication — Jakarta Messaging / Kafka

  • Suitable for processing that does not require an immediate response (notifications, business events)
  • JMS (Jakarta Messaging) — message broker integrated into the Jakarta EE server (ActiveMQ, IBM MQ)
  • Kafka — event streaming platform — MicroProfile Reactive Messaging for integration
  • Advantages: temporal decoupling, buffer under load, event replay

MicroProfile Fault Tolerance

  • @Retry(maxRetries=3, delay=500) — retries the call on failure with delay between attempts
  • @CircuitBreaker(requestVolumeThreshold=4, failureRatio=0.75, delay=1000) — opens the circuit if too many failures
  • @Timeout(value=2000) — throws an exception if the call takes more than 2 seconds
  • @Fallback(fallbackMethod="getFallback") — fallback method in case of failure or open circuit
  • @Bulkhead(value=10) — limits the number of concurrent calls to prevent saturation

Circuit Breaker — States

  • CLOSED — normal state, requests pass through — failure accounting
  • OPEN — failure threshold exceeded, requests fail immediately without network call — wait delay before switching to HALF-OPEN
  • HALF-OPEN — a few test requests are allowed — if success: back to CLOSED, if failure: back to OPEN
🚪 API Gateway

Definition and role

The API Gateway is the single entry point of the microservices architecture. External clients have no knowledge of internal services — they communicate exclusively with the Gateway.

Gateway Responsibilities

  • Routing — routes each request to the appropriate internal service based on path or domain
  • Authentication & authorization — validates JWT/OAuth2 tokens before forwarding the request
  • Rate limiting — protects internal services against abuse and load spikes
  • Response aggregation — can call multiple services and merge responses into a single payload (BFF — Backend for Frontend)
  • SSL termination — handles HTTPS to clients, internal calls can remain in HTTP
  • Logging & monitoring — centralized point for metrics and traces of incoming calls

Request Routing

  • GET /api/accounts/{id} → account-service:8080/accounts/{id}
  • POST /api/transfers → transfer-service:8080/transfers
  • GET /api/clients/{id} → client-service:8080/clients/{id}

Response aggregation

  • The Gateway can call account-service and client-service in parallel to build a complete dashboard
  • Use of CompletableFuture or MicroProfile Reactive for parallel calls
  • Reduces the number of network round-trips for mobile clients (chattiness)
🔍 Service Discovery and Configuration

Service Discovery — Problem

In a dynamic environment (cloud, containers), service IP addresses change. Service Discovery allows a service to find the address of another service without hard-coding it.

Client-side Service Discovery

  • The client queries the service registry (e.g. Consul, Eureka) to get the address of the target service
  • The client itself chooses the instance (client-side load balancing)
  • Advantage: flexibility in load balancing strategies
  • Disadvantage: discovery logic in every client

Server-side Service Discovery

  • The client sends the request to a load balancer or the Gateway
  • The load balancer queries the registry and routes to an available instance
  • Advantage: simplicity on the client side
  • Example: Docker Compose internal DNS, Kubernetes Service

Docker Compose DNS

  • In Docker Compose, each service is accessible by its service name via internal DNS
  • account-service is reachable at http://account-service:8080 from any container on the same network
  • MicroProfile Config: account-service/mp-rest/url=http://account-service:8080

MicroProfile Config — Multi-environment configuration

  • Property injection via @ConfigProperty(name="account.service.url")
  • Source priority: Environment variables > System properties > microprofile-config.properties
  • Overrides without recompilation — ideal for Docker/Kubernetes deployments
  • defaultValue on @ConfigProperty for local development values
📊 Observability — The 3 Pillars

Metrics — MicroProfile Metrics + Prometheus

Metrics allow quantitative measurement of system behaviour over time.

  • @Counted — count the number of method invocations
  • @Timed — measure execution duration
  • @Gauge — instantaneous value (queue size, connection pool balance)
  • Endpoint /metrics exposed automatically in Prometheus format
  • Prometheus scrapes the metrics, Grafana visualizes them

Structured Logging — ELK Stack

  • Logs must be structured (JSON) to be indexable by Elasticsearch
  • Each log must include the correlation ID to link logs from different services for the same request
  • Logstash collects and transforms logs, Elasticsearch indexes them, Kibana visualizes them
  • MDC (Mapped Diagnostic Context) with SLF4J: MDC.put("correlationId", id)

Distributed Tracing — MicroProfile Telemetry (OpenTelemetry) + Jaeger

  • Distributed tracing allows following a request through all the services it traverses
  • Span — unit of work in a service (DB call, REST call) with duration and metadata
  • Trace — tree of spans representing the complete path of a request
  • Correlation ID — unique identifier propagated via HTTP headers (X-Correlation-ID, traceparent)
  • Jaeger or Zipkin collect and visualize traces
  • MicroProfile Telemetry (OpenTelemetry) automatically instruments Jakarta REST and Rest Client calls

Note: MicroProfile OpenTracing is deprecated since January 2023. Use MicroProfile Telemetry 1.0+ with OpenTelemetry instead.

🔄 Data Consistency

CAP Theorem

The CAP theorem (Brewer, 2000) states that a distributed system cannot simultaneously guarantee more than 2 of the following 3 properties:

  • Consistency (C) — all nodes see the same data at the same time
  • Availability (A) — every request receives a response (without guarantee of being the most recent)
  • Partition Tolerance (P) — the system continues to operate despite network partitions

In practice, in a distributed network, P is always present — the choice is therefore between C and A (CP or AP).

Eventual Consistency

  • The system eventually converges to a consistent state, without guarantee of immediate consistency
  • Common pattern in microservices architectures — services propagate changes via events
  • Reads may return slightly stale data during the propagation period

Saga Pattern

  • Replaces distributed ACID transactions with a sequence of compensatable local transactions
  • Choreography — each service publishes events and reacts to events from others (no central coordinator)
  • Orchestration — a central orchestrator (saga orchestrator) coordinates the steps and manages compensations
  • Each step must have a compensatory transaction in case of failure (e.g. cancel a debit if the credit fails)

Event Sourcing

  • The state of an entity is derived from the list of all events that modified it
  • The Event Store is the source of truth — events are immutable
  • Advantage: complete audit trail, ability to replay events, reconstruction of state at any point in time

CQRS — Command Query Responsibility Segregation

  • Separation of the write model (Commands) and the read model (Queries)
  • The write model guarantees consistency, the read model is optimized for performance
  • Projections (read models) are updated asynchronously from events
🐳 Deployment with Docker Compose

Structure of a Docker Compose file

  • version — Docker Compose format version (3.8 recommended)
  • services — definition of each container: image, ports, environment variables, networks, volumes
  • networks — internal networks isolating services (bridge by default)
  • volumes — persistent storage shared between containers or between container and host

Service definitions

  • image — Docker image to use (from Docker Hub or private registry)
  • build — path to a Dockerfile to build the image locally
  • ports — host:container mapping (e.g. "8080:8080")
  • environment — environment variables overriding MicroProfile Config
  • depends_on — startup order (does not guarantee readiness)
  • healthcheck — periodic verification that the service is operational
  • networks — list of networks the service belongs to

Local execution of all microservices

  • docker compose up -d — starts all services in the background
  • docker compose logs -f account-service — follows the logs of a service
  • docker compose ps — status of all containers
  • docker compose down — stops and removes containers
  • docker compose down -v — also removes volumes
🚀 Deployment Strategies

Blue-Green Deployment

  • Two identical production environments: Blue (current version) and Green (new version)
  • Traffic is switched instantly from Blue to Green via the load balancer
  • Immediate rollback in case of problem — switch back to Blue
  • Drawback: double infrastructure (doubled cost during transition)

Canary Deployment

  • The new version is deployed and receives a small percentage of traffic (e.g. 5%)
  • Monitoring of error and latency metrics on the Canary
  • If all goes well: progressive increase of traffic percentage up to 100%
  • Detects regressions on a real sample before a full deployment

Rolling Update

  • Instances are updated one by one (or in batches) without service interruption
  • Default strategy in Kubernetes (maxUnavailable, maxSurge)
  • During the update, both versions coexist — APIs must be backwards compatible

CI/CD Pipeline for microservices

  • Build — compilation, unit tests, static analysis (Sonar)
  • Test — integration tests, contract tests (Pact), component tests
  • Package — Docker image build, push to registry
  • Deploy — automatic deployment to staging, manual or automatic promotion to production

Kubernetes — introduction

  • Container orchestrator — automatic management of scheduling, scaling, self-healing
  • Pod — deployment unit (1 or more containers)
  • Service — stable network abstraction in front of a set of pods
  • Deployment — declares the desired state (N replicas of a given image)
  • ConfigMap / Secret — externalized configuration compatible with MicroProfile Config

Health Checks

  • Liveness probe — is the service alive? (otherwise restart)
  • Readiness probe — is the service ready to receive traffic? (otherwise removed from load balancer)
  • MicroProfile Health exposes /health/live and /health/ready — directly consumable by Kubernetes
