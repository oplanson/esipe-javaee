Key Concepts

Comparisons, communication strategies, microservices patterns, observability pillars, CAP theorem and glossary for microservices architecture.

Monolith vs Microservices

AspectMonolithMicroservices
DeploymentSingle artifact (WAR/EAR) — all-or-nothing deploymentN services deployed independently — targeted deployment
ScalabilityHorizontal only on the entire monolith — expensiveIndependent scalability per service based on actual load
Technological diversitySingle technology stack constrained for the whole applicationEach service chooses the stack best suited to its needs
Data managementShared database — common schema, native ACID transactionsDatabase per Service — eventual consistency, Saga for transactions
TestsSimple integration tests — everything is in the same processComponent and contract tests required — more complex
Team sizeThe whole team works on the same code — strong coordination requiredAutonomous teams per service (2-pizza teams) — Conway's Law
Recommended whenSmall team, low-complexity domain, fast start (MVP)High-growth application, multiple teams, differentiated scalability

Microservices Patterns — Overview

PatternProblem solvedSolutionWhen to use
API GatewayClients must know the address of each serviceSingle entry point that routes requests to internal servicesAlways in production — protection and simplification of exposed APIs
Circuit BreakerA slow or failing service cascades to the whole systemDetects failures and short-circuits calls to the failing serviceAll synchronous inter-service calls in production
SagaMaintain data consistency across multiple services without distributed ACID transactionSequence of local transactions with compensatory transactions on failureAny multi-service business operation (e.g. bank transfer)
Database per ServiceA shared database creates coupling and schema conflicts between servicesEach service is the sole owner of its databaseAlways — it is a prerequisite for microservices independence
CQRSThe optimal data model for writing differs from the optimal model for readingSeparate write (Commands) and read (Queries) modelsServices with frequent complex reads and transactional writes
Event SourcingLoss of change history — impossible to reconstruct past stateState is derived from the immutable sequence of past eventsDomains with mandatory audit trail or event replay requirements
Service DiscoveryService addresses change dynamically in cloud/container environmentsService registry enabling dynamic location of available instancesDynamic environments with auto-scaling (cloud, Kubernetes)

CAP Theorem

PropertyDescriptionCP systems (sacrifice A)AP systems (sacrifice C)
C — Consistency All nodes see the same data at the same instant. Every read receives the most recent data or an error. MongoDB (strict mode), HBase, Zookeeper —
A — Availability Every request receives a response (no guarantee of being up to date). The system remains available even if some nodes are down. — Cassandra, CouchDB, DynamoDB
P — Partition Tolerance The system continues to operate despite network partitions between nodes. Always required in production. ✅ Required ✅ Required

Glossary

TermDefinition
MicroserviceAutonomous application service with a single responsibility, independently deployable, owning its own database and communicating via lightweight interfaces
API GatewaySingle entry point of the microservices architecture — handles routing, authentication, rate limiting and response aggregation
Circuit BreakerResilience pattern detecting service failures and short-circuiting calls to prevent cascade effects — states: CLOSED, OPEN, HALF-OPEN
Saga PatternDistributed transaction management via a sequence of local transactions with compensation — variants: choreography (events) and orchestration (coordinator)
CQRSCommand Query Responsibility Segregation — separation of read and write models to independently optimize performance and consistency
Event SourcingPersistence of entity state as an immutable sequence of events — current state is recalculated by replaying events from the beginning
Service MeshNetwork infrastructure dedicated to inter-service communication — handles mutual TLS, retries, circuit breaking, tracing at proxy level (e.g. Istio, Linkerd)
Eventual ConsistencyProperty of a distributed system guaranteeing that if no new update is performed, all replicas will eventually converge to the same value
