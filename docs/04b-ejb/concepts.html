Key Concepts

Comparisons, reference tables, common patterns and EJB glossary.

⚠️ EJBs in Jakarta EE 11+: Enterprise Java Beans are deprecated in Jakarta EE 11 in favour of CDI Beans combined with Jakarta Transactions (@Transactional) and MicroProfile. EJBs remain supported for backward compatibility but new projects should use CDI @ApplicationScoped beans with @Transactional instead of @Stateless, and MicroProfile Reactive Messaging instead of @MessageDriven. See the migration table below.

EJB vs CDI — When to use which?

Feature EJB (Session Bean) CDI Bean
Declarative transactions ✅ Natively integrated (CMT) Via @Transactional (CDI interceptor)
Clustering & passivation ✅ Stateful beans passivable, native clustering ❌ Not natively supported
Remote access (@Remote) ✅ Via @Remote interface ❌ Local only
Security @RolesAllowed ✅ Built into the container Via custom interceptor
Timer Service ✅ @Schedule, @Timeout native ❌ Not available
Message-Driven ✅ @MessageDriven built-in ❌ Not supported (use MicroProfile Reactive Messaging)
Complexity ⚠️ Heavier — dedicated specification ✅ Lightweight, POJO-oriented
Recommended when Distributed transactions, clustering, remote calls, MDB, timers — or maintaining legacy apps Modern services, microservices, loose coupling — preferred for new projects

EJB to CDI Migration

EJB (legacy) CDI Modern equivalent Notes
@Stateless @ApplicationScoped Standard choice for stateless services in modern Jakarta EE
@Stateful @SessionScoped Conversational state in CDI session scope; requires Serializable
@EJB @Inject Standard CDI injection; works for any bean type
Container-Managed Transactions (CMT) @Transactional Jakarta Transactions interceptor; same semantics as CMT @TransactionAttribute
@MessageDriven MicroProfile Reactive Messaging @Incoming / @Outgoing on CDI beans; works with Kafka, AMQP, JMS

Session Bean Types

Type Annotation State preserved Pooling Typical use case
Stateless @Stateless ❌ No state between calls ✅ Instance pool managed by the container Stateless business services, DAO facades, REST backends
Stateful @Stateful ✅ State per client, per conversation ❌ Dedicated instance per client Shopping cart, multi-step wizards, collaborative editing
Singleton @Singleton ✅ Shared global state ❌ Single instance Application cache, global configuration, shared counters

@TransactionAttribute Values

Attribute Called WITH existing transaction Called WITHOUT existing transaction
REQUIRED (default) Participates in existing transaction Creates a new transaction
REQUIRES_NEW Suspends existing, creates an independent new transaction Creates a new transaction
MANDATORY Participates in existing transaction ⛔ Throws EJBTransactionRequiredException
SUPPORTS Participates in existing transaction Executes without a transaction
NOT_SUPPORTED Suspends existing, executes without a transaction Executes without a transaction
NEVER ⛔ Throws EJBException Executes without a transaction

EJB Declarative Security

Annotation Scope Description
@RolesAllowed({"ROLE1","ROLE2"}) Class or method Allows only callers possessing one of the listed roles
@PermitAll Class or method Allows all callers with no role restriction
@DenyAll Class or method Denies all calls — method inaccessible regardless of role
@RunAs("ROLE") Class only Executes the bean under a different security role (privilege escalation)
@DeclareRoles({"R1","R2"}) Class only Declares known roles for use in isCallerInRole()

Common EJB Patterns

Pattern name Description When to use
Service Facade A Stateless EJB exposes a simplified API hiding the complexity of internal subsystems (JPA, JMS, other EJBs) When clients (REST, JSF) should not know the details of internal operations
Session Facade A Stateful EJB orchestrates multiple operations over multiple calls for the same client, maintaining intermediate state Multi-step workflows requiring context preserved between requests
DAO Pattern A Stateless EJB encapsulates all CRUD operations on a JPA entity, separating data access logic from business logic Always — to isolate the persistence layer and facilitate unit testing

Glossary

Term Definition
EJB Enterprise Java Beans — server-side Java components managed by the Jakarta EE container, encapsulating business logic and delegating cross-cutting services (transactions, security, timers) to the container
@Stateless Annotation declaring a Session Bean with no conversational state — pooled by the container, ideal for high-performance business services
@Stateful Annotation declaring a Session Bean that preserves state per client — one dedicated instance per conversation, passivable by the container
@Singleton Annotation declaring a Session Bean of which only one instance exists in the entire application — requires explicit concurrency management
@MessageDriven Annotation declaring a Message-Driven Bean — asynchronous component triggered by the arrival of JMS messages in a queue or topic
CMT / BMT Container-Managed Transactions / Bean-Managed Transactions — two EJB transaction management modes. CMT delegates to the container (via @TransactionAttribute), BMT manages manually via UserTransaction
@EJB Injection annotation for injecting a reference to another EJB into a Jakarta EE component — analogous to @Inject but specific to EJBs. Prefer @Inject in modern code.
Timer Service EJB service for scheduling method execution at defined times — via @Schedule (automatic, cron-style) or via the programmatic TimerService API
Activation Configuration Set of @ActivationConfigProperty properties configuring an MDB — destination type, JNDI name, message filter, acknowledgement mode
