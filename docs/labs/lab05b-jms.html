Lab 05B

Jakarta Messaging (JMS)Messagerie Jakarta (JMS)

Add asynchronous enterprise messaging to the banking application: a JMS producer publishes transaction events to queues and a topic; Message-Driven Beans process them for transaction handling, email notifications, durable audit logging, and dead-letter recovery — all on Open Liberty with the embedded wasJms messaging engine and PostgreSQL. Ajoutez de la messagerie d'entreprise asynchrone à l'application bancaire : un producteur JMS publie des événements de transaction vers des files d'attente et un sujet ; des Message-Driven Beans les traitent pour le traitement des transactions, les notifications e-mail, la journalisation d'audit durable et la récupération des messages en échec — sur Open Liberty avec le moteur de messagerie wasJms intégré et PostgreSQL.

01Goal of the labObjectif du lab

Lab 04B introduced EJBs and CDI interceptors for synchronous transaction processing. In this lab you layer asynchronous messaging on top: a CDI bean acts as a JMS producer sending TransactionEvent objects to two queues (jms/transactionQueue, jms/emailQueue) and one topic (jms/auditTopic). Four Message-Driven Beans consume those destinations, and a utility class provides secure JSON-based message serialization as an alternative to Java object serialization. Le Lab 04B a introduit les EJB et les intercepteurs CDI pour le traitement synchrone des transactions. Dans ce lab, vous ajoutez une couche de messagerie asynchrone : un bean CDI fait office de producteur JMS qui envoie des objets TransactionEvent vers deux files d'attente (jms/transactionQueue, jms/emailQueue) et un sujet (jms/auditTopic). Quatre Message-Driven Beans consomment ces destinations, et une classe utilitaire fournit une sérialisation JSON sécurisée comme alternative à la sérialisation Java.

02What the starter gives youCe que fournit le starter

Starter anomalies to be aware of
  • The starter does not contain the com.bank.util package: you must create src/main/java/com/bank/util/JsonMessageUtil.java from scratch (Step 8).
  • persistence.xml uses transaction-type="JTA" and <jta-data-source>, which is correct for a JTA-managed environment — the README incorrectly describes it as RESOURCE_LOCAL. Keep JTA.
  • The Flyway Maven plugin in pom.xml points at bankdb (wrong); the actual database is bankingdb. Do not modify pom.xml: the plugin is only used for manual CLI migrations and the application runs Flyway at startup via Liberty.
  • docker-compose.yml publishes ports without 127.0.0.1: binding. The guide uses explicit host-binding in standalone podman run commands; see the security note in the Setup section.

Security noticeNote de sécurité

Demo credentials — never reuse in production

The database uses credentials bankuser / bankpass for demonstration only. In production, use a secret manager and never hard-code credentials. Ports are bound to 127.0.0.1 in all explicit podman run commands in this guide to prevent remote exposure, even though docker-compose.yml binds on all interfaces. If you use Compose directly, add 127.0.0.1: to each port mapping.

Identifiants de démo — ne jamais réutiliser en production

La base utilise les identifiants bankuser / bankpass à titre de démonstration uniquement. En production, utilisez un gestionnaire de secrets et ne codez jamais d'identifiants en dur. Les ports sont liés à 127.0.0.1 dans toutes les commandes podman run explicites de ce guide pour éviter toute exposition distante, même si docker-compose.yml lie sur toutes les interfaces. Si vous utilisez Compose directement, ajoutez 127.0.0.1: à chaque port mappé.

Security — why JSON instead of Java serialization?

Using ObjectMessage with Java serialization exposes your application to deserialization gadget-chain attacks (CVE class similar to Apache Commons Collections). A safer pattern sends a TextMessage with a JSON body and deserializes to a specific type on the consumer side, eliminating the ability to inject arbitrary classes. The solution includes JsonMessageUtil to demonstrate this alternative. For this lab you implement the utility; adapting the MDBs to use text messages is left as a bonus exercise.

Sécurité — pourquoi JSON plutôt que la sérialisation Java ?

L'utilisation d'ObjectMessage avec la sérialisation Java expose l'application aux attaques par chaîne de gadgets de désérialisation (classe CVE similaire à Apache Commons Collections). Une approche plus sûre envoie un TextMessage avec un corps JSON et désérialise vers un type spécifique côté consommateur, éliminant la possibilité d'injecter des classes arbitraires. La solution inclut JsonMessageUtil pour illustrer cette alternative. Pour ce lab, vous implémentez l'utilitaire ; l'adaptation des MDB pour utiliser des messages texte est laissée en exercice bonus.

Hint 2 — toJson and fromJson implementationsIndice 2 — implémentations toJson et fromJson 
public static String toJson(Object object) {
    if (object == null) return null;
    try {
        return jsonb.toJson(object);
    } catch (JsonbException e) {
        LOGGER.log(Level.SEVERE, "Serialization failed: " + e.getMessage(), e);
        throw new JsonSerializationException("Failed to serialize to JSON", e);
    }
}

public static <T> T fromJson(String json, Class<T> type) {
    if (json == null || json.trim().isEmpty()) return null;
    if (type == null) throw new IllegalArgumentException("type cannot be null");
    try {
        return jsonb.fromJson(json, type);
    } catch (JsonbException e) {
        throw new JsonSerializationException(
            "Failed to deserialize JSON to " + type.getName(), e);
    }
}

public static <T> T fromJsonSafe(String json, Class<T> type) {
    try { return fromJson(json, type); }
    catch (JsonSerializationException e) {
        LOGGER.warning("Safe deserialization failed: " + e.getMessage());
        return null;
    }
}
