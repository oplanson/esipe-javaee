🗄️ What is JPA / ORM?

ORM (Object-Relational Mapping) automatically maps Java objects to SQL tables, eliminating repetitive JDBC code and manual conversions.

Benefits of ORM with JPA:

  • Portability — switch databases without modifying business code
  • Productivity — less boilerplate code, focus on logic
  • Maintainability — consistent object model, no SQL/Java duplication
  • Security — parameterised queries by default, protection against SQL injections
  • Cache — first and second level cache for performance

JPA (Jakarta Persistence API) is the standard specification — Hibernate, EclipseLink, and OpenJPA are its implementations.

🏷️ Basic JPA Annotations

Essential annotations:

  • @Entity — declares the class as a persistent JPA entity
  • @Table(name="...") — specifies the corresponding SQL table name
  • @Id — designates the primary key field
  • @GeneratedValue — primary key generation strategy:
    • AUTO — provider chooses the strategy
    • IDENTITY — auto-increment column (PostgreSQL, MySQL)
    • SEQUENCE — database sequence (PostgreSQL, Oracle)
    • TABLE — dedicated generation table (portable)
  • @Column — customises the column (name, nullable, length, unique)
  • @Temporal — specifies the temporal type (DATE, TIME, TIMESTAMP)
  • @Transient — field excluded from persistence
  • @Lob — large object field (CLOB / BLOB)
🔗 Entity Relationships

Relationship types:

  • @OneToMany / @ManyToOne — bidirectional relationship (e.g. Client → Accounts)
  • @ManyToMany with @JoinTable — association table (e.g. Users ↔ Roles)
  • @OneToOne — exclusive relationship (e.g. Client ↔ Profile)

Fetch types:

  • LAZY (default for @OneToMany, @ManyToMany) — load on demand
  • EAGER (default for @ManyToOne, @OneToOne) — immediate loading

Cascade types:

  • PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL

Warning: the N+1 problem — use JOIN FETCH in JPQL for LAZY associations.

🔍 JPQL — Object-Oriented Queries

JPQL (Jakarta Persistence Query Language) operates on Java entities, not on SQL tables.

Key syntax:

  • SELECT c FROM Client c WHERE c.email = :email
  • SELECT c FROM Client c JOIN FETCH c.accounts WHERE c.id = :id
  • Named parameters — :param via query.setParameter("param", value)
  • Named queries — @NamedQuery on the entity, compiled at startup

Aggregation functions:

  • COUNT(c), SUM(a.balance), AVG(a.balance), MIN, MAX
  • GROUP BY, HAVING, ORDER BY
⚙️ Criteria API

The Criteria API builds dynamic type-safe queries in Java, without string concatenation.

Main elements:

  • CriteriaBuilder — query element factory (obtained via em.getCriteriaBuilder())
  • CriteriaQuery<T> — defines the result type
  • Root<T> — query starting point (represents the entity)
  • Predicate — condition (cb.equal, cb.like, cb.between…)
  • Join<T, V> — join between entities

Benefit: ideal for dynamically filtered searches (advanced search forms).

🔄 Transaction Management

JPA entity states:

  • New / Transient — object created, unknown to the persistence context
  • Managed — entity under EntityManager control (active context)
  • Detached — entity disconnected from context (after close or detach())
  • Removed — entity marked for deletion

EntityManager operations:

  • em.persist(entity) — New → Managed
  • em.merge(entity) — Detached → Managed (copy)
  • em.remove(entity) — Managed → Removed
  • em.find(Class, id) — retrieval by primary key
  • em.flush() — immediate synchronisation with DB

JTA vs resource-local:

  • JTA (Jakarta Transactions — Container-Managed) — use @Transactional or @TransactionAttribute, the container manages boundaries. Set transaction-type="JTA" in persistence.xml. Standard for Jakarta EE server deployments.
  • Resource-local (Application-Managed) — use EntityManager.getTransaction() managed manually. Set transaction-type="RESOURCE_LOCAL". Suitable for standalone Java SE or integration tests.
🚀 Migrations with Flyway

Flyway manages database schema versioning via versioned, traceable SQL scripts.

Naming convention:

  • V1__init.sql — initial schema version
  • V2__add_accounts.sql — add accounts table
  • V3__add_index_email.sql — add index

Execution order:

  • Migrations are executed in ascending numeric order
  • Each executed migration is recorded in the flyway_schema_history table
  • An already-applied migration will never be re-executed
  • Any modification to an already-applied file causes a checksum error

Best practice: always create a new migration file, never modify an existing one.

🔌 JNDI and DataSource

JNDI (Java Naming and Directory Interface) allows locating resources (DataSource, JMS queues) by their logical name.

JNDI lookup:

  • Standard name: java:comp/env/jdbc/bankDB
  • Programmatic lookup: InitialContext ctx = new InitialContext(); DataSource ds = (DataSource) ctx.lookup("java:comp/env/jdbc/bankDB");
  • Injection: @Resource(name="jdbc/bankDB") private DataSource ds;

Liberty server.xml configuration:

  • <dataSource jndiName="jdbc/bankDB"> — declares the DataSource
  • <jdbcDriver libraryRef="PostgreSQLLib"/> — JDBC driver
  • <properties.postgresql serverName="..." portNumber="5432" databaseName="..."/>
  • Configurable connection pool: minPoolSize, maxPoolSize, connectionTimeout
