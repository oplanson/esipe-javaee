Authentication Methods — Comparison

MethodProtocolSecurityStateUse CaseRisks
Basic Auth HTTP RFC 7617 ⚠️ Weak without TLS Stateless Dev APIs, internal tools Credentials in clear (Base64) without HTTPS, replay possible
Form-Based HTTP POST + Session ✅ Good Stateful Traditional web applications CSRF, session fixation, session hijacking
Token (JWT) RFC 7519 / Bearer ✅ Good Stateless REST APIs, microservices, SPAs XSS if stored in localStorage, token theft, no immediate revocation
Certificate (mTLS) TLS/X.509 RFC 5246 ✅✅ Excellent Stateless Service-to-service, critical systems Certificate management complexity, PKI required
OAuth2 / OIDC RFC 6749 / OIDC ✅✅ Excellent Stateless Delegation, social login, identity federation Protocol complexity, redirect_uri misconfiguration

RBAC vs ABAC

FeatureRBACABAC
FlexibilityLow — based on predefined rolesHigh — combination of multiple attributes
ComplexitySimple to understand and administerComplex — XACML policy, conditional rules
ScalabilityGood for few rolesExcellent for many access cases
Use CaseApplications with clear business roles (ADMIN, USER, VIEWER)Multi-tenant systems, fine control (time, IP, classification)
Jakarta EE Support✅ Native — @RolesAllowed, SecurityContext.isCallerInRole()⚠️ Partial — requires custom implementation
AuditEasy — who has access to what by roleDifficult — dynamic contextual decisions
ExampleUser "alice" has the ADMIN roleUser "alice" can access if department=HR and time between 8am-6pm

OWASP Top 10 Vulnerabilities (2021)

RankVulnerabilityDescriptionJakarta EE Mitigation
A01 Broken Access Control Unauthorized access to resources or features @RolesAllowed, SecurityContext, server-side authorization testing
A02 Cryptographic Failures Sensitive data transmitted or stored in clear Mandatory TLS, bcrypt/Argon2 for passwords, JCE encryption
A03 Injection SQL, LDAP, OS injection via unvalidated data Parameterized JPQL, Jakarta Validation (@NotNull, @Size), JPA criteria
A04 Insecure Design Absence of threat model, insufficient security controls from design Threat modeling, defense-in-depth, principle of least privilege
A05 Security Misconfiguration Insecure default configurations, detailed errors exposed Disable debug endpoints, configure error pages, harden server.xml
A07 Identification & Auth Failures Weak authentication, non-invalidated sessions, weak passwords Jakarta Security API, HTTPS, token expiration, secure @RememberMe
A03 XSS (Cross-Site Scripting) Injection of malicious scripts into web pages HTML encoding of outputs, CSP header, server-side validation
A08 Software & Data Integrity Failures Updates with unsigned dependencies, insecure deserialization Verify Maven checksums, avoid native Java deserialization

JWT Token Structure

Tip: MicroProfile JWT Propagation (MP-JWT) standardizes JWT-based authentication across microservices. Annotate your JAX-RS application with @LoginConfig(authMethod="MP-JWT") and inject claims with @Claim.

PartDescriptionExample content
Header Token metadata: signature algorithm (alg) and type (typ) {"alg": "RS256", "typ": "JWT", "kid": "rsa-key-2026"}
Payload Claims: identity, roles, issuance and expiration dates, issuer, audience {"iss": "https://auth.bank.com", "sub": "alice", "aud": "banking-api", "exp": 1735689600, "iat": 1735686000, "groups": ["USER", "MANAGER"], "upn": "alice@bank.com"}
Signature Cryptographic hash of (Base64URL(header) + "." + Base64URL(payload)) signed with the private key RSA-SHA256 or HMAC-SHA256 — verifiable with the public key
Final format The three parts Base64URL-encoded, separated by dots eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.SflKxwRJSMeKKF2QT4fwpMeJf36

Security Best Practices

CategoryPracticeJakarta EE Implementation
TransportAlways HTTPS in production, HTTP → HTTPS redirectLiberty <ssl>, HSTS header, disable HTTP port
AuthenticationUse appropriate hashing algorithms (bcrypt, Argon2)IdentityStore with BCrypt, never store passwords in clear
AuthorizationPrinciple of least privilege — grant the minimum necessary@DenyAll by default, @RolesAllowed explicit
TokensShort lifetime for access tokens (15-60 min)Claim exp in JWT, separate long-lived refresh tokens
InputsValidate and sanitize all user inputsJakarta Validation, @Pattern, @Size, @Valid
ErrorsDo not expose technical details in error messagesJAX-RS ExceptionMapper returning generic messages
SecretsNever hard-code credentials and keys in codeMicroProfile Config from env vars, Kubernetes Secrets
HeadersAdd HTTP security headers in all responsesJAX-RS or Servlet Filter adding CSP, HSTS, X-Frame-Options
LogsLog access and authentication failuresAvoid logging sensitive data (passwords, tokens)

Glossary

TermDefinition
CIA TriadThe three pillars of security: Confidentiality, Integrity, Availability
JWTJSON Web Token — RFC 7519 standard for self-contained signed tokens, composed of a header, payload and Base64URL signature
OAuth2Authorization delegation protocol (RFC 6749) allowing an application to access a user's resources without knowing their credentials
OIDCOpenID Connect — identity layer on top of OAuth2 adding an ID Token (JWT) for user authentication
RBACRole-Based Access Control — access control based on predefined roles assigned to users
ABACAttribute-Based Access Control — access control based on dynamic attributes (user, resource, environment)
mTLSMutual TLS — bidirectional TLS authentication where both client and server present an X.509 certificate
OWASPOpen Web Application Security Project — organization producing the Top 10 most critical web vulnerabilities
CSPContent Security Policy — HTTP header defining authorized content sources to prevent XSS
CORSCross-Origin Resource Sharing — browser mechanism controlling HTTP requests toward a domain different from the origin
CSRFCross-Site Request Forgery — attack forcing an authenticated user to execute an undesired action on a third-party site
HSTSHTTP Strict Transport Security — header forcing the browser to use HTTPS exclusively for a given domain
